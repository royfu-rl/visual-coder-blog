 WorldBench : Evaluating LLMs on
 Three.js Voxel World Generation 

 Krish Bakshi

 Email: krishrajeshbakshi@gmail.com 

 Abstract 

 Large language models can now write complete, interactive 3D worlds as code, but
grading those worlds automatically is unreliable. Existing judges take one view of
the output: a vision–language model scores a few rendered snapshots, or a language
model reads the source. On worlds written by five frontier models we find that the
two views disagree on 32% of required items, mostly code that no frame shows, and
that fixed views miss small close-up contents. We present WorldBench, a benchmark and judge for open-ended,
LLM-generated Three.js worlds. From one prompt describing a floating voxel island
with ten biomes, physics, and day/night and seasonal cycles, the judge
 explores the running world, controlling its clock, orbiting it, and sending a
navigator agent to frame each biome, and reads the code for what it sees.
Neither channel is trusted on its own: a code quote counts only if it is text the
source contains, and visual claims are checked against measured pixels where the
property is measurable. A mutation test, in which we remove features by
construction, shows that code-only judging gives full credit to four of five removed features,
because their code remains in the file. Our judge cuts the points kept on removed
features by a third (5.44 to 3.55 of 7.11), and what it still credits is mostly code
that exists but never runs.
We evaluate five frontier models: Claude Fable 5.1, GPT-6 Astra, Kimi K3,
Grok 4.7 and Gemini 3.1 Pro.
Code, prompt, tests and judge configuration are available at
 https://github.com/KrishBakshi/worldbench . 

 1 Introduction 

 Asked for a 3D world, a language model no longer returns a description or a single
asset. It returns a program: one HTML file that builds terrain from noise
functions, places forests from lookup tables, runs water and weather as particle
systems, and turns night into day on its own clock. What that world is only
exists while the program runs. Grading it means answering two questions at once:
does the code build the thing, and does the running world show it? Neither answer
implies the other. Code can build an animal at coordinates no camera ever sees, or
define a weather system that never switches on. A render can show a feature that no
identifier names, such as a terraced noise threshold that is a sandstone
mesa. 

 Automatic evaluators usually answer one of the two. Render-based benchmarks score
a handful of fixed views with a vision–language model
 [ 5 , 2 , 10 ] . They see the result but
not its cause, a still frame cannot show a river flowing, and the judge’s verdict is
taken as given. For generated Three.js programs, Lu et al. [8] found
screenshot-plus-VLM judging essentially uncorrelated with ground truth. Code-based
evaluation reads the source, with a model or with patterns. It sees the cause but not
the result, and pattern matching is easy to game: on our own early keyword test, a
one-line file declaring const pine=1,…,lava=9 scored as highly as every
real world. WorldCoder-Bench sidesteps both by requiring each program to expose its
state through a fixed interface and checking it against expert-written contracts.
That works for functional tasks. It does not fit an open-ended creative prompt:
“the desert borders the jungle” or “autumn looks different from spring” is not
a state variable anyone can specify in advance, and asking for an interface changes
the task being measured. 

 On five frontier models’ worlds, the two views disagree on 32% of required items.
The code is there and the frames never show it in 105 of 365 cases, and the frames
show it but the code was not found in 10. Disagreement alone does not say which view
is right, so we test that on features we remove by construction
(Section 5.3 ). 

 We present WorldBench, a benchmark and judge for open-ended, LLM-written 3D
worlds. One prompt asks for a floating voxel island with ten biomes in stated
relations, physical water, lava and weather, and day/night and seasonal cycles.
Five tests with fixed maxima, 280 points in total, score it item by item. The judge
 explores the running world (Figure 1 ): it takes control of the world’s own clock,
measures which render is day instead of assuming it, orbits the island for wide
views, and sends a navigator agent in for close views of each biome. It also
 reads the code for what it is looking at. Neither channel is trusted. A code
quote counts only if it is text the source contains, a navigator’s “found it” is
re-checked blind, and wherever a property is measurable (brightness, motion,
colour shift), pixels decide instead of the visual judge. 

 Our contributions: 

 • 

 A benchmark for open-ended, code-generated 3D worlds. The prompt asks
for nothing on the grader’s behalf: one fixed prompt, a 280-point ladder of
item-level tests, and a bounded, error-only generation protocol
(Section 3 ). 

 • 

 A judge that explores and reads, and trusts neither , with every
model-made claim backed by the source text or by measured pixels before it scores
(Section 4 ). 

 • 

 Evidence for each design choice on five frontier models’ worlds: an
agreement analysis, a close-versus-wide ablation, a mutation test with features
removed by construction, and an error analysis over four error classes
(Section 5 ).

 2 Related work 

 Evaluating generated 3D content. 

 T 3 Bench [ 5 ] scores text-to-3D methods from
multi-view renders, with a quality metric and an alignment metric in which a
language model judges multi-view captions; it reports that current methods struggle
most with surroundings and multi-object scenes, the kind of content our island
asks for. GT23D-Bench [ 2 ] pairs a large annotated asset set
with ten metrics validated by correlation with human judgment. SceneEval
 [ 10 ] evaluates indoor scene synthesis on explicit requirements 
(object counts, attributes, relations) and implicit expectations (support,
collisions, navigability), using a vision–language model on fixed renders and
geometric checks on the scene’s meshes wherever possible. Our split between
required contents (WC003) and physical behaviour (WC004) follows the same
explicit/implicit distinction. What differs is the object being judged: these
benchmarks score assets or scene data, while we score a program whose output exists
only when it runs, and whose camera, clock and seasons we must drive ourselves. 

 Language models that build 3D scenes. 

 A line of systems uses language models to generate scenes rather than grade
them. SceneCraft [ 6 ] writes Blender Python from a scene graph
and refines it with a vision–language model that critiques the render. SceneX
 [ 12 ] plans procedural Blender commands over a curated asset
library and demonstrates natural landscapes and seasonal changes, the content
closest to ours. Reason-3D [ 1 ] uses large reasoning models for
object retrieval and collision-aware placement, and SceneOrchestra
 [ 4 ] trains an orchestrator to emit whole tool-call
trajectories instead of rendering after every step. These systems give the model
scene tools and asset libraries. Our models get one prompt and plain Three.js and
must write the procedural generation themselves, repairing from errors only
 [ 3 , in the spirit of] . 

 Benchmarks of LLM-written interactive worlds. 

 WorldCoder-Bench [ 8 ] is the closest work: 2,026 tasks
whose output, like ours, is one self-contained Three.js page. It runs each program
in a headless browser, requires it to expose a standard state object, applies
scripted actions, and checks state changes against hidden contracts written by
experts. It also reports that screenshot-based judging fails on these programs.
We share the medium and the scepticism about visual judges, but take the opposite
task shape: one open-ended world instead of thousands of narrow functional tasks,
with nothing exposed for the grader. Where it replaces visual judging with
contracts, we keep visual judging and verify it, against the source text and
against pixels. Table 1 compares the benchmarks side by side.

 Models as judges. 

 Strong language models agree with human preferences often enough to serve as
judges [ 11 ] , but they carry biases, including a preference for
their own family’s outputs [ 9 ] . Most judge pipelines respond
by calibrating the judge against people. Our worlds are open-ended and synthetic,
so there is no reference answer to annotate. We instead check each judgement
against evidence the model under test cannot fake, and validate the judge by
mutation [ 7 ] : features removed on purpose, where the correct
verdict is known by construction. 

 3 The benchmark 

 Figure 2 shows the whole flow, from prompt to score. This section
covers the prompt, how worlds are produced, and how they are scored;
Section 4 covers how each item’s evidence is gathered and checked. 

 Figure 2: The evaluation flow. The model under test turns one fixed prompt into a
single world.html , which must load as a Three.js world. Evidence is then
gathered two ways, by reading the code and by exploring the running world, and each
kind is checked (quotes against the source, sightings against pixels). 

 One open-ended prompt. 

 Every model receives the same prompt (about 2,000 words, reproduced in
Appendix A ). It asks for a single, self-contained HTML file that
renders, with Three.js, a floating voxel island in a black void: ten biomes (snow
mountains, snowy conifer forest, highlands, jungle, swamp, flowering grove,
grassland plateau, coastal delta, desert, volcano) placed in stated relations to
one another (the forest sits in front of the mountains, the swamp on the jungle’s
far side, the volcano away from the desert); water, lava and particles that behave
physically; a day/night cycle and four seasons; and a small on-screen legend. The
prompt fixes relationships, not coordinates, and says nothing about how the world
will be graded. There is no ground-truth world to compare against. The prompt asks for nothing
on the grader’s behalf. Grading runs a copy with one clock patch
(Section 4 ). 

 Generation. 

 We evaluate five models, each queried through its developer’s official API:
Claude Fable 5.1 (Anthropic), GPT-6 Astra (OpenAI), Kimi K3 (Moonshot AI),
Grok 4.7 (xAI) and Gemini 3.1 Pro (Google DeepMind); Table 8 lists
the generation settings. Each world is one completion, sampled at temperature 1.0, continued if the response is truncated. Before
grading, a bounded repair loop removes crashes that would otherwise hide the whole
world: the file is parsed ( node --check ) and loaded in a headless browser,
and any parse error or console error is sent back to the model, which may edit the
file with small verified replacements, for at most five rounds. The model is told
this budget up front. Repairs see only errors, never renders or scores, so
generation never sees the grader’s view. 

 The ladder. 

 A world is graded by five tests with fixed maxima, 280 points in total
(Table 2 ), so totals compare across models. Each test scores many
small, checkable items rather than one holistic grade, and every item is
decided by the judge described next. Throughout the paper, worked examples use one
 reference world , claude-fable-5-1 , the highest-scoring world. 

 WC002 is the one test of spatial reasoning: the prompt describes the island only
through relations, and the world must turn them into a map. A model reads the whole
source, finds where the layout decides each cell’s biome (region centres, boxes,
bands, coast rules) and reports which biomes touch and how high each sits. It may
list two biomes as touching only when the positions it found put them side by side,
quoting those numbers. Fixed rules written from the prompt then score that report
(Figure 3 ). The reference world scores 15 of 20 here. The reading is a
model’s, so Section 6 checks it against the actual biome maps of
four worlds.

 4 The judge: explore and read, trust neither 

 Figure 1 shows the idea. Reading looks at the cause: the program
as written. Looking looks at the result: the program as it runs. An item
scores only for the evidence that survives its check. Several
models fill the judge’s roles; they and their settings are listed in
Appendix F . Each check below exists because a simpler judge failed on
real worlds; Appendix E lists those judges and how each failed. 

 4.1 Looking: exploring the running world 

 The saved world.html is not edited. Grading runs a copy whose clock is
patched, as in Stage I, in a headless browser. An init script seeds
 Math.random , so a reload builds the same island, and reaches the scene and
camera through Three.js’s own developer-tools hook. 

 Looking runs as a four-stage pipeline: the world’s time is brought under control,
views are taken, motion is recorded, and every close view is checked blind before
it can be judged. 

 Stage I: Controlling time. 

 Every world keeps its own clock, written its own way. A language model patches that
clock so it obeys an externally set time of day and season. The patch is tightly
constrained: at most six edits, each under 600 added characters, each required to
read the external time, so a patcher cannot add lighting the model never wrote.
The patch’s mapping from requested time to noon is not trusted either. The world is
rendered at four requested times and the brightest render, by mean luma, is taken
as day (Figure 4 , top). In the reference world, noon falls at a quarter
of the cycle, where a fixed “half-way is noon” rule would have chosen dusk. The
four seasons are then rendered at day (Figure 4 , bottom). Change over
time is measured on these frames, not judged: mean luma for night, frame difference
against day, and chromaticity shift for twilight tint and seasons. In the reference
world the visual judge described the four season frames as “visuals remain identical”; their
measured chromaticity shift from spring is 0.019, 0.035 and 0.024,
and the measurement decides. 

 Figure 4: Controlling time, reference world. Top : the world’s own clock,
patched to the requested time of day; the brightest render (here requested time
0.25, not 0.50) becomes day for every later view, and each other render’s frame
difference from day ( day) is recorded. Bottom : the four seasons at
day. The visual judge called these frames identical; the measured chromaticity
shift from spring is non-zero for every season, and it is the measurement that
scores the item. 

 Stage II: Wide and close views. 

 From day, the judge takes wide views (an overview, four orbits, and the four
seasons) and close views of each biome. Close views come from a
 navigator agent , a tool-calling loop of observe act 
observe. Each turn it receives the page’s accessibility tree and its latest frame,
and calls exactly one tool: click (a legend entry the world itself
provides), orbit , pan , zoom , save or
 give_up , within an eight-step budget. Figure 5 shows the
reference world’s longest episode: the navigator clicks the swamp’s legend entry,
zooms in, orbits away and back to bring the water channels into frame, zooms again
and saves (6 steps). Each turn keeps only the newest frame in context,
so a long episode does not grow the prompt. 

 Figure 5: One navigator episode, reference world, swamp. Each frame is what the
agent saw after the action below it; frames are re-rendered from the recorded
actions with no model call (seeded world, pinned clock, so only animation phase
differs from the original run). The saved frame (6) counts only after blind
identification agrees. Bottom : a rejection from another graded world outside
the five reported here; the navigator saved the delta with confidence
0.7, and the blind answer was forest. 

 Stage III: Motion bursts. 

 A single frame cannot show motion, and a visual judge asked about motion across
frames will report it from appearance alone. For each saved close view the
judge therefore takes a still-camera burst : four frames 2 s apart
with the camera fixed, then one zoom out and three more, and an overlay that paints
every changed pixel. A visual “it moves” counts only if the burst’s pixels
changed. Figure 6 shows the same motion item in two worlds. In one,
rain falls and 38.4% of pixels change. In the other, the visual judge
again reported “Vertical falling rain particles”, but 0.0% of pixels changed, so the
claim is refused. A typical world yields about a hundred frames in total. 

 Figure 6: Still-camera motion bursts for one WC004 item, rain_shaft_fall , in
the jungles of claude-fable-5-1 (left) and gpt-6-astra (right). Red in the overlay marks pixels that changed anywhere in the
burst. The visual judge reports falling rain in both; only the burst whose pixels
changed earns the frames half of the motion credit. 

 Stage IV: Blind identification. 

 The navigator’s claim that it found a biome is not trusted: in one world it saved
the volcano as the swamp with full confidence. Every saved frame is re-taken with
the page’s own interface hidden, so the clicked legend label cannot give the answer,
and then identified blind : all of a world’s saved frames go to one shuffled
call that is never told which biome a frame was meant to show. A frame counts as a
biome’s close view only if the answer matches (Figure 5 , middle row);
otherwise it is dropped and that biome is judged from the wide views alone
(Figure 5 , bottom row). Appendix Figure 12 shows every
close view of the reference world.

 Stage I: Quoting. 

 For each biome, a code probe lists the test’s items and must quote, for each one
it claims, the source lines that build it. 

 Stage II: Verifying. 

 A quote counts only if it is text the
source contains: matching ignores whitespace and is done line by line, at least
80% of a quote’s lines must be found, and a line whose ending was garbled in
copying still matches if its first 85% is verbatim. Invented code does not pass.
Before this check, a model was credited for a plausible
 scene.add(new THREE.Mesh(palmGeo,…)) that appeared nowhere in the file.
A quote must also come from that biome’s own code, and one quote cannot satisfy
two items. 

 Stage III: Repairing. 

 Probes copy imperfectly, joining separate lines or abbreviating with an
ellipsis. Rather than loosen the check, a quote repair step lets a model choose
 line numbers from a numbered window of the file, and rebuilds the quote from
those lines, so it can select code but never write it. 

 Stage IV: Rechecking. 

 When the frames show an item but the probe found no code for it, an evidence agent 
searches the source with read-only tools ( grep , line reads and a small set
of text-only shell commands) over a sandboxed copy of the file, within ten tool
calls. It is told that a sighting is a lead, not proof, and that inferring a
feature from a neighbouring one (“there are pools, so there must be banks”) is
not evidence. Only these disagreements are searched again. This is the one stage
that waits for Looking, since it needs the frames. 

 4.3 Combining the two 

 An item’s points are split evenly between the two channels
(Figure 7 ). The code half is earned by a quote that passes the
checks above. The frames half is earned when the visual judge reports the item in
a blind-confirmed frame of that biome, or, where the property is measurable, when
the pixels confirm it (Stages I and III). Items that must not appear in a biome (a palm in the desert, snow on the
volcano) cost points when either channel finds them: a verified quote that builds one
in the biome, or a sighting in its frames.

 5 Results 

 Setup. 

 We grade one world from each of the five models of Section 3 , all
with the same judge configuration. We ask three questions of the judge before reading the leaderboard: do its two
channels disagree, does exploring matter, and does it notice when a feature is
really gone? 

 5.1 Code and frames disagree on a third of items 

 WC003 checks 73 required items per world, 365 in total. For each, the judge has a
code verdict and a frames verdict (Table 3 ). They agree on 250
items and disagree on 115 (32%), between 26% and 41% per world. Disagreement is
lopsided: in 105 items the code is found but no frame shows the item, against 10
in the other direction. A judge that only read code would credit 289 items (79%);
one that only looked would credit 194 (53%). “Not seen” means not seen in our
frames, which is either a real absence or an item our capture did not reach;
Section 5.3 separates the two on items we removed ourselves, and
Section 5.5 names the two disagreement directions as error classes E2
( unobserved ) and E3 ( unattributed ).

 5.2 Close and wide views see different things 

 To test whether exploring matters, we re-ran WC003’s visual judge on the same saved
frames with the navigator’s close views removed, leaving the overview and four
fixed orbits, which is what a snapshot judge has. Prompt, items and judge are
unchanged (Table 4 ). Close views see more required items (194
against 178), but not by a wide margin, and the two sets differ: 42 items are seen
only up close and 26 only in the wide views. The close-only items are small
contents (animals account for 12 of the 42, followed by flowers, tall grass, vines
and rain shafts). The wide-only items are biome-scale layout and weather (swamp
channels, river mouths, islands, flat basins, mist, ash). The code probe
independently supports 81% of the extra sightings on both sides, so neither set
is mostly hallucinated. Totals barely move (320.2 against 322.1 WC003 points over
five worlds), but individual worlds do: grok-4-7 loses 5.5 points without
close views and gemini-3-1-pro gains 8.9, which swaps kimi-k-3 
and grok-4-7 in the WC003 ranking. Exploration matters for coverage, not
because any one camera is better. Two caveats apply: the close condition gave the
judge two images per biome and the wide one five, and the navigator confirmed
only 5 of 10 biomes in grok-4-7 ’s world.

 5.3 Removing features on purpose 

 Since there is no reference answer to annotate, we create ground truth by

 6 Limitations 

 Unreached code still earns half. 

 The code half asks whether a quote is real text in the source, not whether that
code ever runs. In the mutation test, three features whose functions were kept but
never called still earned their code half, and a feature switched off with
 if(false) was quoted by its disabled line. Checking that quoted code is
reachable from the world’s build or frame loop would close most of this gap. 

 The visual judge can still be fooled. 

 Verification narrows what the visual judge decides but does not remove it. Where no
pixel measurement applies, a look-alike can pass: drifting snowfall near the peaks
was accepted as a blizzard after the blizzard had been removed. 

 Placement is a model’s reading. 

 WC002’s neighbour list comes from a model reading the layout code, and unlike the
item quotes it is not checked pair by pair. Against the actual biome maps of four
worlds it is right on 61 of 76 rule-relevant pairs (of 19 each:
 claude-fable-5-1 17, kimi-k-3 14, gemini-3-1-pro 14, and 16
on claude-opus-5-5 , a world outside the five reported here). The other two
reported worlds, including grok-4-7 , which tops placement, have no such map,
so their placement scores are unchecked. The errors are mostly missed links, so a world can lose a placement point for a border it does have.
Reading each world’s own biome map from the running page would make this exact, but
the code that stores that map differs in every world. In a trial on the same four
worlds, a model asked to locate it reproduced the exact map on its first attempt in
two; in the other two it missed a biome or returned values it could not map. 

 E2 (unobserved) mixes two causes. 

 An item the frames do not show is either not rendered or not captured. The navigator
confirmed all ten biomes in three worlds, nine in one, and five in
 grok-4-7 ’s, so part of that world’s E2 points reflect capture, not
the world. 

 Noise and scale. 

 We grade one world per model, from one prompt, once, and single item verdicts are
noisy (Section 5.3 ). Totals are steadier, but we treat gaps of a few points between neighbouring models
as ties and do not claim a ranking among them. The mutation test covers five
removals in one world. Repeated generations and repeated grading would give the
variance this paper does not report. 

 No human labels, by design. 

 The worlds are open-ended and synthetic, with no reference answer to annotate, so
we validate the judge by construction rather than by agreement with people.
Mutation shows whether the judge notices what we changed, not whether it agrees
with a person on everything we did not. 

 Judges and medium. 

 Every judge role is a model from the same developer as one model under
test (Appendix F ). That model ranked last, but we did not measure the
bias with a cross-family judge. The benchmark covers Three.js worlds only. 

 7 Conclusion 

 A world written as code has to be graded twice, once for what the program says and
once for what it shows, because the two disagree on a third of items, mostly code that no frame shows, and
neither can say alone which is right. WorldBench grades both: it explores the running
world close and wide, reads the code for what it is looking at, and lets an item
score only for evidence that survives a check against the source or the pixels.
Placement is the one reading we do not verify item by item; on four worlds it
matched the biome map on 61 of 76 pairs (Section 6 ).
Removing features on purpose shows the gain over reading alone, and the gap that
remains: code that exists but never runs.

 # Floating Biome Island with Ocean -- World Description 

 ## Visual style (required) 

 Minecraft-like voxel / block aesthetic throughout: 

 - Terrain, cliffs, water, lava, trees, flora, and structures are built 

 from chunky axis-aligned cubes and blocky stacked forms -- not smooth 

 organic meshes, not photoreal terrain, not low-poly "soft" stylization.

 A floating landmass hangs motionless in an infinite black void. 

 Viewed from a high orbit, nearly the entire surface should be readable at

 1. Snow mountains occupy the far / behind end of the island -- the final

 3. Highlands occupy an elevated plain to the side of the snow forest --

 4. Dense jungle is a large wet canopy region, with a backwater / swamp

 5. Flat grassland plateau is the open river plain that receives wet- 

 corridor drainage and leads toward the coast. 

 6. Flowering grove is a moist pink basin off the plains / below the

 7. Desert is a vast arid basin (south / rain-shadow side) with its own

 8. Volcano is a separate tall cone on volcanic ground only (far from

 9. Coastal ocean and beaches wrap much of the southern and western edge.

 - Prefer a clearly legible island: biomes spaced so each reads as its 

 own region from high orbit. 

 - Avoid collapsing adjacent biomes -- especially grassland vs flowering 

 grove, desert vs volcano, snow forest vs alpine peaks. 

 - Within each biome, flora and fauna should feel abundant for that

 - Mountains and the volcano dominate the skyline; desert flats and the

 Voxel / blocky animals (stacked cubes, same aesthetic as the land) --

 - Deer or similar grazers in jungle edges, grasslands, grove, conifers

 Layout and systems must follow ecological logic, not decoration: 

 - Water stays in the wet corridor: mountain melt -> through / past the

 - Flowering grove is a moist offshoot below the highland slope / plains

 - Desert is arid: vast flat basin with sandstone desert mountains;

 - Volcano is a separate tall cone with lava tributaries and lava pools

 - Blizzard / white windstorm lives on the behind face of the snow

 Appendix E Design history: judges that failed 

 The judge in Section 4 was not designed up front. Each of its checks
replaced a simpler judge that was built first, run on real worlds, and found to
fail in a specific, measurable way. Table 11 lists them. Two
patterns repeat. Judges that match the source text (keywords, patterns) reward what
a program names , so they are easy to game and brittle under harmless
rewrites. Judges that trust a model’s answer (a quote, a sighting, an “it changed”)
accept fluent claims that are not true. Every replacement therefore anchors the
claim to something the model under test cannot fake: the source text itself, or
measured pixels.

 Settings. 

 Frames are sent to the vision judge at 896 px wide and to the
navigator at 640 px. The navigator has 8 actions per biome; the evidence agent has
10 tool calls per search. Output is capped at 16,384 tokens per call, and each
request times out after 300 s. 

 Shared family with a model under test. 

 All six judge roles are Gemini or Gemma
models, the same developer as one of the five models under test,
 gemini-3-1-pro . Judges are known to favour outputs from their own family [ 9 ] .
The one comparison we have does not show favouritism: gemini-3-1-pro ranks
last overall (149.00 of 280) and last on WC003 and WC004, the tests that rely most on
the vision and code-probe judges. That is a single model, and a low score does not
rule out a smaller bias. We did not run a cross-family judge to measure the effect
directly.
