## 1 论证漏洞

### 1.1 核心论点：旗舰表的五行里，只有一行站得住

`draft_overview.md` §1 用一张五行表支撑「模型结构不是瓶颈，证据是一旦判定变得确定，开源就追上来了」。逐行审计：

| 行 | 表里的说法 | 审计结论 |
|---|---|---|
| Design2Code 94.8 对 93.4 | 前沿 GLM-5V-Turbo，开源 Qwen3-VL-235B | 【硬错】**厂商归类自相矛盾**：GLM-5V-Turbo 在这一行算「前沿」，下一行 GLM-5.2 算「开源」。同一家被两种归类，差距大小就是归类决定的。另外两个分数都在 93 以上，是**天花板饱和**，差 1.4 点无信息量 |
| MTAC-IFBench 78.6 对 80.4 | 开源反超 1.8 点 | **这一行站得住**。分数在中段，checklist 逐条脚本验，归类无歧义。全表唯一有效的证据 |
| SWE-bench Verified 76.8 对 75.8 | 同 harness 差 1.0 点 | 【证据不足】76.8 已接近该榜饱和区，且这是**最成熟的公开榜**，开源模型针对它优化了两年。差距小可以由「被针对优化」解释，不需要「判定确定」来解释 |
| RealUIReq-300，GPT-5.1 0.13 对 Qwen2.5-Coder-7B 加 GRPO 0.05 | 开源反超（已标注「要打折扣」） | 【硬错】折扣的理由没写出来，而它是致命的：这个 7B 模型**就是用 axe-core 当 reward 训的**，评测主指标 IR_Axe 又是 axe-core。这是 reward 与评测指标同一个量，不是「开源追平前沿」。`draft_domains.md` §7 自己点出了这一点（「避免 reward 和评测主指标是同一个量」），`draft_overview.md` 没有 |
| SimuScene，最强闭源 21.5% Avg@8 对 32B 经 RL 72.2% Pass@8 | 开源反超 | 【硬错】**Avg@8 与 Pass@8 不是同一个量**，且恒有 Pass@8 ≥ Avg@8。拿 Pass@8 去比 Avg@8 是无效比较，这一行必须删掉或换成同口径数字 |

**结论**：五行里两行是口径错误、一行是归类矛盾加天花板饱和、一行可由替代解释覆盖，只剩 MTAC-IFBench 一行。
用一行证据支撑「模型结构不是瓶颈」这个全篇出发点，**证据强度与措辞强度相差一个量级**。

**可执行的改法**
```
1. 删掉 SimuScene 行与 RealUIReq 行，或换成同口径、reward 与评测分离的数字
2. GLM 系列统一归类（建议按权重是否公开，而不是按「感觉像不像前沿」），并在表头注明归类规则
3. 给每一行补上项目自己定的报分五要素：题数、采样数、harness 版本、judge 型号、带不带工具
4. 把结论措辞降级为：「在中段难度、判定确定、且 reward 与评测分离的任务上，目前只找到一例开源反超（MTAC-IFBench）；
   这不足以支持结构不是瓶颈，只能支持结构不是唯一瓶颈」
```

### 1.2 致命反例：两个确定性 three.js 评测给出相反结论

这是本次审查最重要的一条。**项目自己核实过的材料里就有反驳核心论点的证据，而旗舰表把它排除了。**

| 评测 | 判据性质 | 前沿最好 | 开源最好 | 差距 |
|---|---|---|---|---|
| 3JSBench（`91_3jsbench_verified.md`，2026-10-15 实地核实） | 695 条确定性几何检查，**完全不含 LLM 打分** | Astra 80.0% | Kimi K3 23.0% | **57.0 个百分点** |
| WorldCoder-Bench（2606.01869 表 1，本次重新核对原文） | StateProbe 隐藏运行时契约，确定性断言 | GPT-5.4 V-Cov 27.8% | Qwen3.6-Plus 25.3% | **2.5 个百分点** |

两个评测都是 three.js、都是确定性判定、都不用 LLM 打分，差距相差 23 倍。
**所以「判定确定」不能预测「开源追平」。** 真正的解释变量是**天花板与地板效应**：

```
WorldCoder-Bench：原文明说「no system exceeds 30% on the hidden contracts」，前四名挤在 23.0~27.8%
  -> 所有模型都贴在地板上，差距被压缩
3JSBench：Astra 80.0%，有充分的动态范围
  -> 差距张开到 57 点
Design2Code：93~95 分，所有模型贴在天花板上
  -> 差距被压缩到 1.4 点
```

旗舰表选中的全是地板区或天花板区的任务，**而项目真正要做的 three.js 复刻正好落在中段**——那是差距最大的区间。

**更严重的是这件事是可证的选择性采样**：`07_capability_spec.md` 第 121 行原文写着「**三个集给出三种结论**：3JSBench 差距巨大（80 对 23），WorldCoder-Bench 差距很小（27.8 对 25.3），BenchCAD 国内零报分」。
调研阶段已经知道结论不一致，成稿阶段只保留了支持结论的那一侧。

**可执行的改法**
```
把 §1 的论证从「判定确定 -> 开源追平」改成两段：
  第一段（保留，证据充分）：判定方式决定能不能分开模型 —— 3JSBench 的 31 点对 SigLIP 的 0.002 是干净证据
  第二段（新写）：判定确定不等于差距小。同为确定性判定的 3JSBench 差 57 点、WorldCoder-Bench 差 2.5 点，
                 差异由动态范围解释，不由判定方式解释。因此「先把判定做出来」的理由不是「结构不是瓶颈」，
                 而是「没有判定就既测不出差距也训不动」—— 这个较弱的理由完全够用，而且它是对的
```
降级后的论点其实**更有力**，因为它不需要赌「结构不是瓶颈」这个赌不赢的判断。

### 1.3 自我验证反转结论：归因序由四个不可比的量拼成

`draft_overview.md` 第 92 行：「修正后的归因序是：单步质量 ≳ 长程持久性与时间预算校准 > 判别力 > 多轮执行反馈循环本身」，支撑是四个数字。

| 位次 | 支撑数字 | 它的单位 | 问题 |
|---|---|---|---|
| 单步质量 | Astra 的 8.6 倍 no-CoT 时间跨度（30.9 分钟对 3.6 分钟） | **时间跨度的倍数** | 这是代际差距，不是「单步质量」这一维的差距；而且禁用 CoT 的跨度与单步质量不是同一个构念 |
| 长程持久性 | AutoLab 0.68 对 0.46 | **Avg@3 分数差** | 口径可用 |
| 判别力 | ProcessBench 减 16.4、RewardBench 2 只减 0.5 | **两个榜的分数差** | 同一维上两个榜差 33 倍，说明这一维的差距高度依赖测法，不能用来排序 |
| 多轮循环 | 同 harness 差 1.0 点 | **pass 率百分点** | 口径可用，但它测的是「短程多轮」，不是「多轮执行反馈循环」整体 |

【硬错】**把倍数、分数差、百分点差混在一个序里排名，数学上没有定义。** 8.6 倍和 1.0 点之间不存在「大于」关系。
【证据不足】四个位次来自四个不同 benchmark、不同 harness、不同采样数，没有任何一对是同一把尺子量出来的。

**另一处具体算错**：第 71~76 行的负相关表。

| 表里写的 | 实际 | 差异 |
|---|---|---|
| 3DHarnessBench Qwen 3.8 Max：单步基线 0.740，开循环后 0.809，增益「加 5.3%」 | 0.809/0.740 = **加 9.3%**。5.3% 是 0.768→0.809（第二档到第三档）算出来的 | 【硬错】基线列用第一档，增益列用第二档 |
| 3DHarnessBench Claude Opus 5：单步基线 0.725，开循环后 0.871，增益「加 16.4%」 | 0.871/0.725 = **加 20.1%**。16.4% 是 0.748→0.871 算出来的 | 【硬错】同上 |

查 `07_capability_spec.md` 第 196~197 行，原始四档数据是 Qwen 0.740 / 0.768 / 0.809 / 0.857、Opus 0.725 / 0.748 / 0.871 / 0.927，5.3% 与 16.4% 都是**第二档到第三档**的相对增益。成稿把第一档当基线、却沿用了第二档起算的增益。

修正后结论**不翻**（9.3% 对 20.1%，负相关方向仍在），但对比倍数从 3.1 倍缩到 2.2 倍。
【措辞过头】而且这张表只有 4 个点、每个 benchmark 内部只有 2 个点，同时还有「闭式解释」（有上界时倍数增益必然随基线升高而缩小）。
既然承认有闭式解释，这就不是经验发现，而是**恒等式的观测结果**；拿它当「反转证据」是把数学必然性当成了实证支持。混淆相关与因果的典型形态。

**还有一处自我拆台**：`draft_overview.md` §4 用 3DHarnessBench 的观察接口消融（MiniMax 0.3722→0.6148、Gemini 0.6776→0.7605）作为**把自我验证拆成三维的理由**。而 `07_capability_spec.md` 第 769 行自己写着「**3DHarnessBench 表 3 只有 10 个实例。按 §4.3 的公式，M=10、n=1 的 MDE 远大于表里的差值**」。
复算：M=10、n=1 时 MDE = 62.6 个百分点，观测到的 MiniMax 差值 24.3 点、Gemini 差值 8.3 点，**两个都远在噪声内**。
【硬错】用一组自己判定为不可读的数据，去支撑一个会改变整个能力分类体系的决定。

### 1.4 47/47 与 18/18：数字没错，但三处措辞超出范围

先说清楚：**这两个数字本身是诚实的**，而且 `draft_verifier.md` §8、`draft_overview.md` §7 都主动披露了折扣（阈值在前 29 个上看过、单人标注、单处改动）。披露质量高于业内平均。问题在它们被怎么用。

### 1.5 自洽性违规：方案自己定的纪律，方案自己没遵守

这是最容易修、也最伤信誉的一类。

| 纪律原文 | 违反处 | 具体 |
|---|---|---|
| `draft_overview.md` §6「任何维度报分，必须同时报题数、采样数、harness 版本、judge 型号、带不带工具，**缺一项就不要进报告**」 | 同一篇的 §1 旗舰表、§3 反转证据表、§4 差距排序表 | 三张表共 15 行，**没有一行**报齐五要素。多数行只有一个分数 |
| `draft_overview.md` §6「单维度 15 题乘 8 次采样，最小可检测效应是 18 个百分点」 | §3 负相关表、§4 的 3DHarnessBench 消融、§1 旗舰表的 1.4 点与 1.0 点 | 1.4 点与 1.0 点远小于任何一行的 MDE；3DHarnessBench 消融 M=10 时 MDE 62.6 点 |
| `draft_tasks.md` §8「任何阶段都不许用正在调阈值的那个集合做验收」 | `draft_verifier.md` §4 的 L3 拓扑信号、`draft_domains.md` §7 的 Web 22/22 第二遍 | 见 §1.4 |

【缺口】MDE 公式本身还有一个未披露的乐观假设。原文 `MDE = 1.98/sqrt(M·n)` 等价于假设**两个模型的逐题难度差在题间方差为零**（即把 n 次采样当成 n 个独立题）。复算确认 1.98 这个系数算法无误（2.80 × sqrt(2 × 0.25)），但真实情况下

```
Var(配对均值差) = Var_题间(每题的模型差) / M  +  2·p(1-p) / (M·n)
```

公式只保留了第二项。所以表里的 18.1 点是 **MDE 的下界**，真实 MDE 更大。
修法很便宜：在现有 47 个任务上先跑两个模型各 8 次，直接估出 `Var_题间`，再把整张表乘上膨胀系数。这件事几十分钟能做完，而整个 430 题预算都建在这张表上。

### F1 Verifier 的假阳性在十万量级上表现为数据缺失，不是噪声

**机制（这是本次审查发现的最危险的一条，成稿完全没有）**

准入测试的第一条是「参考解必须过 Verifier」。于是：

```
如果 Verifier 对某一类几何有系统性盲区（例如开面曲面的体素填充无效）
  -> 这一类的【参考解自己】就过不了准入
  -> 整个这一类任务被静默丢弃，一条都不进数据集
  -> 数据集的指标全都很漂亮（因为留下来的都是 Verifier 看得准的）
  -> 缺失不以噪声的形式出现，而以【某个几何类别从分布里消失】的形式出现
```

假阳性比假阴性危险得多，而且 `draft_domains.md` §3 已经证明假阳性是主要形态：图表线的三个 bug **全部制造假阳性**，而且「三个都不是阈值问题，调阈值一个也修不掉」。三个 bug 的真因是坐标系（2 个）和帧（1 个）——都是会**整类**失效而不是随机失效的那种 bug。

已知的三类盲区都已经有实证，而且都有明确的几何特征：

| 已实测的盲区 | 出处 | 会被静默丢掉的任务类别 |
|---|---|---|
| 开面曲面的体素填充无效（射线奇偶判内外） | `draft_verifier.md` §4 的 `ok_lathe`；`90_local_experiments.md` §3.4 | 一切用 LatheGeometry、ExtrudeGeometry、开壳、单面片建模的场景 |
| 文本记录跨帧累加 | `draft_domains.md` §3 | 一切带动画的图表与页面 |
| 坐标系没过变换矩阵 | `draft_domains.md` §3 | 一切含旋转、含嵌套层级的场景 |
| 48 立方体素下薄部件量化成单层 | `draft_verifier.md` §7（自述「参考解自己的最大值就是 1.0」） | 一切薄壳、薄板、细杆为主的场景 |

把这四条叠起来：**带动画 + 含旋转 + 薄壳 + 开面** 的场景几乎会被成批排除。而这正是真实前端与 three.js 作品的主流形态。

**触发条件**：任务生成进入 S1 模板化阶段（2,000 个任务）之后，模板槽位里一旦出现开面几何或动画。

**早期征兆**
- 准入拒绝率按场景特征分层后呈显著非均匀（而不是均匀地 6%~12%）
- 某个模板的拒绝率远高于其他模板，但人工看被拒的 case 觉得「这破坏明明是对的」
- 被拒 case 的失败层高度集中在同一层（例如全是 L2 体素）

**最便宜实验**（2 小时，复用现有脚本）
```
1. 对现有 47 个任务 + 被弃的那几个 case，按六个二元特征打标：
   含开面几何 / 含动画 / 含旋转层级 / 含薄壳(最薄维度 < 场景尺度的 2%) / 含透明材质 / 含贴图
2. 统计每个特征下的「参考解自比自通过率」和「准入拒绝率」
3. 对每个特征做 Fisher 精确检验；任何一个 p < 0.1 就是一条系统性盲区
4. 验收口径：盲区清单必须成为造题阶段的【禁止槽位表】，与 draft_tasks §7 的「可见性审计」合并
```
这个实验的价值在于它把「Verifier 体检」从**逐 case 人看**升级成**按特征分层的统计量**，而后者是唯一能在十万量级上跑的形式。

### F2 准入测试把训练集偏向「Verifier 已经擅长的那类错误」

**机制**

准入的第二条是「破坏版必须被判挂」。这条规则的字面含义就是：**只收 Verifier 当前看得见的破坏**。于是训练集的错误分布 = Verifier 当前能力的像，而不是真实错误分布的像。

项目自己的数据直接显示了这个偏斜。`draft_tasks.md` §4 收下的 16 个任务按失败层分布是 **L1 六个 / L2 八个 / L3 两个**：

```
L3 只占 2/16 = 12.5%
而 L3 里真正救场的那个信号（开放边界边数）对应的任务数 = 0
```

也就是说：**那个一次救回四层同时失明的信号，在收下来的 16 个任务里一道都没考到。** 更糟的是，催生它的那个 case（`ok_lathe`）在准入流程里的身份是「我们标错了标签的正确改写」——它本来会被当成正样本收进去。

后果链条很具体：

```
训练集只含 Verifier 看得见的错误
  -> policy 在 RL 里学会修这些错误
  -> 评测用同一个 Verifier，分数一路涨
  -> 真实用户看到的产物里，Verifier 看不见的那一类缺陷一点没少
  -> 「reward 涨而 holdout 不涨」这个告警也抓不到它，因为 holdout 用的是同一个 Verifier
```

最后一句是关键：`draft_training.md` §6 的七条告警里，「proxy 与 held-out 的散度」依赖 held-out 判据与训练判据不同源。而本方案的 held-out 判据与训练判据**是同一套分层 Verifier**，只是换了题。**这条告警在本方案里是失效的。**

**触发条件**：S3 RL 开始之后立即生效，无需任何额外条件。

**早期征兆**
- 收下任务的失败层分布持续偏向浅层（L1、L2 占九成以上）
- 每次给 Verifier 加一层新信号，新层对应的任务数接近零
- 人工抽检中「Verifier 判通过而人判不通过」的比例不随训练下降

**最便宜实验**（2 小时）
```
留一层消融（leave-one-layer-out）：
1. 关掉 L3，用剩下三层重跑现有 16 个任务的准入
   -> 数出「只有 L3 能抓到」的任务数 k1
2. 关掉 L2 同理得 k2；关掉 L1 得 k3
3. 指标：每一层的【专属任务占比】k_i / N。任何一层的专属占比 < 5%，
   说明这一层在数据生产里是哑的 —— 它保护的那类错误根本没进数据集
4. 对策（必须进造题流程）：造题阶段按目标层配额出题，
   例如强制 L3 专属任务不低于 20%；出不来就说明破坏提案器的提案分布太窄，
   要改提案 prompt 而不是改 Verifier
```
**另外一条必须加的制度**：held-out 评测集的判据必须与训练判据**不同源**。最便宜的做法是把 VLM judge 的投票结果当 held-out 判据之一（它的盲区与程序化信号互补，这一点项目自己已经证明了），而不是只换题不换判据。

### F3 通过全部断言但很丑：reward 与用户偏好正交

**机制**

`draft_training.md` §3 的聚合结构明确把「美学分、全局 CLIP 与 DINO 相似度、任何与 token 数相关的项」**一律不进 reward**。这个决定在防 hack 上是对的（有 RULER 的实测背书），但它的直接推论是：**reward 对产物的观感零敏感**。

3JSBench 的失败统计给出了这个盲区的量级（`91_3jsbench_verified.md` §4）：3,000 次尝试里最常见的五类失败是物体互相穿插 20%、可见背面 19%、表面闪烁 17%、朝向不符 16%、部件断开 16%。
**前三类（合计 56% 的尝试）全是渲染层面的物理不自洽**，而 `draft_verifier.md` §7 自述「本项目的判据里只覆盖了可见背面一项」——后来补了穿插与绘制顺序两个，但**按部件两两算穿插在 48 立方体素下不可用，只能当诊断量**。

更直接的风险是 RL 会朝着**满足断言的最小场景**收敛。3JSBench 的网格预算数据正好给出了这个方向的两端：Astra 中位 45 个网格、Fable 24 个，而 Muse Spark 995 个。断言只查「有几个部件、接在哪、挨着谁」，**一个 24 个网格的极简场景完全可以全过**，而人看会觉得空。

**触发条件**：S3 RL 跑过约 100 步，policy 开始利用「断言不查什么」。

**早期征兆**
- 代理指标里「场景图对象数与三角面数」的中位数**单调下降**（`draft_training.md` §6 已经列了这个代理指标，但没说方向：下降同样危险）
- 几何相似分（权重压在 0.3 以内的那个分项）持续下降而总 reward 上升
- 人工抽检中出现「全过但一眼看就是占位符」的产物

**最便宜实验**（1 天，不需要训练，这是全清单里信息量最高的一个）
```
对现有 Verifier 做 best-of-N 攻击，直接量出「Verifier 最优解」有多丑：
1. 取 18 个留出车辆任务，用一个强模型每题采 64 次，不给任何反馈
2. 按当前 Verifier 打分，取每题得分最高的 3 个产物
3. 把这 54 个产物与参考解混在一起，让 3 个人盲排序（或用 4 模型 pairwise 投票做粗筛）
4. 指标：Verifier 最高分产物对参考解的人工胜率
   - 胜率 >= 40%：reward 与偏好基本对齐，可以放心上 RL
   - 胜率 20%~40%：需要在闸后补一个弱美学分项（权重 <= 0.1，且必须门控在硬闸之后）
   - 胜率 < 20%：reward 与偏好正交，RL 会把模型训丑，必须先补判据
5. 同时记录这 54 个产物的网格数、三角面数、穿插比例分布,
   与参考解比对 —— 这直接给出「最小化到什么程度还能全过」的实测边界
```
这个实验的好处是**不花训练算力就能预测训练结果**，而且它产出的 54 个产物直接就是下一轮变异集的素材。

### F4 任务分布与真实需求分布不匹配

**机制**

全部任务都是「修复单处破坏」：`draft_tasks.md` §4 的生成器是「在一个能跑的页面上提出若干语义性破坏」，`90_local_experiments.md` 的 47 个变异全是单处改动。
而真实需求（以及项目自己选的主要对标评测 3JSBench）是**从零构建、一次成型**。

两件事的差别不是难度，是**所需能力的构成**：

| | 修单处破坏 | 从零构建 |
|---|---|---|
| 定位 | 给了初态，差异可枚举 | 无初态 |
| 规划 | 几乎不需要 | 全部工作量 |
| 空间推理 | 局部 | 全局 |
| 失败模式 | 改错一处 | 整体结构错 |

`draft_tasks.md` §3.1 自己把变异扰动范式的最大短板写成「**变异分布偏离真实错误**」，`draft_training.md` §4 又引了 ReTerm 的「手工注错与 agent 自身的执行错误分布不匹配」。两处都识别了问题，但**任务生产线仍然 100% 是变异式的**，而且没有任何实验验证迁移性。

**触发条件**：训练完成、第一次在 3JSBench 或任何从零构建的评测上报分。

**早期征兆**
- 修复类 held-out 分数涨，而一次成型的分数不动
- 轨迹长度分布在从零构建任务上异常（卡在开头）
- 同一规格下，模型在「修破坏」上的通过率与在「从零建」上的通过率逐题相关系数低

**最便宜实验**（半天）
```
1. 取 18 个留出车辆变异。每个变异背后都有一句用户视角的需求描述
2. 构造配对任务：
   A 版 = 给破坏后的页面 + 需求，要求修复（现有形态）
   B 版 = 只给需求（加参考多视角图），要求从零写出同一个场景
3. 同一个模型各采 8 次，算每题通过率，再算 A 与 B 的 Spearman 相关
4. 判读：
   - rho >= 0.6：修复类任务可以当从零构建的训练代理，现有生产线不用改
   - rho < 0.4：两者几乎无关，必须在任务池里加入从零构建档，
     且比例不低于最终评测中从零构建任务的比例
5. 顺带产出：B 版的通过率就是「从零构建」这一族的难度基线，
   它是 §2.5 零梯度估计的直接输入
```
这个实验还有一个附加价值：B 版任务的构造几乎零成本（需求描述和参考图都已经有了），**如果 rho 高，等于免费把任务池翻倍**。

### F5 零梯度组与 rollout 放大

**机制**

`draft_training.md` §2 的零梯度估计算错了（见 §1.6 第 4 条）：组大小 8、通过率 0.1 时全零组概率是 **43.1%** 而不是 19%，通过率 0.05 时是 **66.3%**。
真实情况比方案假设的差一倍以上。而 DAPO 的动态采样是**重采到非退化为止**，所以代价不是「浪费了那些组」，而是**rollout 数量放大**：

```
有效组比例 = 1 - P(全零) - P(全对)
通过率 0.05、组 8：有效比例 33.7%  -> rollout 放大 2.97 倍
通过率 0.10、组 8：有效比例 56.9%  -> rollout 放大 1.76 倍
通过率 0.25、组 8：有效比例 89.9%  -> rollout 放大 1.11 倍
```

而 `draft_training.md` §7 的 12,800 GPU 小时与 204,800 条轨迹的估算用的是 `400 步 × 64 prompt × 组 8`，**没有乘动态采样的放大系数**。按初期通过率 5%~10% 算，真实轨迹数是 36 万到 61 万条，GPU 小时 2.3 万到 3.8 万——**超过它自己引作参照的 Qwen3-8B 纯 RL 的 17,920 小时**。这反过来削弱了 §1「RL 不如蒸馏」那个判断的成本前提：实际差距比表上更大，不是更小。

公开实测还印证了方案的难度带留存更乐观：`draft_tasks.md` §8 自己引了 Skywork-OR1 开训前 54%~63% 零梯度、GRESO 训练中有效 prompt 掉到约 20%，并写明「如果实际留存是 0.30，候选数从 26.9 万翻到 53.8 万」。**同一个悲观情形没有回写进 §7 的 GPU 预算。**

**触发条件**：S3 第一步。

**早期征兆**：全零组占比 > 40%、动态采样的重采轮数中位数 > 2、每优化步墙钟超预期一倍。

**最便宜实验**（1 小时，`draft_tasks.md` §8 已经提过，这里只是把它提前并扩一句）
```
在现有 47 个任务上跑 pass@8（376 次调用，几十分钟）：
1. 直接得到通过率分布，算出全零组与全对组的占比
2. 把占比代回 §7 的成本表，重算轨迹数与 GPU 小时
3. 同时得到「难度带留存」这个最敏感外推项的实测值，替掉 0.60 那个猜测
4. 如果有效组比例 < 40%，S3 之前必须先做一件事：
   用 S2 拒绝采样的结果把任务池按 pass@8 重排，只留 1/8 到 7/8 的那些
```

### F6 Verifier 信息量超过题面，而准入测试结构上查不到

**机制（第二危险的一条）**

方案把这个问题识别得很清楚：`draft_tasks.md` §5、`draft_verifier.md` §3 都写了「Verifier 能查的信息量必须小于等于 Problem Statement 给出的信息量」，并且给了三个实证（杯子颜色、桌腿位置、日光功率）。
**但准入测试的三条闸没有一条能查它**：

```
闸 1 参考解必须过 Verifier       -> 参考解当然过，它就是答案
闸 2 破坏版必须被判挂            -> 破坏版当然挂
闸 3 search 片段在源码中唯一     -> 与信息量无关
```

三条闸全过的任务**仍然可以是不可解的**。实测频率不低：桌子那批 9 个任务里 2 个（22%），Blender 留出集 7 个里 1 个（14%）——`draft_tasks.md` §7 自己记了这件事。按 22% 算，十万任务里有**两万多道不可解题**持续向 RL 注入噪声，而且

```
单看通过率会把它们判成「超难题」留在池里（draft_tasks §7 自己写的）
-> 难度带筛选不但不会剔掉它们，反而会【优先保留】它们
   （因为它们的通过率稳定在 0 附近，正好落在「有挑战性」那一侧）
```

这是一个**正反馈**：越是不可解的题，越容易被难度筛选留下来。

**触发条件**：S1 模板化之后，题面由模板自动生成（人不再逐条读题面）的那一刻。

**早期征兆**
- 通过率恒为 0 的任务占比 > 10% 且不随 policy 变强而下降
- `draft_tasks.md` §7 提到的 item-total 相关为负或接近零的题集中在特定模板
- 人工仲裁「欠规格」的时间占抽检总时间的比例持续上升

**最便宜实验**（3 小时，可以做成常驻闸）
```
加第四条准入闸：【题面可解性闸】
1. 让一个与 Verifier 作者无关的模型，只看 Problem Statement（含参考图，如果有），
   枚举「你认为验收会检查哪些点」，输出结构化清单
2. 与真实断言集做匹配，算召回 R = 被猜到的断言数 / 断言总数
3. 阈值建议：R < 0.8 的任务直接退回，并把未被猜到的那几条断言
   要么删掉、要么把信息补进题面
4. 先在现有 47 个任务上跑一遍校准 —— 已知的 3 道不可解题应该被这条闸抓出来，
   抓不出来就说明闸的实现有问题（这 3 道题是现成的金标准）
5. 成本：每任务 1 次调用。对十万任务是 10 万次调用，
   相对 §8 已规划的 95 万次是 10% 增量,换掉两万道噪声题,显然值
```
**这条闸应该是本次审查里最该立刻落地的一件事**：它有现成的金标准（3 道已知不可解题）、成本只有现有 LLM 预算的 10%、而它堵的是方案自己判定为「纯噪声」的那一类任务。

### F7 十万量级下的不确定性残留

**机制**

`draft_domains.md` §6 自述两个硬漏点：Web Worker 里的时钟拦截不住（一套公开评测为此排除了 225 个游戏，是它最大的一类技术性排除）、超越函数跨引擎版本会分叉。`draft_verifier.md` §6 又说「只冻结时钟不够……20 次里仍有 2 种」，只有「接管帧调度与随机源」才能逐字节一致。

而 flaky 门槛是 ≤ 1%（`draft_tasks.md` §6）。在十万任务上：

```
1% × 100,000 = 1,000 道永久带噪的任务
而 draft_domains §6 要求的对策是「同一份代码双跑，产物不一致就不进数据集」
-> 取证成本翻倍，且这一项没有写进 §8 的成本模型
   （§8 的探针调用 159 万次是单跑口径）
```

**触发条件**：S2 多样性扩张引入动画、物理、随机数的模板时。

**早期征兆**：flaky 率按模板分层后出现长尾模板；双跑不一致的 case 集中在含物理或含 Worker 的那些。

**最便宜实验**（1 小时）
```
1. 现有 47 个任务每个双跑（或三跑），逐字节比对全部探针产物
2. 分层：静态场景 / 含动画 / 含随机数 / 含物理
3. 得到 flaky 基线与分层分布；把双跑成本乘进 §8 的成本模型
4. 如果静态层 flaky 已经 > 0.5%，说明「接管帧调度与随机源」这件事还没做干净,
   在扩产前必须先补 —— 十万量级上没有第二次机会
```

### F8 48 立方体素与拓扑信号对薄壳、开面、透明体系统性失明

**机制**

L2 的主干是 48 立方体素占据，而 `draft_verifier.md` §7 自己证明了这个分辨率的上限：「按部件两两算穿插比例，在 48 的体素分辨率下不可用：薄部件会被量化成单层，看起来像被另一个部件完全包含，**参考解自己的最大值就是 1.0**」。
同一个分辨率同时承担 L2 的占据判定。所以：

```
薄部件在 48 立方下 -> 量化成单层 -> 占据 IoU 对它的位移、厚度、朝向都不敏感
而 L3 的连通块与开放边界边数是为了补这个 -> 但开放边界边数对【合法的开面几何】会误杀
```

第二半是未测的风险。现有三个 three.js 场景的参考解**全是闭合实体**（球、圆柱、立方体、小车），所以「开放边界边数明显多于参考」这条判据从来没在「参考解本身就是开面」的场景上试过。而真实 three.js 作品里 `PlaneGeometry`、`Sprite`、`ExtrudeGeometry`、单面片、`InstancedMesh` 极其常见。

**触发条件**：任务池引入以平面、精灵、挤出几何为主的场景（也就是绝大多数真实前端 3D 作品）。

**早期征兆**：L3 的触发率按几何类型分层后严重不均；被 L3 判挂的 case 里人工复核「其实是对的」的比例超过 10%。

**最便宜实验**（半天）
```
1. 用 10 种不同实现路径写出【世界几何等价】的同一辆小车：
   平面拼接 / 挤出 / 精灵 / 实例化 / Lathe / CSG / 顶点着色 / 薄壳 / 混合 / 原版
2. 全部跑现有四层 Verifier，统计误杀率（这些全都该放行）
3. 判读：误杀率 > 10% 说明 L3 绑死了实现路径 ——
   这正是 draft_verifier §2 自己批评朴素断言的那个毛病（「查的是实现路径而不是结果」）
4. 修法方向（不是调阈值）：开放边界边数改成【相对参考的同类几何归一化】,
   或者只在参考解本身闭合时启用这一条
5. 同时把体素分辨率从 48 提到 96 跑一遍，量「薄部件灵敏度」的改善与成本倍数
   （体素成本按立方增长，48->96 是 8 倍，要先知道值不值）
```

## 3 被忽略或被低估的替代方案

> 本节按**改后的成稿**评估。§1、§2 指出的问题已经修掉，所以这里不再重复，只问一件事：
> **有没有更便宜或更可能成功的路线被这套方案跳过了。**
> 每条给支持证据、反对证据，以及一个可判定的「什么条件下它比当前方案更优」。

### 3.0 总览

| 替代方案 | 成稿现在的处理 | 审查判断 | 优先级 |
|---|---|---|---|
| A 全盘蒸馏（不做 RL） | 蒸馏只当前端族的路线与 S1 冷启动 | **路由搞反了**：教师最强的那一族被排除在蒸馏之外 | 高 |
| B 纯 SFT 加大数据量 | S1 规划 8K 到 15K 条 | **最大的未开采杠杆**，成稿自引的饱和点是 48K | **最高** |
| C 人类偏好数据与专用 RM | 阶段二刻意排除审美 | 推迟的理由可被同一份证据反驳 | 中 |
| D 预算全投评测与 harness | 阶段一已经是 3 个月测量 | 方向已采纳，但**缺一个决策闸** | 高 |
| E 只做一个窄领域 | `draft_domains.md` §7 收敛到 Web 优先 | 与 `draft_overview.md` §4 的 14 维 430 题规划仍冲突 | 中 |

### A 全盘蒸馏：只蒸馏，不做 RL

**支持证据**

| 证据 | 数字 | 为什么重要 |
|---|---|---|
| 教师在目标域上近乎饱和 | Astra 在 3JSBench 上 **pass@3 解出 96/100** 道题（`91_3jsbench_verified.md`） | 一个 96% 可解的教师，蒸馏的天花板极高。而成稿 `draft_training.md` §1 把 three.js 复刻的教师能力写成「部分能」 |
| SFT 的绝对增益远大于 RL | SWE-Master 0 到 60K 条轨迹，解决率 **6.2% 到 57.8%**（+51.6 点） | 对照成稿期待的 RL 增益：ReLook 25.84 到 27.88（+2.04）、CATCH pass@1 26.00 到 30.00（+4.00）。**差一个量级** |
| 拒绝采样本身就是带质量闸的蒸馏 | 成稿的 S2 就是这件事 | 也就是说方案已经做了蒸馏的全部基础设施，只是把它定位成「RL 的前置」而不是「候选终点」 |
| RL 不扩展能力边界 | Qwen3 实测 RL **完全没有抬高 pass@64**，而蒸馏把 AIME24 pass@64 从 90.0 抬到 93.3（2505.09388 表 21，已核原文） | RL 的作用是把 pass@k 的质量压到 pass@1，蒸馏同样做这件事，而且顺带抬了上界 |

**反对证据（三条，都是硬约束）**

1. **Qwen3 的十倍效率依赖教师 logits，本项目的候选教师拿不到。** 原文第 2777 行明写「distillation from **teacher logits** enables the student model to expand its exploration space」。Astra、Opus 5.5 都是 API-only，只能做序列级（off-policy）蒸馏——这是另一种方法，没有那个十倍结论。
   原文第 2776 行还写明实验设置：两条路线**都从同一个已经 off-policy 蒸馏过的 8B checkpoint 出发**，且**只用数学与代码 query**。学生已在教师分布里、教师同族、任务是文本数学——对蒸馏最有利的条件同时成立。
   【这一条意味着成稿 §1 引这组数字时必须补限定词，否则读者会以为十倍效率可以照搬。】
2. **天花板就是教师。** 3JSBench 上 Astra 还有 20% 的尝试不过，96/100 是 pass@3 而不是 pass@1。要超过教师，只有 RL 或自对弈。
3. **合规风险**：大规模蒸馏竞品 API 输出，条款与审计都要先过。成稿完全没提这件事。

**什么条件下它比当前方案更优**

```
设 T = 教师在目标任务族上过 Verifier 的 pass@8 率
   S = 蒸馏后学生的 pass@1 率
   R = RL 相对蒸馏后学生的实测增益（百分点）

全盘蒸馏更优，当且仅当三条同时成立：
  (1) T >= 0.80         教师够强,蒸馏天花板不构成约束
  (2) S / T >= 0.85     学生吃得下教师,序列级蒸馏没有严重损耗
  (3) R <= 修正后的真实 MDE（见 §4 第 9 条）
      也就是 RL 的增益读不出来 —— 那就不该付那 2.2 万到 3.8 万 GPU 小时

当前能填的只有 T：3JSBench 上 Astra pass@3 = 0.96,pass@8 必然更高,(1) 成立
(2) 与 (3) 都没有数据 —— 而这正是 §5 第一条要补的实验
```

**结论**：全盘蒸馏现在**不能排除，也不能采纳**，因为判据里两项没测。但有一件可以立刻改的事：
**three.js 复刻族的路由方向错了。** 成稿的路由依据是「教师能不能做对」，而按这个依据：

```
three.js 复刻：教师 pass@3 96/100  -> 教师极强  -> 本该优先蒸馏
前端 WebDev：  没有同等强度的教师实测        -> 却被排在蒸馏第一位
```
正确的读法是两个判据独立：**教师强度决定蒸馏值不值；判定确定性决定 RL 可不可行。**
three.js 两者都高，所以顺序是**先蒸馏拿基线，再在蒸馏后的模型上做 RL**——这恰好也是 Qwen3 实验自己的顺序。

---

### B 纯 SFT 加大数据量，不做 RL

**支持证据**

成稿 `draft_training.md` §7 自己引了饱和点，然后把规划停在饱和点之前：

| 项 | 数字 | 占饱和点 |
|---|---|---|
| SWE-Master 实测饱和点 | 48K 条轨迹（60K 时解决率 57.8%，48K 之后趋平） | 100% |
| 成稿 S1 规划 | **8K 到 15K 条** | **17% 到 31%** |

也就是说：方案主动放弃了 SFT 曲线上最陡的那一段，然后用 RL 去追那一段本来可以靠加数据拿到的分。
而扩产成本是已知可算的：教师采样 + Verifier 筛选，取证成本在秒级且纯 CPU（`draft_verifier.md` §6 实测 14 任务每秒）。

**反对证据**

| 反对 | 出处 | 这条反对能挡住多少 |
|---|---|---|
| 纯净轨迹训不出纠错能力（修订能力 10.84 对 46.75） | `draft_training.md` §4 引 Agent-R | **挡不住**。这是「SFT 数据的构成」问题，不是「数据量」问题。加量与加纠错轨迹不冲突，成稿 §4 已经写了怎么构造纠错轨迹 |
| SWE-Master 是文本 SWE，不是视觉 | — | 有效。迁移性未验证，这是真风险 |
| SFT 上界是 Verifier 筛过的教师产物 | — | 有效，但与 A 的第 2 条同源，不是 B 独有的问题 |

**什么条件下它比当前方案更优**

```
做一个三臂分叉实验（成本 = 两次额外 SFT,远低于一轮 RL 的 2.2 万到 3.8 万 GPU 小时）：
  臂 1  15K SFT + RL      （成稿规划）
  臂 2  48K SFT,不做 RL
  臂 3  48K SFT + RL

B 更优的判据：臂 2 >= 臂 1 - 真实 MDE
  即「光加数据不做 RL」已经追平「少数据加 RL」-> RL 这条线整体降级
再看 臂 3 - 臂 2：这才是 RL 的真实边际价值,也是唯一该拿去跟 GPU 账单比的数
```
**这是本节里性价比最高的一个实验**，因为它同时回答 A、B、D 三条的核心未知量（RL 的边际增益 R）。

### C 人类偏好数据与专用 reward model

**支持提前做的证据（全部来自成稿自己引的同一批材料）**

| 证据 | 数字 | 含义 |
|---|---|---|
| 审美是数值上最大的差距 | Design Arena Elo 约差 **69**，Code Arena WebDev 约差 **139** | 比长程持久性（0.68 对 0.46）和长程多文件（约 7 点）在相对量级上都更大，却排在 14 维的第 5 位 |
| 噪声是可以工程掉的 | 同一批标注员**无 rubric 一致率 65.0%，有人写 rubric 后升到 92.0%**；3 人平均后 ICC 到 **0.637** | `draft_overview.md` §6 自己写了结论句「审美的可度量性主要是 rubric 工程问题」 |
| 专用小 RM 的性价比已有实测 | VL-RewardBench 上专训 7B 做到 **73.1**，超过 78B 通用模型的 63.3 与 GPT-4o 的 65.8，代价约 **190k 对**比较数据 | 190k 对是公开实测量级，不是天文数字 |

**反对提前做的证据**

| 反对 | 数字 | 评价 |
|---|---|---|
| 单人标注不可用 | Krippendorff α 只有 **0.368**（51 名设计师、1,395 个 UI） | 有效，但它反对的是「单人标注」，不是「人类偏好数据」 |
| judge 噪声淹没档位差 | judge 标准差 **11.4 ELO**，档位间只差约 40 ELO | 有效，且这正是要训专用 RM 的理由 |
| 审美分最易被 hack | RULER 实测美学分从 4.42 顶到 6.21 而 rubric 分从 0.395 崩到 0.262 | 有效，但成稿 §3 的乘法门控已经解决了这个问题（审美只能在硬闸后进加权） |
| 众包周期长 | 平局率 26%、约 18% 的票是「两个都差」 | 有效，但它反对的是「众包 Elo 当迭代指标」这一种做法 |

**判断**：【证据不足】推迟的措辞覆盖了整个审美维度，而证据只支持推迟「众包 Elo 当短周期迭代指标」。

**什么条件下它比当前方案更优**

```
C 不与当前方案竞争,它竞争的是【阶段二的一个维度名额】。更优条件：
  (1) 3 人 rubric 化标注的 ICC >= 0.60   （公开实测 0.637,大概率成立）
  (2) 在 2,000 对内部标注上训出的小 RM,与 3 人均值的一致率 >= 0.80
  (3) 该 RM 在乘法门控的闸后作为权重 <= 0.1 的分项接入,且 proxy 与 held-out 不背离

最便宜的验证：不要先标 190k 对。先标 300 对（分层：高分/中/边界）,
  量 (1) 与「rubric 前后一致率」两个数。半天到一天,直接决定这一维要不要提前
```
建议把阶段二的「审美」从**排除**改成**保留但换形态**：rubric 化的 3 人内部标注加专训小 RM，不是众包 Elo。

### D 把预算全投在评测与 harness 上，不自己训模型

**支持证据：零训练干预的收益量级，与方案期待的 RL 增益同档或更高**

| 零训练干预 | 效果 | 可信度 |
|---|---|---|
| 换脚手架 | GPT-5.5 在三个脚手架上 69.85 / 67.39 / 58.19，极差 **11.7 点** | 高，样本量大 |
| 换脚手架 | GLM-5.2 在 MTAC-IFBench 上 12.7 掉到 6.7，**腰斩** | 高 |
| 规范化截图前的视口 | MiniMax M3 从 0.3722 到 0.6148（+24.3 点） | **低**。M=10、MDE 62.6 点，在噪声里——成稿 §4 现在已经如实标注了这一点 |
| 现成量尺 | 3JSBench 有 100 题、695 条确定性检查、含两个目标前沿模型的实测分 | 高，已实地核实 |

对照：方案期待的 RL 增益是 2 到 4 点（ReLook +2.04、CATCH +4.00）。
**可信的那两条 harness 证据（11.7 点、腰斩）就已经比期待的 RL 增益大。**

**反对证据**
- harness 增益是一次性的，吃完就没有了；训练增益可以累积。
- harness 增益不进权重，换部署环境就丢。
- 产品上交付的是模型，不是 harness。
- A11yn 是「确定性 reward 加 RL 就能赢闭源」唯一的公开验证，说明训练这条路是通的。成稿 `draft_domains.md` §4 自己把这个数打了折（reward 与评测主指标同源），而本次核原文的结果是**这个折可以打得比成稿更轻**：人工两两比较是 5 名评测员的 1,330 次判定，非平局里 64.7% 偏向 A11yn（z = 8.3），见 §4 第 9 条。也就是说「训练这条路通」的证据比成稿写得更硬——**这一条反对 D、支持当前方案**。

**什么条件下它比当前方案更优**

成稿的阶段一本来就是 3 个月纯测量，所以方向已经采纳了一半。**缺的是一个决策闸**：现在阶段二的触发条件是「阶段一做完」，而它应该是一个数值判据。

```
阶段一出闸前必须填完这张表（三个数都在同一个基座、同一套 430 题上量）：
  a = 纯 harness 与 prompt 工程的增益      （换脚手架、规范视口、固定时钟、多视角）
  b = 蒸馏的增益                            （§3-A 的最便宜验证）

否则阶段二的 2.2 万到 3.8 万 GPU 小时就是在「还有更便宜的点没捡」的情况下烧掉的
```

## 5 如果只能再改三处

> 前一轮的五条建议成稿已经照改。这三条是**改后版本上剩余风险最大的三处**，按「改动成本 ÷ 挽回的风险」排序。

| 优先级 | 改什么 | 改成什么 | 为什么是它 |
|---|---|---|---|
| **1** | `draft_training.md` §1 的任务族路由表 | ①「WorldCoder-Bench 通过率 2.7%」改成「隐藏契约覆盖率 27.8%，前四名 23.0 到 27.8%」（2.7% 是截图加 VLM 这个**判定范式**的通过率，不是模型的）；②据此重判三族路由：three.js 复刻的教师 pass@3 是 96/100，属于「教师极强」，应当**先蒸馏再 RL**，不是「优先上 RL」 | 这是改后版本里**唯一的硬错**，而且它恰好是整张路由表的依据。更糟的是它现在与 `draft_overview.md` §1 刚写对的 27.8% 直接矛盾——同一篇成稿里一个数差十倍，读者会怀疑全部数字。改动量是两个单元格，但它改变的是「先蒸馏还是先 RL」这个最大的投入决策 |
| **2** | 两个基础估算：GPU 预算与 MDE | ①把动态采样的重采放大系数乘进 §7 的成本表：通过率 5% 到 10% 时是 **1.76 到 2.97 倍**，真实是 2.2 万到 3.8 万 GPU 小时，**超过它自己引作参照的 Qwen3 纯 RL**；②在现有 47 任务上两个模型各采 8 次，估出 MDE 公式缺失的 `Var_题间` 项，把 430 题预算表整体上调 | 整个阶段规划建在这两个数上：430 题够不够、1.3 万 GPU 小时够不够。两件事合起来不到半天（pass@8 是 376 次调用），而不改的代价是阶段二开到一半发现预算差两倍、阶段一交付的分数读不出来。**顺带说明：改对之后「先问教师」的判断会变得更强，不是更弱** |
| **3** | 给 held-out 判据加一条「不同源」要求 | `draft_training.md` §6 的 1 号告警「proxy 与 held-out 的散度」要求两者不同源才成立，而本方案的 held-out **与训练判据是同一套分层 Verifier，只换了题**。所以这条告警在当前设计下**结构性失效**：Verifier 的盲区会同时让训练分和 held-out 分一起涨。修法：held-out 判据里必须含至少一路与程序化信号盲区互补的判据（最便宜的是 VLM 投票——项目自己已经证明两者盲区互补），并单独报它的曲线 | `draft_tasks.md` §6 新增的两条盲区里收了「留一层消融」（数据集偏向），但没收这一条。它比数据集偏向更危险：**数据集偏向会被人工抽检发现，而 held-out 同源会让所有自动告警一起失明**。方案的七条告警里最重要的那一条现在是空转的，而修法只是在 held-out 里加一路判据 |

**不建议再改的地方**（避免过度修正）

- Verifier 分层的技术结论（几何指标分部件算、断言只查钉死字段、取证不靠产物自觉、感知相似只作分项、不随尺寸衰减的拓扑量）——three.js、Blender、Web、图表四条线独立成立，是全篇最硬的部分。
- 乘法门控与四类终止原因的处理——有 SWE-Master、L1、OTC、CAD-Coder 四组独立实测背书。
- 新增的 `draft_verifier.md` §9 与 `draft_tasks.md` §6——这两节把「盲区变成数据缺失」和「准入查不到题面可解性」写清楚了，验收指标也落到了「准入拒绝率按场景特征分层必须均匀」这种可执行的形式，不需要再动。
- 对本项目实测局限的披露（Wilson 下界、p=0.125 不显著、第一遍 21/22、L3 红线违反的自曝）——这一轮的披露质量已经高于业内平均，**要改的是正文措辞，不是脚注的坦白**。
