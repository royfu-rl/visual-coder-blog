# 15 网页游戏与交互式产出的「可玩性」怎么自动验证

**分层、乘法门控、判别力用带标签变异集量、留出集验阈值迁移。**

## 0 结论先行

1. **「能玩」能拆开，而且大部分能做成确定性判据。**
   本文列了 **6 族 34 行**子命题（表 1.1），其中 E3 与 C2 是同一条，去重后 **33 条**。按能不能做成程序判据分：
   **24 条全确定性**、6 条需要 agent 真玩、3 条只能靠人。
   也就是说「可玩性只能靠真玩」这个说法是错的 —— 只有大约十分之一真的只能靠人。

2. **真正的瓶颈不是「判得准不准」，是「验得到验不到」。**
   A2Z 在 Phaser 游戏上做脚本 playtest，**第一遍正常玩只能对 40.5% 的规则给出结论**，
   其余是「前置条件没达到，无法判定」。加一遍正常玩只涨到 41.0%，
   换成**把状态直接注入到规则前置条件**的对抗式 playtest 才涨到 48.5%（2609.39564 表 4c）。
   逐 agent 看更夸张：正常玩覆盖 13.1%~29.0%，加状态注入后 53.3%~88.0%（同文 附 F.3）。
   **判据再准，碰不到的规则就是 0 信号。**

3. **只读源码会被骗，而且骗的量级是可测的。**
   A2Z：源码判满分的规则，真玩时**只有 76.8% 成立**；反过来源码判零分的规则里有 25.7% 真玩是对的
   （2609.39564 §4.3，核实见 2.2）。
   同一篇还给了更狠的一条：规则**局部**通过率 72.4%，但要求它的所有上游规则也通过，就只剩 **22.7%**，差 49.7 个百分点（§1、附 B.7）。
   Code2Games 的消融是另一个角度：只给编译与运行诊断，构建成功率从 78.5 涨到 88.7，
   但交互符合度只从 58.0 涨到 59.0；**加了玩法断言反馈才从 59.0 涨到 75.8**（2610.05033 表 3）。
   能跑和能玩是两个几乎正交的量。

4. **像素与录屏判不了可玩性，它判的是「有东西在动」。**
   V-GameGym 把交互代码**改写成 10 秒自动演示**再录屏打分，录屏 rubric 里还留着
   「Interaction Logic：用户输入响应性 0~25 分」—— 全程没有发过任何一次输入（2509.20136 §2.2、附 P/R）。
   这不是实现瑕疵，是「用录屏当可玩性证据」这条路本身的归谬。

5. **状态接口不能靠模型配合，但不配合也能拿到大部分状态。**
   A2Z 自己就是靠 `window.GameInspector.exportState()`，而且脚手架明确规定每个 build 都要暴露
   `setState` 与场景变更器，这个注入面还被**显式排除在 invariant 检查之外**（2609.39564 附 D.1.2、D.3.2）。
   训练时照搬，模型学到的就是「写那一行」。
   替代路线有四条（表 3.2），按抗欺骗强度排序是
   **输入重放加状态差分 > 绘制调用拦截 > 引擎自带钩子 > 像素与音频 > 要求模型暴露接口**。
   最强的那条反而最便宜：它不需要知道游戏内部任何东西，只需要**同一份代码跑两条输入轨迹然后比差异**。

6. **确定性回放是这一切的地基，而且地基会漏。**
   要固定五件东西（随机源、时间源、帧驱动、输入、资源加载），每一件都有已知的漏法。
   最硬的漏点是 **Web Worker 里的时钟拦截不住**：PlaySuite 为此排除了 **225 个 Construct 3 游戏**，
   是它技术性排除里最大的一类（2610.07127 表 5）。
   次硬的是**超越函数跨引擎版本结果不同** —— ECMAScript 规范不要求 `Math.sin` 的精度，
   `bounce` 物理库有一个现存 issue 就是刚体仿真在 Node（V8 11.3）与 Chrome 149（V8 14.9）下分叉。

7. **难度与平衡是可计算的，而且历史上有现成判据。**
   GVGAI 的 Relative Algorithm Performance Profile（RAPP，2015）：
   让 7 个强弱不同的控制器玩同一个游戏，**好控制器与坏控制器的分差越大，游戏设计越好**。
   实测归一化分：人设计的 18 个游戏里 Explorer 0.7966 对 DoNothing 0.1317；
   随机生成的 65 个游戏只有 0.6193 对 0.3747。胜率差是 8.0 倍对 1.39 倍。
   还有一个更干脆的量：**随机生成游戏的分数标准差最小是 199,406，比人设计游戏的最大值 121.55 大 1500 倍以上**。
   方差爆炸本身就是「规则不自洽」的指纹。

8. **自动 judge 的一致率天花板是人与人的一致率，而且已经很接近了。**
   PlaytestArena：GUI judge 与人的条目级一致率 **87.9%（κ=0.66）**，人与人 **91.4%（κ=0.68）**；
   游戏级 ρ=0.89 对人与人 0.92（2605.28258 表 2，核实见 2.2）。
   PlaySuite：里程碑 judge 与人的「±1 级内一致」**90.4%**，人与人 **93.0%**；
   人与人的 Krippendorff α 只有 **0.624**（2610.07127 §3）。
   **差距只有 2.6 个百分点，而人自己的一致性就不高。** 继续优化 judge 的收益很小，
   该把力气花在第 2 条（覆盖率）和第 3 条（确定性判据）上。

### 1.2 分族要点与各族的坑

**A 能起来：最便宜、也最容易被高估。**
它是必要条件但几乎没有区分度。Code2Games 的基线构建成功率在 91.8~95.9 之间几乎持平，
而核心玩法分从 43.5 到 58.1（2610.05033 表 1）；A2Z 的可验证率 93.9%/94.2%，
Claude-Fable-5.1 可验证率 98.7% 而 GDD 忠实度只有 77.0（§4.2）。
**A 族只能当门，不能当分。**

**B 有响应：本文认为这是最被低估的一族。**
它有一个极漂亮的性质：**不需要知道游戏内部任何东西**。
固定种子、固定时钟，跑「空输入」和「有输入」两条轨迹，比较帧哈希序列是否分叉 —— 就这么简单。
要骗过它，模型必须真的实现一个对输入有反应的系统。
CreativeGame 的做法恰好停在门口：它的 Tier 2 浏览器检查会「发送基本输入」，
但**输入之后什么都不读回**（2604.19926 §6.3），所以它实际上从没回答「有没有响应」这个问题。

**C 规则自洽：判别力最高，也最依赖「题面说了什么」。**
3JSBench 的 695 条必查项里，部件计数 223 + 结构 160 + 空间关系 157 = 540 条，占 78%，
全是「有几个、接在哪、挨着谁」（91_3jsbench_verified §3）。游戏侧的同构物就是 C 族。
但这里有 `90_local_experiments.md` §5 那个坑的游戏版：
**verifier 能查的信息量必须小于等于题面给的信息量。**
A2Z 的解法是把题面做成长篇 GDD（平均每份 **69 条结果性需求 + 32 条不变量**，配 20 个重放场景，§3.3），
信息量足够支撑细粒度判据。短 prompt 配细判据等于纯噪声。

**D 可完成：覆盖率问题，不是判定问题。**
见 §0 第 2 条。这一族的正确做法是**放弃「让 agent 碰运气玩到」**，
改成「把状态注入到前置条件，再只用玩家输入观察效果」。
A2Z 把这件事做得很干净：注入只提供前置条件，**不提供期望效果**，
触发与效果仍必须由真实执行产生，注入要记 `ASSISTED_RULE` 备注（附 D.3.1 原文）。
对比证据在附 G.4：一个 milestone 式的在线游戏 agent（Orak，GPT-5.6-Luna、3 个种子、≤200 步）
在十个游戏上的里程碑达成率只有 6.7%~26.7%，而对抗 playtest 的判定覆盖率是 73.4%。

**E 不可退化：最容易被 reward hacking 利用的方向，必须正面加闸。**
这族的共同点是「错误不随规模衰减」，所以阈值好定。
本项目在 3D 侧已经验证过同类信号的价值：开放边界边数是拓扑量，不随洞的大小衰减，
因此能抓住被全局 IoU 淹没的小破洞（90_local_experiments §2.2）。
E4/E5/E6 是它在游戏侧的对应物。

**F 难度与平衡：本文认为这是公开文献里最被忽视、而落地成本最低的一族。**
RAPP 那篇 2015 年的论文给了一个现成的、完全确定性的难度度量，而 2026 年的游戏生成 benchmark
（A2Z、PlaytestArena、PlaySuite、V-GameGym、Code2Games）**没有一个用它**。
它只要三样东西：一个分数读数、三档强弱策略、多次重放。
`90_local_experiments.md` §2.1 那种「带标签变异集」的方法论可以直接复用：
把「球速 ×3」标成「该挂（难度窗口过窄）」，把「砖块排布 6×8 改 5×10」标成「不该挂」。

### 1.3 层级与门控：照搬 3D 侧的乘法门控

3D 侧是 L0 执行门 → L1 多视角剪影 → L2 体素占据 → L3 部件与拓扑，任一层挂即 fail。
游戏侧的同构分层：

```
L0 执行门    A1 无报错 / A2 主循环在跑 / A3 画面有内容 / A4 首屏可达     → fail
L1 响应门    B1 输入能分叉 / B2 各通道分别有效 / B3 重放一致 / B4 松手即停 → fail
L2 规则门    C2 碰撞 / C3 边界 / C5 状态画面一致 / C6 不变量 / C7 依赖链   → fail
L3 退化门    E1 不卡死 / E4 不泄漏 / E5 不闪烁 / E6 帧预算 / E7 画面没塌   → fail
L4 完成门    D1 可通关 / D2 注入后可验 / C1 分数 / C4 失败可达            → 需策略
L5 平衡门    F1 技能可分辨 / F2 不动不赢 / F3 随机不满分 / F4 方差有界     → 需多策略
```

三条照搬的原则，都有本项目或公开文献的证据支撑：

1. **乘法门控，不做加权求和。** 依据见 `08_rl_recipe.md`：
   RULER 式加权和把 rubric 从 0.395 压到 0.262，L1 加法会塌缩。
   A2Z 的源码分也是乘法的：`F_src = F_rule × F_inv`，不变量违例直接拉低整体（式 4）。
2. **诊断量不进判定。** 3JSBench 把 SigLIP2 相似度明确标为「描述性图像信号，不确立几何正确性，不改变判定」——
   三个模型通过率差 53 个百分点，嵌入相似度只差 0.004。
   游戏侧的对应物是：**录屏的 VLM 打分只报事件，不定生死**。
3. **执行门单列，不混进判定。** 基础设施故障（浏览器崩、超时）要单独一桶。
   A2Z 把「可验证率」单独报（93.9%/94.2%），VideoGameBench 把超预算的 run 单列。

### 1.4 一个必须先承认的量：判定本身也有噪声地板

照 `collapse-stage2-verdict-noise-floor` 那条教训，先把噪声量出来再谈效应。
公开文献里有三个可用的噪声地板：

| 噪声源 | 实测 | 来源 |
|---|---|---|
| 同一个 LLM judge 重判同一条规则 | 谓词结构相同的规则，**重判分差 ≥0.25 的比例是 12.7%（Small）/ 8.8%（Big）**；结构不同时升到 17.7%/11.1% | A2Z 附 B.5 表 S10 |
| 换 judge 配置重判固定 trace | 判定一致率 0.910（Small）/ 0.888（Big）；222 条里只有 6 条、242 条里只有 3 条改变了是否计分 | A2Z §4.6 |
| 人与人判同一条 rubric | 一致率 91.4%、κ=0.68；Krippendorff α 只有 0.624 | PlaytestArena 表 2；PlaySuite §3 |

**推论**：游戏任务上任何 LLM 参与的判定，单次效应小于 3 个百分点就不要相信。
这和 `subset-rate-needs-its-variance`、`case-iteration-n5-resolution-limit` 是同一条教训。
反过来，纯程序判据（A/B/E/F 族）的噪声地板是 **0**（重放逐字节一致），
这是它们真正的优势 —— 不是更准，是**没有方差**。

### 2.2 两个被点名要核实的数字：都成立，而且比原笔记更有料

**A2Z 的 76.8% —— 成立，原文（§4.3）：**

> even among rules that pass with a full source-code score, only **76.8%** are confirmed as satisfied during playtesting, while 23.2% do not receive a full score. In contrast, **25.7%** of rules receiving zero source-code score are judged as satisfied during playtesting.

原笔记只记了 76.8%，漏了三件更重要的：

| 补充项 | 数字 | 含义 |
|---|---|---|
| 反向错判 | 源码判 0 分的规则里 **25.7%** 真玩是满足的 | 源码 judge 既有假阳也有**假阴**，不是单边保守 |
| 部分分段 | 源码分落在 (0,1) 的规则，真玩满足率 **54.3%** | 部分分和真玩的相关性接近抛硬币，`EvilGenie` 那条「部分分挡不住 hacking」在这里同样成立 |
| 去掉某一轴后的排序翻转率 | 去源码 **20.5%**、去重放 **8.9%**、去 playtest **11.2%** | 三轴真的互补；而且**源码轴仍是信息量最大的一轴**，不能因为它会被骗就扔掉 |

**PlaytestArena 的一致率 —— 成立，原文（§3「Is the GUI Evaluator Reliable?」表 2）：**

| 指标 | GUI judge 对人 | 人对人 |
|---|---|---|
| 原始一致率 | **87.9%** | **91.4%** |
| Cohen κ | **0.66** | **0.68** |
| Spearman ρ（游戏级） | **0.89** | **0.92** |
| Pearson r（游戏级） | **0.89** | **0.93** |

额外三条值得记（都在附 C）：

- **换 judge 不改结论**：GPT-5.5、Claude Opus 4.8、Gemini 3.5 Flash 三个 judge 都保持
  `Direct LLM < OpenGame < Play2Code` 的排序；judge 两两的游戏级相关在 0.86~0.94（表 7）。
- **低分到底是游戏坏还是 agent 不会玩**：人工审了 50 条 agent 轨迹，**46/50（92%）是有效试玩**（附 C.3）。
  这是把「评测器失效」和「产物失效」分开的唯一一个公开数字。
- **判错的两类成因**：实时游戏（尤其平台跳跃）的时序不准，以及**漏看小的或低对比度的 UI 元素**
  （原文：一个人能看见能用的控件，agent 看漏了就断言「游戏起不来」，附 C.3）。

### 2.3 一致率的天花板已经摸到了，继续调 judge 收益很小

| 系统 | judge 对人 | 人对人 | 差距 |
|---|---|---|---|
| PlaytestArena（条目级一致率） | 87.9% | 91.4% | **3.5 点** |
| PlaytestArena（游戏级 ρ） | 0.89 | 0.92 | **0.03** |
| PlaySuite（±1 级内一致） | 90.4% | 93.0% | **2.6 点** |
| PlaySuite（Krippendorff α，5 档序数） | 0.605（6 人 + judge） | 0.624（6 人） | **0.019** |

PlaySuite 还做了换 judge 的敏感性（表 10，里程碑一致 / ±1 级内一致）：
Qwen3.5-9B **84.4% / 90.4%**、Qwen3.5-27B 83.9% / **91.6%**、Gemma-4-31B-it 82.5% / 77.3%、Molmo2-8B 77.9% / 81.2%。
**9B 和 27B 基本打平**，所以它选了 9B。

数据解读：人与人在「这关有没有通」这种看似客观的问题上 α 只有 0.624，
意味着**标签本身就带 35% 以上的不可解释方差**。
这和 `90_local_experiments.md` §3.4 那次翻案（VLM 对、我标错了）是同一件事：
**人工标签不是金标准。** 在这个背景下再去优化 judge 的 2.6 个百分点是浪费。

### 2.4 「让 agent 真玩」的真实能力边界

三组数字放在一起看，结论很清楚：**agent 真玩只能验证简单的、前期的、非实时的东西。**

| 设定 | 成绩 | 来源 |
|---|---|---|
| 浏览器小游戏按关卡判通过（20 个游戏约 120 关） | GPT-5.4 pass@5 0.67 / pass@10 0.75 / **pass@20 0.82**；Sonnet 4.6 0.63/0.76/0.79；Kimi K2.5 0.52/0.68/0.72；**人 0.83/0.92/0.92** | PlaytestArena 表 1 |
| 5,734 个真实 itch.io / PyWeek 游戏，0~4 档进度 | 最好 **0.84 分 / 19.5% 达到 Partial+**（Qwen3-Omni-30B，无历史）；最差 0.43 / 8.4% | PlaySuite 表 2 |
| 1990 年代商业游戏，感知哈希判检查点 | 最好 **0.48%** 完成度；3 个保密游戏全 0%；Doom II 第一关「走两个转角」被一位无游戏经验的作者 20 秒内通过 | VideoGameBench 表 2、§4.2 |
| 十个 Big GDD 游戏，milestone 式在线 agent | 里程碑达成率 **6.7%~26.7%**（3 个种子，≤200 步） | A2Z 附 G.4 表 S20 |

三条可直接用的工程结论：

1. **题材差异大于模型差异。** PlaySuite 表 3（≥60 个游戏的题材）：
   模拟 0.893 / 27.1% Partial+，策略 0.858 / 25.2%，而**解谜只有 0.606 / 10.0%，冒险 0.544 / 9.5%**。
   模型间排序却很稳：各题材对总排序的 Spearman ρ = 0.88~0.99。
2. **给 agent 看历史反而更差。** PlaySuite：无历史在两个语料上平均进度都最高；
   k=3→5 无明显收益，k=10 更差；**加 k=3 在每一个题材上都降低了平均进度**（表 11）。
   少样本提示也降分。这和 GUI agent 的常识相反，值得在自己的 harness 上复验。
3. **动作频率不是瓶颈。** 把 PyWeek 的动作频率从 0.33 Hz 提到 3 Hz，平均进度只从 **0.862 到 0.926**。
   也就是说「agent 玩不动」不是手慢，是不理解。

### 2.5 世界模型不能当可玩性 verifier

| 系统 | 公开规模 | 公开评测指标 | 能不能当 verifier |
|---|---|---|---|
| **Microsoft Muse / WHAM**（Nature 2025-02，WHAM-1.6B） | 超过 **10 亿**图像与手柄动作对，约等于**七年以上连续人类游玩**，单一游戏 Bleeding Edge 七张地图；当前输出 **300×180 像素**（最早的模型 128×128） | 一致性：用真实 gameplay 与动作做条件，生成最长**两分钟**序列，与真值比 **FVD**；多样性：给同样的 10 帧（1 秒）起始，与人类录像比 **Wasserstein 距离**；持久性：把一个角色编辑进画面看能不能带下去，**只有定性演示，没有指标** | **不能。** 这三个指标量的是「生成的 gameplay 像不像人玩的分布」，不是「这条规则成不成立」。微软自己把它定位为 gameplay ideation，官方页面全文没提 playtesting |
| **Genie 2 / Genie 3**（DeepMind 2025-08-05 公告） | Genie 3：**720p、24 fps、实时**，一致性维持**「几分钟」**；Genie 2 是 10~20 秒 | **公告里没有任何定量基准。** 可提示的世界事件只有例子（往崖壁加瀑布）；SIMA agent 在三个 Genie 3 世界里达成目标的说法是**定性的**，没有成功率、试验次数或基线 | **不能，而且连评也评不了。** 没有公开数字可引 |

一句话：世界模型解决的是「造出一个能交互的东西」，
可玩性 verifier 解决的是「判断一个已经造出来的东西是否按规则交互」。
后者需要的恰好是世界模型没有的东西：**确定性与可重放性**。

### 2.6 传统游戏 AI 的自动测试：三条能直接抄的东西

**(1) 随机猴子是强基线，不是陪衬。**
Choudhary / Gorla / Orso 对 6 个 Android 自动测试工具在 **68 个应用**上各跑 10 次、每次 1 小时
（[1503.07217](https://arxiv.org/html/1503.07217)）。原文结论：

> Considering the four criterion of the study, **Monkey would clearly be the winner** among the existing test input generation tools, since it achieves, **on average, the best coverage**, it can report the largest number of failures, it is ease to use, and works for every platform.
> 我们的结果表明：1) 大部分行为只靠生成 UI 事件就能触发；2) 要暴露这些行为，**随机方法已经足够有效**。

两个边界也在原文里：覆盖率最低的工具在少数应用上也能到约 80%（都是最简单的应用，
其中一个就是只接受点击与划动的游戏 DivideAndConquer）；
而 K9mail、PasswordMakerPro 这类依赖外部账号的应用，**所有工具都低于 5%**。
**推论**：对我们这种 50~200 行的小网页游戏，随机输入猴子的覆盖率会很高，
所以 F3（随机不能满分）这条闸尤其必要 —— 否则模型写一个「乱按就能赢」的游戏会被判满分。
（精确的逐工具覆盖率百分比只在原文图 2 里，未能从文本提取，本文不引具体数值。）

**(2) 好奇心驱动的探索 agent：用来找卡死点与越界，不是用来打分。**
Gordillo 等（EA SEED，CoG 2021，[2103.13798](https://arxiv.org/html/2103.13798)）在一个复杂 3D 地图上：
以访问计数的倒数做新颖性奖励，每 episode **3000 步（约 1 分钟游戏时间）**，5 次独立运行；
100% 覆盖估为 **25K 个可达点**，**跑约 24 小时覆盖 90%**；随机策略只能到容易到的区域。
三个可抄的机制：

- **卡死点定位**：对每个已访问点维护「episode 在此终止的次数」，训练结束后看分布离群点（§IV-D）。
  这是 E1/E2 的一个无需语义的实现。
- **越界检测**：预先画一个 exploration boundary，agent 越界就终止 episode（§IV-B）。这是 C3 的实现。
- **意外通路检测**：用连通图分析区域之间的连接，识别设计外的路径（§IV-C）。这是「穿墙 / 走捷径」的高阶版。

代价很诚实：24 小时换 90% 覆盖，**单个游戏**。
这个量级不可能进 RL 内循环，只能用于离线造变异集和体检 verifier。

**(3) RAPP：现成的确定性难度判据。**
Nielsen / Barros / Togelius / Nelson，EvoStar 2015
（[kmjn.org/publications/GVGprofiles_Evostar15.pdf](https://www.kmjn.org/publications/GVGprofiles_Evostar15.pdf)）。
7 个控制器（Explorer、MCTS、GA、OneStep-Score、OneStep-Heuristic、Random、DoNothing）
玩 **18 个人设计 + 146 个变异 + 65 个随机生成**的 VGDL 游戏。

| 游戏来源 | Explorer 归一化分 | Random | DoNothing | 最强与 DoNothing 分差 | Explorer 胜率 / DoNothing 胜率 | 分数标准差范围 |
|---|---|---|---|---|---|---|
| 人设计（18 个） | 0.7966 | 0.2493 | **0.1317** | **0.665** | 0.4467 / 0.0556 = **8.0 倍** | 4.02 ~ 121.55 |
| 变异（146 个，另有 54 个被排除） | 0.8361 | 0.2581 | 0.1819 | 0.654 | 0.3055 / 0.0959 = 3.2 倍 | 666.81 ~ 6,441.77 |
| 随机生成（65 个） | 0.6193 | 0.3195 | **0.3747** | **0.245** | 0.2566 / 0.1846 = **1.39 倍** | **195,365 ~ 262,508** |

四条可以直接变成判据：

1. **技能分差**（F1）：人设计 0.665 对随机生成 0.245，差 2.7 倍。阈值取 0.4 有安全边界。
2. **DoNothing 必须接近 0**（F2）：原文明确把这条单列为「设计良好的次级指标」——
   在人设计的游戏里 DoNothing 极少获胜甚至极少得分（0.1317 / 胜率 0.0556）；
   随机生成的游戏里它反而拿 0.3747、胜率 0.1846，**甚至比 Random 高**。
3. **分数方差爆炸就是规则不自洽**（F4）：随机生成游戏的最小标准差 199,406（表中 Random 一行）
   比人设计游戏的最大值 121.55 大 **1,500 倍以上**。这是本文认为最被低估的一个免费信号。
4. **「分数永不涨 / 永不赢」和「单帧超过 50ms」应当是独立的退化闸**：
   原文在分析前就把这两类变异游戏**整类排除**（§4.2，200 个变异里排掉 54 个）。
   这正好对应本文的 C1 与 E6 —— 2015 年的人已经知道这两类必须先滤掉。

局限要说清：RAPP 的载体是 VGDL，有**可前向仿真的模型**（控制器能做 lookahead）；
网页游戏没有这个，所以 Explorer / MCTS 这档策略在网页上要换成「贪心启发式脚本」。
分差会变小，阈值必须在自己的数据上重标。

### 2.7 三个反面案例：被骗的具体方式

这些是造变异集时最该抄的「该挂」标签。

| 骗法 | 出处 | 为什么骗得过 | 对应判据 |
|---|---|---|---|
| 进入目标区域就记分，**2.75 秒后又跳回去** | A2Z 附 G.4（`Toybox Rider`：180.23 s 进 Art Desk，182.98 s 回到 Block Street） | milestone agent 只查「到过没」，到过就给分 | C6 不变量必须**持续**成立，不是瞬时成立 |
| 画面显示溺亡，**状态里 Hull 仍是 100** | A2Z §4.5 图 7（`Abyssal Chain` RT-DAMAGE D5） | 只看截图的 judge 看到了溺亡画面 | C5 必须同帧交叉断言状态与像素 |
| 数字渲成**白底白字**，单测全过但游戏不可玩 | PlayCoder §5.4（MetaGPT 生成的 2048） | 单测只查数据结构，不查可见性 | E7 画面熵与对比度下限 |
| 教程前 120 秒不该有移动障碍物，**7.37 秒就出现了** | A2Z 附 G.4 同一个游戏 | milestone 谓词里没有这条 | C6 不变量要带作用域（时间窗） |

最后一条特别值得展开：GameArena 用「回溯分析」（离线用完全相同的 prompt 与历史重放，
要模型吐出每一轮的中间状态）造出过程信号，结果**过程信号与推理榜的秩相关 τ=0.8，
结果信号只有 τ=0.2，Taboo 的结果信号甚至是 −0.2**。
翻译到我们的场景：**「通关了」这个 0/1 比「通关过程中每条规则是否按契约生效」弱得多，而且可能是反向的。**

## 3 状态接口怎么拿

### 3.1 先说清楚：公开系统全都靠游戏配合，而且这不是能直接搬进训练的

**UI-TARS-2（[2509.02544](https://arxiv.org/html/2509.02544) §2.5.1）原文：**

> 我们用 LLM 合成新游戏，生成**保留核心玩法机制同时暴露显式状态接口**的轻量代码实现。
> 对真实与合成的游戏，**我们都写简短的 JavaScript 验证脚本去查询运行时变量**（分数、关卡序号、剩余生命），
> 并提供时间对齐的状态属性。

它的沙箱（§2.2）：HTML5/WebGL 浏览器沙箱，兼容 CDP 与 Playwright，
**「重新实现的 Window 计时 API 允许在启动时加速与暂停时间，在不改变游戏逻辑的前提下提升采样效率与可复现性」**。
reward（§2.5.2）：游戏属于「有自动函数式 verifier」的一档，**直接算二元正确性信号**；
生成式 ORM 只用在 GUI-General 这类没有 verifier 的任务上（那个 F1=83.8 是 GUI 轨迹上的，不是游戏上的）。

**A2Z（[2609.39564](https://arxiv.org/html/2609.39564)）走得更远，把它写进了脚手架：**

- 附 C「Game Development Environment」：100 个任务全是 Phaser 4.1 + TypeScript + Vite，
  **所有 coding agent 从同一个工程与同一份「运行时接口规范」出发**。
- 附 D.3.2：bot 拿到的 `ctx.state()` 读的就是 `GameInspector.exportState()`；
  对抗式 playtest 额外用 `ctx.setState(patch)` 把状态注入到前置条件。
- 最关键的一句在附 D.1.2「Checking an Invariant」：
  **「每个 build 里为 verifier 而存在的状态注入面（`setState`、场景变更器、场景入口）不被当作违反路径，因为它本来就是设计用来允许任意状态修改的。」**

**所以这条路的问题不是「不好用」，是三个具体的后果：**

| 后果 | 说明 |
|---|---|
| 训练时会学成一行代码 | reward 只要求 `exportState` 存在且字段对得上，模型的梯度会流向「把这一行写对」，而不是「把游戏写对」。换 harness 即失效，这和 `90_local_experiments.md` §1.2 里拒绝 `window.__SCENE__` 是同一个理由 |
| 注入面本身是个 hack 通道 | A2Z 必须把它显式从 invariant 检查里豁免，等于承认它破坏了「不变量在所有可达路径上成立」这个性质。模型完全可以让 `exportState` 返回一份与真实状态无关的漂亮数据 |
| 成本模型是「一个游戏一份脚本」 | UI-TARS-2 对真实游戏就是逐个手写验证脚本。这在 15 个游戏上可行，在 RL 需要的几万个任务上不可行 |

### 3.2 四条替代路线

| 路线 | 怎么拿到状态 | 能验证哪些子命题 | 骗得过吗 | 覆盖面 | 成本 |
|---|---|---|---|---|---|
| **R0 要求模型暴露接口** | 脚手架规定 `exportState`/`setState` | 理论上全部 C、D 族 | **骗得过**，而且训练时一定会被骗 | 100%（强制） | 低 |
| **R1 引擎自带钩子** | 由引擎自己派发的全局（见 3.3） | 实体数、位置、变换、材质色、物理体位置与速度；配合差分可做 B/C2/C3/E4 | **难骗**（事件由引擎发，不是作者写的），但钩子只给**渲染/场景图**，不给分数与生命 | 取决于引擎，见 3.3 表 | 低 |
| **R2 渲染循环与绘制调用拦截** | 预加载时劫持 `requestAnimationFrame`、`getContext`、2D ctx 方法、`drawArrays/drawElements` | A 全族、E1/E4/E5/E6、B1（用绘制调用序列做差分）；2D 游戏还能从 `fillText` 的参数**直接读出 HUD 文字**（分数、生命）而不用 OCR | **几乎骗不过**：这就是玩家看到的东西，要骗必须真的画出来 | 全部 canvas 游戏 | 中 |
| **R3 输入重放 + 确定时钟 + 状态差分** | 不读游戏内部任何东西；固定种子固定时钟跑**多条输入轨迹**，比较 R1/R2 产物或帧哈希序列 | B 全族、C1（分数读数来自 R2 的 `fillText`）、C3、E1/E2、**F 全族** | **最难骗**：要骗必须真的实现一个会按规则响应输入的系统 | 全部 | 中 |
| **R4 像素与音频弱监督** | 帧差；`AudioBufferSourceNode.prototype.start` / `AnalyserNode` 探测音效事件 | A3、E7、B1 的弱版本 | **容易骗**：背景动画会让每一帧都不同 | 全部 | 低 |

**抗欺骗强度排序：R3 > R2 > R1 > R4 > R0。**
和 `feature-value-is-veto-not-ranking` 那条一致：R4 只能当否决器（画面全白就判挂），不能当排序器。

**R3 是本文的主推，理由是它的性质而不是它的强度：**
它把「可玩性」转成了一个**不需要语义的差分问题**。
一条空输入轨迹、一条有输入轨迹、几条不同强度的策略轨迹，
剩下的全是序列比较。这条路本项目已经有一半基础设施了 ——
`scripts/vc_verifier/proto/harness.js` 的冻结时钟部分可以原样复用。

### 3.3 R1 的现实：引擎钩子的实际可用性（逐引擎核实）

下表是实地读 CDN 发行包源码得到的，不是文档转述。

| 引擎 | 钩子 | 谁创建的 | 不配合也能用吗 |
|---|---|---|---|
| **three.js** | `__THREE_DEVTOOLS__` 的 `observe`/`register` 事件；另有 `window.__THREE__` 版本指纹 | **引擎**（`WebGLRenderer` 与 `Scene` 构造函数里各一处） | **能**，前提是在页面脚本执行前注入 |
| **PixiJS v8** | `globalThis.__PIXI_APP_INIT__(app, version)`、`__PIXI_RENDERER_INIT__(renderer, version)` | **引擎**（`ApplicationInitHook` / `RendererInitHook`，8.6.6 实测） | **能**。注意 `__PIXI_DEVTOOLS__` 是**作者**要自己设的，devtools 文档明确要求 `initDevtools({app})`，不能依赖 |
| **Babylon.js** | `EngineStore.Instances`（`AbstractEngine` 构造函数里无条件 push）、`LastCreatedScene` | **引擎**，无 debug 开关 | **能**，前提是 `window.BABYLON` 存在（UMD/CDN 构建）。tree-shaken 的 ESM 构建里 store 存在但没有全局名 |
| **Phaser 3** | 只有 `window.Phaser` 命名空间（版本指纹，无实例列表）。`src/core/Game.js` 里有 `if (typeof WEBGL_DEBUG && window) window.PHASER_GAME = this`，但**在 3.60/3.70/3.80.1/3.90 的八个 dist 文件里 grep `PHASER_GAME` 全是 0 命中** | 引擎，但发行包里被编译掉了 | **不能**。没有 `Phaser.GAMES`（那是 Phaser 2 的东西，在 phaser-ce 2.20.0 里也未能确认）。唯一通用路子是在页面脚本前用 Proxy/getter 劫持 `Phaser.Game` 构造函数 |
| **p5.js** | `window` 上的 `p5Ready` 事件；global 模式下 `p5.instance` 被赋值，且整个 API 与 `mouseX`/`frameCount`/`width` 等被拷到 `window` | 引擎，仅 global 模式 | **部分能**。`new p5(sketch, node)` 的 instance 模式下 `p5.instance` 不被赋值。好消息是手写小游戏基本都是 global 模式，**连 sketch 自己的 score 变量都在 window 上** |
| **matter.js / planck.js** | 无注册表 | — | **不能**。只能劫持工厂（`Matter.Engine.create`）或劫持 `Matter.Engine.update` 从第一个参数拿到 engine，后者顺带得到一个 per-tick 钩子。拿到之后能读**真值位置、速度、碰撞对**，常常比分数更好用 |
| **Unity WebGL** | `unityInstance.SendMessage(obj, method, value)` | **作者的 index.html 模板** | **不能**，而且 `SendMessage` 是**只写**的，没有返回值。读 C# 状态要去翻 `Module.HEAPF32` 的 IL2CPP 偏移，是逐 build 逆向，不是技术 |
| **Godot 4 web** | `JavaScriptBridge`（**只在 Web 导出里有，构建时可关**） | 作者的 GDScript | **不能**。没有文档化的路子让页面 JS 调进 GDScript 或读引擎状态 |

**三条结论：**

1. **可靠的钩子全都是「在 document-start 注入一个引擎会条件读取的全局」。**
   所以 verifier 的真正硬需求不是什么巧妙的运行时查询，而是
   **控制 document-start 脚本注入**（Playwright `addInitScript` / CDP `Page.addScriptToEvaluateOnNewDocument`）。
2. **没有一个钩子给得出游戏逻辑状态。** 它们给的是渲染图与场景图。
   分数和生命仍然在作者的闭包里 —— 这正是 UI-TARS-2 要逐个游戏写脚本的原因。
3. **最常见的网页小游戏引擎 Phaser 3 恰好是最不可用的那个。**
   A2Z 的 100 个任务全是 Phaser，这解释了它为什么只能走 R0。
   如果本项目要做 Phaser 任务，必须自己实现构造函数劫持，不能指望现成钩子。

### 3.4 R2 的边界：绘制调用拦截能读出什么、读不出什么

**能读出的**：每帧绘制调用数、图元数、绑定的 program/texture/VBO 身份、
uniform 值（于是 model/view/projection 矩阵 → 物体变换）、clear color、混合与深度状态。
现成工具是 **Spector.js**（https://github.com/BabylonJS/Spector.js ），
可以作为普通 script/UMD 注入（`new SPECTOR.Spector()`），
API 是 `captureNextFrame` / `startCapture(obj, commandCount, quickCapture)` / `stopCapture(): ICapture`（返回 JSON），
另有 `spyCanvases()` 读纹理内存与格式、`getFps()`。
原文注明单次 capture **到达指定命令数或 10 秒后自动停止** —— 它是采样器，不是连续状态流。
WebGL-Inspector 已经被 Spector 自己的 README 说明为「不兼容 WebGL2，已被取代」，不要用。

**读不出的，而且这几条比上面重要：**

| 盲区 | 为什么 |
|---|---|
| **精灵批处理会把逐物体信号抹平** | Pixi 与 Phaser 都会把共用图集的上千个精灵合并成一次 `drawArrays`。所以「绘制调用数约等于物体数」这个直觉**恰好在网页小游戏最常用的 2D 引擎上是错的** |
| 没有语义身份 | trace 只说「在矩阵 M 处画了一个带贴图的四边形」，不说「这是玩家」。要映射回实体就得逐游戏解码，又回到逐游戏成本 |
| 没有不被渲染的状态 | 分数、生命、关卡序号、计时器、RNG 种子、AI 状态，凡是算了但没画的都看不见 |
| shader 侧的逻辑不透明 | 顶点蒙皮、GPU 粒子、任何在 shader 里用时间 uniform 算出的变换 |
| WebGPU 不在范围内 | Spector 只管 WebGL1/2 |

**一个被低估的技巧**：对 **Canvas2D** 游戏，draw-call trace 的语义比 WebGL **更强** ——
拦截 `fillText` 就能直接从参数里读出 HUD 字符串（分数、生命、关卡），**完全不需要 OCR**。
网页小游戏绝大多数 HUD 就是 `fillText`。这条让 C1（分数会涨）从「半确定性」降级成「全确定性」，
是本文认为最值得先实现的一条。
（本条是机制推论，没有找到公开文献把渲染 trace 当游戏测试 oracle 的；
GraphicsFuzz 那条线测的是驱动不是游戏。当作未开垦地带而不是有论文背书的做法。）

### 3.5 存活与卡死的探测：三个会骗人的地方

1. **rAF 计数为 0 不等于游戏死了，可能只是被节流。**
   Chrome 官方：「页面在后台时 Chrome 不调用 `requestAnimationFrame()`，这个行为从 2011 年就有了」
   （https://developer.chrome.com/blog/background_tabs ）。
   所以**在把帧计数当证据之前必须先把可见性钉住**（前台化目标页、检查 `document.visibilityState`）。
   一个有用的副作用：**有声音的页面豁免后台节流**，所以 §3.2 的 R4 音频通道顺带解决了这个问题。
2. **主线程卡死时你的探针也卡死。** `Runtime.evaluate` 跑在渲染进程主线程上，
   游戏把主线程卡住，你的 `page.evaluate` 一起超时 —— **超时本身就是信号**。
   还能回话的带外通道：`Performance.getMetrics`、浏览器级 target、
   `Page.captureScreenshot`（走合成器，所以冻结但仍在合成的页面会截到一张不变的旧帧）。
   **判据：截图成功但 evaluate 超时 ⇒ 主线程卡死。**（这一条是推论。）
   区分「卡死」与「只是慢」要四个条件一起看：rAF 计数不增、LoAF/longtask 出现秒级条目、
   短超时的 evaluate 失败、N 秒内截图哈希不变。单看任一条都有歧义。
3. **JS 里拦不住同 realm 的死循环。** 事件循环永不让出，你自己的看门狗回调也永不执行。
   两条现成办法：
   - **静态插桩**：`loop-protect`（https://github.com/popcodeorg/loop-protect ）用 Babel AST 改写，
     给循环包一个条件 break，默认阈值 **100ms**；原文自认**不解决停机问题**，
     只覆盖 `while`/`for`/`do`，**不防递归**。CodePen 用同样思路，freeCodeCamp 用约 500ms。
   - **跨 realm 杀**：把游戏放进 Worker 或跨进程 iframe，从外面 `terminate()`。代价是失去逐帧粒度。
   Long Tasks 的阈值是规范写死的：「本 API 暴露耗时 50ms 及以上的任务」，且
   「时长只以 **1ms** 粒度提供」（https://w3c.github.io/longtasks/ ）。
   更细的归因要用 **Long Animation Frames（LoAF）**，`entryType: "long-animation-frame"`。

### 3.6 输入保真度：五个会让「没响应」变成假阳的坑

| 坑 | 事实 | 怎么办 |
|---|---|---|
| **合成事件不是可信事件** | MDN 原文：`isTrusted` 在 `dispatchEvent()` 派发时为 `false`；`HTMLElement.click()` 也是 `false`。后果是**游戏自己的监听器照样会收到**（绝大多数游戏不查 `isTrusted`），但**不触发默认动作**，也会被任何依赖用户激活的 API 拒绝 | 一律走 CDP `Input.dispatchKeyEvent` / `dispatchMouseEvent` / `dispatchTouchEvent`，它们进 Chrome 原生输入管线，产生可信事件。Puppeteer 的 `page.keyboard` 就是它 |
| **`rawKeyDown` 与 `keyCode=0`** | Puppeteer 在按键不产生文本时发 `rawKeyDown` —— 也就是**恰好在方向键、空格跳跃、WASD、Escape 上**。手搓 CDP 时如果漏掉 `windowsVirtualKeyCode`，读 `event.keyCode` 的游戏会看到 0 | `code`、`key`、`windowsVirtualKeyCode` **三个都填**，可打印键再填 `text`/`unmodifiedText`。参照表是 Puppeteer 的 `USKeyboardLayout.ts` |
| **按键重复** | 很多游戏用 keydown 集合实现按住移动，另一些依赖自动重复。Puppeteer 对已按下的键再 `down()` 会设 `autoRepeat: true` | 朴素的 down/up 对会产生「一按一格」，看起来像游戏坏了。要显式长按 |
| **只绑了 touch 的游戏** | 移动优先的 HTML5 小游戏经常**只绑 touch 事件**，纯鼠标 harness 会静默什么都不发生。CDP 规定 `touchStart`/`touchMove` 必须带至少一个触点，`touchEnd`/`touchCancel` 必须不带 | 配 `Emulation.setTouchEmulationEnabled` / `setEmitTouchEventsForMouse`；B2 这条子命题必须逐通道单独验 |
| **Gamepad 无法合成** | 实地枚举 `browser_protocol.json` 的 53 个域与全部命令：**没有 Gamepad 域**。`Input` 只有 13 个命令，`Emulation` 的 48 个命令覆盖传感器、设备姿态、压力、空闲、视觉缺陷、屏幕，**没有 gamepad**。整个协议里 "gamepad" 只出现一次，作为 permissions-policy 的 feature 名 | 只能在 init script 里 `Object.defineProperty(navigator, 'getGamepads', ...)` 做 shim 并派发假的 `gamepadconnected`。产生的是 `isTrusted: false` 的事件和非原生对象，严格 duck-typing 的游戏会挂 |

另外两条：headless 页面常常是失焦的，失焦页面丢键盘输入，要 `Emulation.setFocusEmulationEnabled`；
pointer lock 下游戏读 `movementX/movementY` 而不是 `clientX/Y`，
CDP 派发的鼠标移动在 headless 下能不能给出正确的 `movementX/Y` **未核实**，
把指针锁定类的第一人称网页游戏当已知高风险类别，单独测。

## 4 确定性回放

目标：**同一份代码、同一条输入序列，两次跑出逐字节相同的轨迹。**
做到这一点，§1 的 24 条确定性判据的噪声地板就是 0；做不到，所有判据都要配容差和重复采样，成本直接乘上去。

### 4.1 要固定的五件东西

| # | 要固定什么 | 怎么固定 | 本项目现状 |
|---|---|---|---|
| 1 | **随机源** | 预加载时替换 `Math.random` 为确定 PRNG（xorshift / seedrandom）；`crypto.getRandomValues` 也要换 | `harness.js` 已接管 `Math.random`（90_local_experiments §1.1） |
| 2 | **时间源** | `Date.now`、`new Date()`、`performance.now` 全部返回由 harness 推进的虚拟时钟 | 已接管 `performance.now`、`Date.now` |
| 3 | **帧驱动** | 接管 `requestAnimationFrame`，帧只在 harness 调 `__vcStep(n, dt)` 时推进；`setTimeout`/`setInterval` 也要挂到同一个虚拟时钟上；CSS 动画与 Web Animations 另算 | 已接管 rAF，**`setTimeout`/`setInterval` 未接管，游戏任务必须补** |
| 4 | **输入** | 输入事件的发出时机按**帧号**而不是墙钟毫秒；每条轨迹是一个 `(frame, action)` 列表 | 新增，3D 任务不需要 |
| 5 | **资源加载** | 断网，页面从内存里的 URL 加载，固定加载顺序 | `harness.js` 已做（除引擎本身所有外部请求一律拦掉） |

**两条路线，选一条或两条都用：**

- **页内 shim**（上表的做法，UI-TARS-2 说的「重新实现的 Window 计时 API」大概是这条）：
  便宜、可移植，但**游戏可以检测**（查 `Date.now.toString()` 就能看出被改过），
  而且漏一个 API 就漏一个熵源。
- **CDP 虚拟时间**（`Emulation.setVirtualTimePolicy`，EXPERIMENTAL）：
  协议原文「为所有 frame 打开虚拟时间（**用合成时间源替换真实时间**）并设置当前虚拟时间策略。
  注意本调用会取代之前的任何时间预算。」
  参数：`policy` 取 `advance` / `pause` / `pauseIfNetworkFetchesPending`；
  `budget`「这么多虚拟毫秒过去之后虚拟时间暂停并发出 `virtualTimeBudgetExpired` 事件」；
  `maxVirtualTimeTaskStarvationCount`「在虚拟时间被强制前推以**防止死锁**之前能运行的最大任务数」；
  `initialVirtualTime`「`base::Time::Now` 会被覆盖为初始返回这个值」。
  配 `HeadlessExperimental.beginFrame` 做显式步帧。
  标准用法（`pause` 拿基准时间戳 → 按动画帧间隔分块给预算 → 先 `beginFrame`）在 Chromium 自己的
  helper 里：https://chromium.googlesource.com/chromium/src/+/main/headless/test/data/protocol/helpers/virtual-time-controller.js
  **它在 JS 之下，游戏检测不到**，这是它相对页内 shim 的硬优势。
  代价：实验性接口，跨 Chrome 版本会变；`maxVirtualTimeTaskStarvationCount` 的存在说明它自己会遇到死锁。

**建议：两条都用。** CDP 虚拟时间负责「游戏检测不到」，页内 shim 负责「漏网的 API」。
两条同时在，可以互相当对照：如果只开一条和同时开两条的轨迹不一致，说明有个熵源被漏了。

### 4.2 破坏因素清单

按「能不能治」分三档。

**第一档：能彻底治。**

| 破坏因素 | 表现 | 治法 |
|---|---|---|
| `Math.random` | 每次轨迹不同 | 替换为固定种子 PRNG |
| `Date.now` 当熵源或当 dt 来源 | 两次跑 dt 不同，物理步长不同 | 冻结。**注意：只接管 rAF 不接管 `Date.now` 会漏**，因为很多游戏自己用 `Date.now()` 差算 dt |
| `setTimeout` / `setInterval` | 回调相对帧的次序不定 | 挂到同一虚拟时钟上，按虚拟时间排队 |
| 外部资源加载顺序 | 竞态 | 断网 + 内存 URL + 固定顺序 |
| CSS 动画 / Web Animations | 与 rAF 不同步 | Playwright 的 `animations: 'disabled'` 原文「停止 CSS 动画、CSS 过渡与 Web Animations」（有限动画会快进到终态）。**但它对 rAF 驱动的 canvas 游戏循环完全无效** |
| GPU 光栅化差异 | 截图逐位不一致 | SwiftShader 软渲染 + `--disable-gpu`（本项目 3D 线已经这么跑） |

**第二档：只能缩小，不能消除。**

| 破坏因素 | 量级与证据 | 缩小办法 |
|---|---|---|
| **超越函数跨引擎版本不同** | ECMAScript 规范**不要求** `Math.sin` 等的精度（只对若干边界情形要求精确值，其余留给实现）。TC39 的 bug 记录里有 Firefox 与 Chrome 在 Windows/Mac 上通过而在 Linux 上不通过同一个 sine 测试的案例。现实例子：`bounce` 物理库有一个**现存 issue**，刚体仿真在 Node（V8 11.3）与 Chrome 149（V8 14.9）下分叉，而简单场景一致（https://codeberg.org/perplexdotgg/bounce/issues/8 ，报告者自测，issue 仍开着） | **锁死浏览器版本与镜像**，verifier 与造题用同一个镜像。判据用容差不用逐位 |
| 浮点运算顺序（SIMD、FMA） | 跨 CPU 微架构可能不同 | 同上，锁机器类型；本机 3D 线用 SwiftShader 已经绕掉了 GPU 侧 |
| `performance.now` 的精度被故意粗化（Spectre） | 跨源隔离上下文 5µs、否则 100µs 量级（**具体数值未核实**） | 本来就该用虚拟时钟而不是真实计时 |
| GC 与长任务抖动 | 单帧真实耗时抖 | 虚拟时间能让**逻辑**确定，但**测不了真实帧率**。PlaySuite 明确声明「闭环协议把模型推理延迟从游戏动态里移除了，所以 PlaySuite 不测实时反应速度」（§6）。E6（单帧预算）因此只能当粗闸 |

**第三档：治不了，只能排除任务。**

| 破坏因素 | 证据 |
|---|---|
| **Web Worker 里的时钟拦截不住** | PlaySuite 排除了 **225 个 Construct 3 游戏**，原因是「它们的游戏循环依赖 Web Worker，我们的浏览器时钟拦截机制无法可靠地暂停它」（2610.07127 表 5）。这是它技术性排除里**最大的一类**，比「只支持拖拽」的 72 个、「多人」的 25 个都多。Spector.js 的 `spyWorkers()` 也是实验性的，并且明确拒绝 URL 对象、module Worker、blob/data/跨源 URL、嵌套 Worker |
| OffscreenCanvas + Worker 渲染 | 同上 |
| WebGPU | Spector 不覆盖；WebGPU 的 timestamp query 本身也是非确定的 |
| 依赖真实网络的游戏 | 断网就起不来；A2Z/PlaySuite 都是网络隔离沙箱 |

**一个常被当成破坏因素但其实不是的**：`Map`/`Set` 的迭代顺序。
ECMAScript 规范保证按插入序迭代，这是确定的。真正有坑的是 `for...in` ——
整数型字符串键会被排到前面，这个行为跨引擎一致但容易写出意料外的结果。

### 4.3 可操作的自检流程

照 `90_local_experiments.md` §1.3 的做法（实测打包版页面也能抓到），确定性也要有一个能跑的自检：

```
对每个任务（参考解与每个变异）：
  1. 同一轨迹跑两遍，比较完整状态序列的 SHA256  → 不一致就是漏了熵源，查日志里哪一帧先分叉
  2. 只开页内 shim 跑一遍，同时开 CDP 虚拟时间跑一遍  → 不一致说明有一条路漏了 API
  3. 换一台同镜像机器跑一遍  → 不一致说明浮点或 GPU 侧有残留
  4. 把 (frame, action) 列表的时间基准从帧号改成毫秒再跑  → 应该不一致（这是反向自检：证明判据真的在用帧号）
```

第 1 条是硬门：**任何一个任务过不了双跑一致，就不许进数据集。**
这正是 `90_local_experiments.md` §4 那个「准入测试」的确定性版本 ——
准入测试的产出不只是任务，还是 harness 的体检报告。

## 5 本机最小实验设计：输入重放加状态差分

不要求实现，给方案。目标是用最小代价回答一个问题：
**「输入重放 + 状态差分」这条不需要游戏配合的路线，判别力够不够。**
判别力的度量方式照搬 3D 线：**带标签变异集，该挂与不该挂都要有，阈值先定死再跑。**

### 5.1 被试与基础设施

- **被试游戏**：手写一个约 150 行的 Canvas2D 打砖块（Breakout）。
  选它的理由是**一个游戏覆盖全部六族**：分数（C1）、碰撞（C2）、边界（C3）、
  失败条件（C4）、胜利条件（D1）、HUD 文字（R2 的 `fillText`）、随机性（球的初始角度）。
  贪吃蛇没有「可通关」，Flappy Bird 没有「分数上限」，都少一族。
- **参考解**：我自己写，不是模型写的。参考解必须先过 verifier（自比自），防 verifier 本身坏掉。
- **Harness**：复用 `scripts/vc_verifier/proto/harness.js`，补四样：
  1. `setTimeout`/`setInterval` 挂到虚拟时钟（3D 线不需要，游戏必须）
  2. `getContext('2d')` 返回 Proxy，记录 `fillRect`/`fillText`/`drawImage`/`fillStyle` 的调用序列
  3. 输入重放：`(frame, action)` 列表，在 `__vcStep` 的对应帧前用 CDP `Input.dispatchKeyEvent` / `dispatchMouseEvent` 发送
  4. 每帧末尾导出一个**状态指纹**：绘制调用序列的哈希 + 从 `fillText` 解析出的 HUD 数字 + 画布像素哈希
- **不读游戏任何内部变量。** 这是实验的核心约束，否则证明不了 R3 这条路可行。

### 5.2 四条轨迹

| 轨迹 | 输入 | 用来验 |
|---|---|---|
| T0 空轨迹 | 600 帧无输入 | 基线；A 族；E1/E2；F2（不动不能赢） |
| T1 固定脚本 | 600 帧，预先写死的 `(frame, action)` 列表 | B 族（与 T0 比是否分叉）；C1/C3；B4（含 down→帧→up→帧 的段） |
| T2 贪心脚本 | 每帧按 HUD 与绘制调用里解析出的球位置追球（不读内部变量） | D1（能不能通关）；F1（技能分差的上端） |
| T3 随机猴子 | 600 帧随机按键，固定种子，跑 10 个种子 | F3（随机不能满分）；F4（分数方差）；顺带做覆盖率 |

**F1 的计算**：`(T2 的归一化分) − (T3 十个种子的均值)`，以及 `(T2) − (T0)`。
RAPP 的实测分差是 0.665（人设计）对 0.245（随机生成），阈值先取 **0.40** 死值，跑完再看要不要动。

### 5.3 变异清单

**该挂的，20 个**（每个标注预期被哪条判据抓到；一个变异只能有一个「主抓手」，否则说明判据冗余）：

| # | 变异 | 预期抓手 | 为什么别的层抓不到 |

### 5.4 判据与阈值（先定死，跑完不许回头调）

```
L0 执行门   未捕获异常数 > 0                              → fail
            600 帧后 rAF 回调计数 < 600                    → fail
            首 10 帧内无任何绘制调用                        → fail
L1 响应门   T1 与 T0 的状态指纹序列完全相同                  → fail
            键盘-only 轨迹与 T0 相同，或鼠标-only 与 T0 相同  → fail
            同一轨迹两次跑的指纹序列 SHA256 不等             → fail（判为 harness 问题，单列一桶）
            down→20 帧→up→20 帧 的后 20 帧位置增量 > 1 像素 → fail
L2 规则门   极端同向输入 1000 帧后挡板中心出界               → fail
            球的相邻帧位移线段穿过砖块或墙（采样 1 帧）        → fail
            T2 全程 HUD 数字从未严格递增                     → fail
            命数到 0 后 60 帧内未出现终局画面                 → fail
L3 退化门   第 500~600 帧的绘制调用数对帧号线性拟合斜率 > 0.5 → fail
            连续 120 帧状态指纹完全不变且非终局              → fail
            画布像素熵 < 阈值，或 HUD 与背景对比度 < 3:1      → fail
            同一帧渲两次像素差异 > 100 个像素                → fail
L4 完成门   T2 在 3 个种子里 0 次打完全部砖块                → fail
L5 平衡门   T0 的最终分数 > 0                               → fail（不动不该得分）
            T3 十个种子的分数均值 > T2 分数的 0.6 倍          → fail（乱按就能赢）
            T2 − T3均值 的归一化分差 < 0.40                  → fail（技能不可分辨）
            T3 十个种子的分数标准差 / 均值 > 2.0              → fail（方差爆炸）
```

三个阈值的来源要诚实标注：
`0.40` 来自 RAPP 的 0.665 对 0.245 取中间偏严；
`0.6 倍` 和 `2.0` 是**拍的**，没有文献依据，第一轮跑完必须报告它们离边界多远
（照 90_local_experiments §2.4「阈值是怎么定的，要打的折扣」那个口径）。

### 5.5 耗时推算

本机无 GPU，Chrome 无头 + SwiftShader。基准取自 3D 线实测：
**单次探测约 0.8~1.0 秒，含启动浏览器**（90_local_experiments §1.5）。
游戏任务的增量是步 600 帧。以下是**推算**，不是实测：

| 项 | 推算 | 依据 |
|---|---|---|
| 单条 600 帧轨迹（2D canvas，软渲染，无截图） | 约 1.0~2.0 秒 | 2D 填色比 3D 体素化便宜；主要成本是 600 次同步 `__vcStep` 往返 |
| 每帧都存指纹（绘制调用哈希 + HUD 解析） | 约 +0.3 秒 | 字符串哈希，廉价 |
| 像素哈希（每 10 帧一次，共 60 次 `toDataURL`） | 约 +1.5 秒 | 3D 线 9 视角截图约占单次探测的大头，按比例折算 |
| 浏览器启动 | 0.6 秒，**四条轨迹复用同一个浏览器实例** | 同上 |
| **单个变异的四条轨迹 + 双跑一致性自检（×2）** | **约 20~30 秒** | (1.0+0.3+1.5)×4×2 + 0.6；T3 的 10 个种子只跑 100 帧的短版，另加约 10 秒 |
| **30 个变异 + 1 个参考解，单进程** | **约 11~16 分钟** | — |
| 加上 §4.3 的跨机器自检（第 3 条） | ×2 | — |
| **一轮完整实验** | **约 25~35 分钟** | 可以一晚跑十几轮，阈值扫描完全负担得起 |

对比参照：A2Z 的三轴评测总共花了约 **900 墙钟小时**（10 台 m7i.4xlarge + 1 台工作站），
其中 playtest 占 56.8%、重放占 40.1%、源码检查只占 3.1%（附 C）。
**纯程序判据的成本优势是两到三个数量级**，这是它最被低估的一点。

### 5.6 这个实验能回答与不能回答什么

**能回答：**
1. R3（不读内部状态）的判别力有多少 —— 期望看到的曲线是「单条判据 10~15/30，分层组合接近 30/30」，
   和 3D 线的 12/29 → 29/29 同形。
2. 哪些子命题在不读内部状态时**结构性失明** —— 变异 13 就是故意种进去的那一个。
3. 双跑一致性在游戏任务上的真实通过率 —— 这是 §4 整节的唯一硬指标。
4. F 族（RAPP 式难度判据）在网页游戏上是否迁移得住 —— 公开文献里没有人做过这件事。

**不能回答：**
1. 阈值能不能迁移到别的游戏。这需要一个**留出被试**（照 3D 线的做法：第三个场景、18 个变异、阈值一个不动）。
   第一轮之后必须补一个贪吃蛇或 Flappy Bird 的留出集，否则 30/30 要打折扣。
2. 模型写的游戏是不是以同样的方式坏。手写变异是「我想到的坏法」，
   `90_local_experiments.md` §4 的结论是**盲区是被具体 case 逼出来的，不是设计阶段想出来的**，
   所以第二步必须是「让 LLM 提破坏 + 准入测试」。
3. 真实帧率与反应速度。虚拟时钟换来确定性的代价（PlaySuite 明确声明的那条）。
4. 好不好玩。见 §6。

## 6 结论：哪些能做成确定性 reward，哪些只能靠 agent，哪些只能靠人

### 6.1 三档分类

| 档 | 子命题 | 怎么做 | 噪声地板 | 成本 | 证据 |
|---|---|---|---|---|---|
| **甲 确定性 reward（24 条）** | A1~A4、B1~B5、C2、C3、C5、C6、C7、E1/E2/E4/E5/E6/E7、F1~F4（E3 与 C2 同） | 输入重放 + 确定时钟 + 状态差分（R3），辅以引擎钩子（R1）与绘制调用拦截（R2） | **0**（双跑逐字节一致） | 秒级；A2Z 的源码轴只占总成本 3.1% | 本项目 3D 线 47/47；RAPP 的技能分差 0.665 对 0.245 |
| **乙 需要 agent 真玩（6 条）** | C1、C4、D1、D2、D3、F5 | 脚本策略优先，碰不到的用**状态注入到前置条件**；真需要泛化时才用 GUI agent | 条目级 87.9%（人 91.4%）；judge 重判 8.8%~12.7% 会变 | 分钟到小时级；A2Z 的 playtest 占总成本 56.8% | A2Z 覆盖率 40.5%→48.5%（逐 agent 13.1%→88.0%）；PlaytestArena pass@20 0.82 对人 0.92 |
| **丙 只能靠人（3 条）** | F6 好不好玩、F7 审美、F8 创意 | pairwise + rubric 树，**每维设硬阈值不做加权求和** | 人与人 κ=0.68、α=0.624 | 贵 | PlaytestArena §6；CreativeGame 的 LLM 创意分一律 7/10 |

**关于「乙」的一个重要修正**：公开文献的共识是「要 agent 真玩」，
但 A2Z 的数据表明**真正起作用的不是 agent 会玩，是状态注入**：
在同样的第二遍预算下，再玩一遍正常游戏只加 0.5 个百分点的覆盖率，
换成对抗式注入加 8.0 个百分点（表 4c）；十个游戏的细粒度版本是 10.0% → 73.4%（附 G.4）。
而一个 milestone 式的在线游戏 agent 在同样十个游戏上的里程碑达成率只有 6.7%~26.7%。
**结论：先把钱花在「能把状态摆到任意位置」上，而不是「训一个会玩的 agent」上。**
这同时解释了为什么「乙」档的成本可以压下来 —— 大部分乙档条目用脚本策略 + 注入就够，
不需要一个真正的 GUI agent。

### 6.2 可落地优先级

**P0（先做，一周内能有数字）**

1. **扩 harness：`setTimeout`/`setInterval` 挂虚拟时钟 + Canvas2D 绘制调用拦截 + CDP 输入重放。**
   这三样是后面一切的前置。`fillText` 拦截这一条单独算是最高性价比的一项 ——
   它把 C1（分数会涨）从「需要 agent」降级成「纯程序判据」，而且不需要游戏配合。
2. **做 §5 的 Breakout 变异集（20 该挂 + 10 不该挂），阈值先定死再跑。**
   预期产出和 3D 线同形的那张表：单信号 10~15/30，分层组合接近 30/30。
3. **双跑一致性当硬准入门。** 任何过不了 SHA256 双跑一致的任务不进数据集。
   这一条比判别力更重要 —— 不确定的任务进了 RL 就是纯噪声，和
   `90_local_experiments.md` §5 那个「verifier 比问题描述知道得多」的坑同级。
4. **把 F 族（RAPP）实现出来。** 四个判据（技能分差、不动不赢、随机不满分、方差有界），
   总共不超过 100 行，公开文献里**没有任何游戏生成 benchmark 做过这件事**。

**P1（两到四周）**

5. **留出被试。** 第二个游戏（贪吃蛇或 Flappy Bird），18~20 个变异先写死标签再跑，阈值一个不动。
   没有这一步，P0 的 30/30 要打折扣。
6. **LLM 提破坏 + 准入测试**（照 `gen_tasks.py` 的三条：参考解自比自要过、破坏版必须被判挂、
   search 片段唯一）。被弃掉的 case 就是 verifier 的盲区报告。
7. **引擎钩子层**：three.js（已有）、PixiJS v8 的 `__PIXI_APP_INIT__`、Babylon 的 `EngineStore.Instances`。
   **Phaser 3 要自己实现构造函数劫持**，不能等现成钩子。
8. **逐输入通道验证（B2）**：键盘-only、鼠标-only、触摸-only 各一条轨迹。
   配 `Emulation.setTouchEmulationEnabled`。Gamepad 直接不支持，任务生成时就排除掉。

**P2（有了 P0/P1 的数字再决定）**

9. **脚本 playtest + 状态注入（乙档）**。注意 A2Z 的协议细节：
   注入只给前置条件不给期望效果，触发与效果必须由真实执行产生，注入要记备注。
   **不要**把注入面写进任务要求（那就退化成 R0），而要由 harness 从引擎钩子侧提供。
10. **VLM 只报事件不定生死。** 照 3JSBench 把 SigLIP2 标成「描述性信号，不改变判定」的做法，
    录屏 VLM 的输出进诊断，不进 reward。
    `90_local_experiments.md` §3.4 的结论在这里同样成立：
    **VLM 的价值是帮你找到该加哪条程序化检查**。
11. **丙档只在最后一道排序里用，且每维设硬阈值。**

### 6.3 和 3D 线的复用关系

| 组件 | 3D 线现状 | 游戏线需要的增量 |
|---|---|---|
| 断网 + 内存加载 | 已有 | 无 |
| 冻结时钟（rAF、`performance.now`、`Date.now`、`Math.random`） | 已有 | 补 `setTimeout`/`setInterval`；可选叠加 CDP 虚拟时间 |
| 引擎钩子抓场景 | three.js 已有 | 加 Pixi v8、Babylon；Phaser 要自己劫持构造函数 |
| 多视角渲染 + 剪影 + 体素 | 已有 | 游戏线用不上（2D），但 3D 网页游戏能直接复用 |
| 分层乘法门控 | 已有（L0~L3） | 加 L1 响应门、L4 完成门、L5 平衡门 |
| 带标签变异集 + 留出验阈值 | 已有（47/47，其中 18 个留出） | 照抄方法论，换被试 |
| 自动造题 + 准入测试 | 已有（`gen_tasks.py`） | 准入条件多一条：双跑一致 |
| 输入重放 | **没有** | 新建，是游戏线的核心新件 |
| 绘制调用拦截 | **没有** | 新建，2D 的 `fillText` 是最高性价比的一条 |
| RAPP 式难度判据 | **没有** | 新建，约 100 行 |

### 6.4 一句话

**「可玩性只能靠真玩验证」这个说法是错的 —— 对的说法是「可玩性不能只靠看源码和看截图验证」。**
三十三条子命题里，二十四条可以靠「同一份代码跑几条不同的输入轨迹然后比差异」做成零方差的确定性判据，
而这件事不需要游戏暴露任何接口、不需要一个会玩游戏的 agent、成本比 playtest 低两到三个数量级。
剩下六条的瓶颈不是判得准不准，是**验得到验不到**，解法是把状态摆到前置条件上而不是训一个更会玩的 agent。
真正只能靠人的，只有三条，而且它们在人与人之间的一致率本来就只有 κ=0.68。
