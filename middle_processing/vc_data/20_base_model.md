> 2026-10-15。补整个方案里唯一还空着的一环：**用什么底座**。
> 前面的任务构造、verifier、训练配方都已成稿，但从头到尾没有回答这个问题，不定它前面所有规划都悬空。
> 与 04（verifier）、05（轨迹修复）、06（harness）、08（RL 配方）配套，只写增量。
> 日期按 arXiv ID 推算。数字后面括号里是出处的表号或节号，URL 统一为 `https://arxiv.org/abs/<id>`。

## 0. 结论速览

**要不要视觉输入（§1）**

1. **要，不可替代。** 本项目核心任务（判断自己写的代码渲染出来对不对）落在「图是唯一信息源」档：
   ArtifactsBench 只给代码 **79.06** → 给图 **90.95**；
   SWE-bench Multimodal 的「图是必需的」子集，去掉图 **17.6 → 8.8（砍半）**，
   而「图主要是文字」的子集 **23.1 → 23.1（完全一样）**。
2. **但「让模型自己把截图描述成文字再推理」是负收益**，三篇独立复现：
   OpenCUA L3 **17.6 < L2 18.5**；ChartMimic 先 caption 再写码 **81.1 ≈ 直接 81.2**，
   而看自己渲染结果再改是 **84.8**。一句话：**看图有用，把图描述成文字没用。**
3. **最重要的一条推论**：Plot2Code 里纯文本 GPT-4（只给从参考代码抽出的精确描述）拿到 rating **7.36**，
   GPT-4V（图+文）**7.68** —— **纯文本拿到了多模态的 95.8%**。
   但那份描述是 **oracle**（从 ground truth 代码里抽的）。
   → **「把视觉信息精确地文本化」极其有价值，「让模型自己去文本化」毫无价值。**
   **本项目的 scene graph 属于前者 —— 它是程序从运行时状态直接读出来的，不经过模型。这是它的全部价值来源。**
4. **但 scene graph 替代不了全部视觉通道**：闭集语义的结构图单独用会严重欠载
   （GraphEQA：只给 3D 场景图 **13.6%** / 只给视觉 **45.7%** / 两者 **63.5%**），颜色等视觉属性会在转译中丢失（DePlot）。
   **必须两路交叉核对** —— 这与 04_verifier 自己实测的「按 API 名断言只能到 14/29」是同一个病。
5. **视觉输入不贵，比完整 a11y 树便宜一个数量级**：720p 图恒定 **1,196 token**，
   而 HTML / a11y 方案每次交互 **4,000 ~ 6,000 token**；Multimodal-Mind2Web 上视觉 **4,172** 对 HTML **91,163**。
   贵的是全分辨率长截图和多图同存。

**视觉编码器与分辨率（§2）**

6. **分辨率是第一旋钮，编码器规模不是。** MM1：224 → 336 分辨率值 **约 3%**，
   而 ViT-L → ViT-H 参数翻倍值 **不到 1%**。
   PaliGemma 2 在算力配平下更干净：3B 上 224→448（4.6× FLOPs）**DocVQA +33.7**，
   而 224² 上 3B→10B（3.7× FLOPs）只 **+4.0** —— **分辨率赢 8.4 倍**。
7. **但分辨率只对特定任务族有效，而且饱和点由「源图原生分辨率」决定，不由模型决定。**
   四条独立归因指向同一判据（Monkey：TextVQA 原图平均只有 950×811，所以 896² 就是顶；
   IXC2-4KHD：InfoVQA 约 50% 的图长边超 2000 px，所以到 8,737 token 仍不饱和）。
   **收益曲线 ≈ min(模型有效分辨率, 源图原生分辨率) 的函数。**
8. **所以前端长截图要按 InfoVQA / DocVQA 外推，不能按 TextVQA / ChartQA / OCRBench。**
   全页截图长边常 3,000 ~ 10,000 px，属于 InfoVQA 那一侧。
   **OCRBench 不适合做本场景的选型指标** —— 它的图太小，576 token 就见顶，放大反而掉分（828 → 786）。
9. **「文字不可读」是错的方向。** 文字是最早饱和、最不可训、最不区分模型的那一维：
   Design2Code Text 全模型极差只 **2.7 个点**、SFT+RL 只涨 **0.013**，而 Position 涨 **0.129**。
   真正的瓶颈是**大图上的元素召回**（Design2Code-HARD 漏 30~40% 的 block，DCGen **85.34% 的错误是漏元素**）**与布局层级**。
10. **像素预算要 ≳ 8M，而这一格很容易做错。** 实测：GLM-4.5V/4.1V 的面积上限 **9,633,792 px（12,288 token）**、
    Qwen2/2.5-VL **12,845,056（16,384 token）** —— **1280×6000 的全页截图（7.68M px）在两者默认下都不缩放，
    按原生 1280 px 宽进去，约 9,844 token**。
    而 UI-TARS（2.1M）/ ShowUI-README（1.05M）/ OS-Atlas（1.05M）/ Aguvis（0.94M）这些 GUI 专用权重
    **差 4 ~ 10 倍，会把宽度压到 448 ~ 672 px**。
    **只有四条路能让长截图的前端文字保持可读**：GLM/Qwen 原生（1280 px）、IXC2-4KHD HD-55（1008）、
    InternVL n_max≥18（896）、DeepSeek-VL2 mn≥18（737）；其余横向降采样 2.9 ~ 17.9 倍，
    **12 px 正文会落到 0.7 ~ 4.5 px**。
11. **堆分辨率必须配结构信号与压缩，否则白堆。**
    TextMonkey 896 → 1344 不压 token **反而 DocVQA −9.2**（冗余 token 占比 26.6% → 59.5%）；
    Molmo 的 crop 间重叠 4 个 patch 值 **+1.2**；IXC2 的行尾分隔符在**布局动态时**值 InfoVQA **+1.9**。
    projector 里**别用可学习 query**（DocOwl1.5 文本定位 **−10.6**），
    而且**合并方向要跟文字排布一致**（1×4 优于 2×2，72.8 对 71.8）。

**图像 token 预算（§3）**

12. **本节纠正成稿三处口径。** 最重要的一处：「多视角拼图比逐张发省 8 倍」**不是同口径** ——
    703 对 8,288 的像素比本身就是 12.0×，**省的几乎全是降分辨率，不是拼图**。
    同像素下拼图只省 **12.1%**（800 → 703），每格 512 时只省 **5.2%**。
    **想省 token 只有一条路：降分辨率。而降分辨率会直接伤 OCR。**
13. **本节最重要的发现：token 上限不是成本问题，是可读性问题。**
    1440×8000 的整页长图在 Claude 标准档**只要 616 token —— 比 1440×900 的 1,550 还便宜**，
    因为它被缩成了 **282 px 宽**（宽度保真 20%）。
    纵向切 9 片要 13,950 token（贵 22.6 倍），但宽度保真到 **96%**。
    → **「给模型一张整页截图」这种最自然的做法，既最便宜又几乎什么都看不清，而且账单上看不出异常。**
14. **成稿的「图像只占累计输入 8%」要加限定**：它对应最便宜也最看不清文字的那一档。
    换成能看清文字的配置，图像占 **16%**（滑窗 3 张整页截图）到 **36%**（切片）。

**上下文长度（§4）**

15. **32K 是下限，64K 够用，128K 是余量；不要为 256K 付溢价。**
    SWE-Gym 成功轨迹 token 中位数 **16K**、95 分位 **39.5K**；单轮峰值 30~65K。
    而 CompactionRL 实测：**真给 160K 窗口（59.5）和给 80K 加压缩（59.8）完全打平。**
16. **上下文管理第一选择是 observation masking，不是 LLM 摘要。**
    SWE-agent：只留最近 5 条 observation 比完整历史 **高 3.0 个百分点**（不是省钱，是提分）；
    Complexity Trap：5 组里 4 组 masking 成本最低且不输摘要。摘要自己还要钱（占总成本最高 7.2%）。
17. **多图是最早崩的那条轴，而且它比文本上下文更紧。**
    MM-NIAH：图针检索 **22.4** 对文针 **88.4**（而这是四选一的单选题，原文说「可能差于随机猜测」）；
    Visual Haystacks：**开源 8B 级 VLM 在 20 ~ 50 张图就崩到随机水平**。
    → **「滑窗 3 张」不只是省 token，是在安全区内。一条 40 步轨迹每步留图就是 40 张，正落在崩溃区。**
18. **「LLM 的长上下文能力不传给 VLM」**：InternLM2-20B 在纯文本 200K 上下文里近乎完美找针，
    而同底座的 InternVL-1.5 **超过 32K 就显著下滑**。
    → **选底座时「文本上下文 128K」这个指标对多模态几乎无参考价值。**

**规模与稀疏（§5）**

19. **这条线的主流落点是 7B ~ 9B 稠密，或 16 ~ 30B 总参 / 3B 激活的 MoE。**
    UI2Code^N（最接近的参照）就是 9B 稠密。
    **视觉编码器规模几乎不随 LLM 规模走** —— Qwen2-VL 的 675M ViT 在 2B 和 72B 上完全一样。
20. **视觉能力对规模的敏感度确实与文本推理不同，但是「位置依赖」而非「能力类型依赖」。**
    Cambrian-1（整条视觉栈固定，只换 LLM）：LLM 放大 4.25 倍，**OCR 与图表维度只 +0.6**，知识维度 +5.7。
    **但必须同时引一条反驳**：Cambrian-1 §3.1 自己指出 MMMU / MathVista / AI2D
    **开关视觉输入的差距不到 5%**，说明「推理更吃规模」有一部分是 benchmark 在量 LLM 而非多模态能力。
21. **MoE 要按激活量对标稠密，不要按总参数。**
    InternVL3.5-20B-A4B 的推理分 **56.0，低于 14B 稠密的 62.0**，甚至低于 8B 稠密的 60.3。
22. **「固定算力下更大底座 vs 更好数据和 verifier」没有公开的直接对照实验。**
    最接近的两边：ScaleRL 换规模（8B → 17B×16 MoE）渐近性能 **0.610 → 0.710**，
    而在 8B 上拉满 RL 超参只到 **0.645** —— 换规模约为换超参的 3 倍；
    但在视觉编码这个具体任务上，**固定 9B 基座的数据管线值 +79.6 分**（Design2Code 9.0 → 88.6），
    而同族放大 10 倍只值 **+12.8 ~ +14.7**。
23. **RL 不扩展探索边界，蒸馏才扩展。** Qwen3：RL 后 pass@64 **一点没动**（90.0 → 90.0），
    蒸馏 90.0 → 93.3；且蒸馏只花 **1,800 GPU 小时**对 RL 的 **17,920**。
    → **选底座时这条比任何 benchmark 分数都重要：如果底座的 pass@k 里根本没有正确答案，RL 救不回来。**

**选型（§6）**

24. **一句话配置（推断）**：**9B 级原生分辨率多模态稠密底座，64K 文本上下文，
    当前视口一张 1440×900（约 1,550 token）、历史滑窗 3 张低分辨率，
    单条轨迹视觉 token 上限 10 万，observation masking N=5，
    scene graph 走摘要而非转储、与视觉通道交叉核对。**
25. **三个必须先做的实验**（都是半天到一天）：
    ① 渲染图的多图崩溃点（**所有多图数字都来自自然图 benchmark，没有一条在渲染图上测过**）；
    ② 长截图的有效宽度；
    ③ **OCR 分数与 image-to-code 分数的相关性 —— 零成本，不需要 GPU，而且截至 2026-10 没有任何公开工作做过。**

# 1. 要不要视觉输入，值多少

## 1.0 先给结论：价值取决于「那条文本通道对任务是否信息完备」

公开证据不是「视觉有用 / 没用」的二分，而是**五档**，而且档与档之间差一个数量级。

| 形态 | 视觉输入的净价值 | 代表数字 |
|---|---|---|
| **A. 让模型先把截图描述成文字，再决策或写码** | **≈ 0 或负** | OpenCUA L3 **17.6 < L2 18.5**；ChartMimic 先 caption 再写码 **81.1 ≈ 直接 81.2** |
| **B. 用 caption 替代图** | **恢复一半左右** | VWA 7.25 → 12.75 → 15.05；ArtifactsBench 79.06 → **81.74** 对真图 **90.95** |
| **C. 用精确结构化文本（DOM / 表 / 坐标 / 关系）替代图** | **经常反超图** | SeeAct HTML 候选 **39.1** 对 SoM 截图 **20.3**；SpatialEval 0.555 对 0.237；DePlot 38.2 → **67.6** |
| **D. 图作为补充通道，加在结构化文本之上** | **弱正，常在噪声内** | WorkArena **42.7 → 41.8（−0.9）**、WebArena 23.5 → 24.0、MiniWoB 66.1 → 67.7 |
| **E. 图是唯一信息源（渲染结果、日历控件、视觉崩坏）** | **强正** | WebVoyager Booking **2.3 → 43.2**、Flights **7.1 → 59.5**；ArtifactsBench 79.06 → **90.95** |

**本项目的任务**（判断自己写的 three.js / 前端代码渲染出来对不对）**落在 E**，
而**它的辅助通道（scene graph / DOM）落在 C**。两者都要，而且 A 必须避开。

## 1.1 A 档：「先描述再推理」是负收益，三篇独立复现

### 1.1.1 OpenCUA 的 L1/L2/L3（成稿引过，这里给准确数字）

OpenCUA（2508.09123）定义：**L1** = Action；**L2** = Thought + Action；
**L3** = **Observation**（先描述截图里的显著视觉与文本元素）+ Thought + Action。

表 6（OSWorld，**15 步**，temperature 0）：

| 消融组 | 设置 | SR (%) |
|---|---|---|
| **推理格式**（推理时） | L1（Action） | 16.9 |
| | **L2（Thought+Action）** | **18.5** |
| | **L3（Observation+Thought+Action）** | **17.6** |
| **训练数据的 CoT 混合** | **只训 L2 数据** | **13.1** |
| | Mixture-CoT（L1+L2+L3 混训） | **18.5** |
| 反思式长 CoT | Short-CoT（退化成 Aguvis 式） | 11.5 |
| | Advanced-CoT（带反思） | 15.3 |

原文对 L3 落败的归因（§5）：

> **当模型描述截图里的信息时，往往会描述出大量与任务或下一步动作无关的元素，这可能把模型带偏。**

**成稿里的说法要补两个限定**：
1. **13.1 不是「只用 L2 推理」，而是「训练数据只用 L2、不混 L1/L3」**。推理格式与训练数据是两个不同的消融组。
2. OpenCUA 说自己的「L2 > L1」结论和前人相反、并引 Aguvis 为据，
   **但 Aguvis 原文（2412.04454）不存在 L1/L2 这种分级记号，也没有分层数字对照**，只有「有/无 inner monologue」的二值消融
   （去掉后 ScreenSpot 84.4 → 79.3、AndroidControl Low 80.5 → 69.1、High 61.5 → 60.3）。
   引用这句时要标明是 OpenCUA 的转述。
3. 1/3/5 张历史截图的**具体分数只在图 10 里，HTML 正文没有数值**。
   能引的是原文文字：「从 1 张到多张**显著提升**；从 3 张到 5 张**只有边际收益，却多约 3K 上下文 token 并延迟收敛**」，
   以及「同样 3 图下，L2 历史**没有收益，还可能引入幻觉分散注意力**」，最终默认 **L1 CoT + 3 图**。

### 1.1.2 同一机制在 chart 域的独立复现 —— 而且自带对照

ChartMimic（2406.09961 表 5，GPT-4o Overall）：

| 方法 | 分数 |
|---|---|
| Direct（直接给图写码） | **81.2** |
| **HintEnhanced（先生成 caption 再写码）** | **81.1** |
| **SelfReflection（看自己渲染出的结果再改）** | **84.8** |

**这一组是整份调研里最干净的一句话**：
**「看图有用（+3.6），把图描述成文字没用（−0.1）。」**
原文归因：「HintEnhanced 方法先生成 caption，**可能引入幻觉，从而导致后续生成的代码出错**」。

### 1.1.3 第三例：Flame 的「先解释再写码」

Flame（2503.01619）pass@1 / pass@3 / pass@5，加上「interpretation-before-coding」后：

| 风格 | 原始 | 加「先解释」 |
|---|---|---|
| Evo | 43.8 / 62.9 / 69.1 | 44.6 / 68.1 / 75.8 |
| Waterfall | 52.6 / 65.5 / 70.3 | **50.2** / 67.7 / 74.2 |
| Additive | 51.6 / 67.0 / 71.9 | **43.5** / 63.9 / 70.2 |

**pass@1 三分之二变差，pass@3/5 三分之二变好**（原文解释为「更有效地探索解空间」）。
→ 「先解释」不是提升单次质量，而是**增加多样性**。如果用在 best-of-N 里有价值，用在单次生成里是负收益。

### 1.1.4 一个必须区分的「看起来像 A 但不是 A」的做法

UI2Code^N（2511.08195 表 12）的 Think 阶段：**With Think 88.6 对 Without Think 85.5（+3.1）**。
但它的 Think 是**结构规划**（识别 header / main 等布局区、规划 DOM 层级，原文说目的是
「reduce layout hallucination」），**不是逐元素描述截图**。

→ **分叉点很清楚：规划「要写成什么结构」有用（+3.1），描述「图里有什么」没用（−0.1 到 −0.9）。**
本项目的 prompt 模板要按这条写：**允许并鼓励结构规划，禁止逐元素视觉转写**。

## 1.2 B 档：caption 恢复一半，补不满

### 1.2.1 VisualWebArena（2401.13649 表 3，核实通过）

| 类别 | 模型 | Overall SR (%) |
|---|---|---|
| Text-only（仅 a11y 树） | **GPT-4** | **7.25** |
| Caption-augmented（a11y 树 + BLIP-2 caption） | **GPT-4** | **12.75** |
| Multimodal（图 + caption + a11y 树） | **GPT-4V** | **15.05** |
| Multimodal + SoM | **GPT-4V** | **16.37** |
| 人类 | — | **88.70** |

**按视觉难度分解（附录 C.2，图 6）—— 这张分解比主表更有用**：

| 视觉难度 | GPT-4 纯文本 | GPT-4 + caption | GPT-4V + SoM |
|---|---|---|---|
| Easy | 9.0% | 16.9% | 21.4% |
| Medium | 7.3% | 12.2% | 14.3% |
| **Hard** | **4.8%** | **8.0%** | **12.4%** |

**读法**：caption 把差距补了约 **70%**（7.25 → 12.75，真图 15.05），
但在**视觉难度 Hard** 的子集上只补了 **41%**（4.8 → 8.0，真图 12.4）。
**视觉越关键，caption 越补不上。**

OCR 子集（§6.1，GPT-4V + SoM）：需要 OCR **13.4%** 对不需要 **16.9%** —— OCR 是瓶颈；
需要精确图像匹配 **18.9%** 对其他 16.2% —— **不是**瓶颈。

## 1.3 C 档：精确结构化文本经常反超图（本项目最关心的一格）

### 1.3.1 两个最强的单点

**SeeAct（2401.01614 表 3）**，同一个 GPT-4V，只换「怎么指认要操作的元素」：

| grounding 方式 | Cross-Task | Cross-Website | Cross-Domain |
|---|---|---|---|
| Attribute（元素属性） | 16.1 | 12.1 | 19.0 |
| **Annotation（SoM 图像标注）** | **20.3** | **13.9** | **23.7** |
| **Choice（HTML 文本候选项）** | **39.1** | **32.7** | **42.0** |
| Oracle（人工指认） | 61.9 | 65.0 | 62.1 |

**HTML 文本候选是 SoM 截图的近 2 倍。**
错因分析（§4.3）：100 条「动作对但 grounding 错」的采样里，**54% 是视觉幻觉**（凭空编 bbox / label），
**46% 是 bbox 与 label 连错**。

同篇还有一条更狠的（表 2，SFT 组）：
**FLAN-T5-XL（纯文本）53.5 / 41.1 / 38.9** 对 **BLIP-2-T5-XL（同底座 + 视觉）47.0 / 37.0 / 38.9** ——
**加视觉编码器全线不涨甚至倒退**。原文：「微调后的 BLIP-2-T5 相对 FLAN-T5 没有显著增益，尽管它有额外的视觉输入」。

**SpatialEval（2406.14852）**，而且它的文本不是 caption，**是精确结构化描述**
（Spatial-Map 用成对关系「X 在 Y 的东南方」，Maze-Nav 用 **ASCII 迷宫**，Spatial-Grid 用网格文本）——
**正好是本项目 scene graph 的形态**：

| 模型 | Spatial-Map 文本 / 图 | Spatial-Grid 文本 / 图 |
|---|---|---|
| GPT-4V | **0.555 / 0.237**（2.3 倍） | **0.923 / 0.668** |
| Claude 3 Opus | 0.619 / 0.348 | **0.957 / 0.455**（2.1 倍） |
| GPT-4o | 0.616 / 0.617 | 0.986 / 0.833 |

**更极端的一组（§4.1，标题就叫「Seeing Without Understanding」）**：
在「图 + 文」设定下把原图换成 ① 无图 ② 高斯噪声图 ③ 随机不匹配图：

> **在缺少视觉输入时，VLM 在空间推理任务上的表现反而更好**（图 8）
> **把原图换成高斯噪声图，在多种 VLM 架构上都提升了性能**（图 9）
> 在 Maze-Nav 上，**把原图换成随机图也带来提升**（图 10）

原文把机制说得很直白：

> 当前已知的 VLM 架构试图把视觉输入「**翻译**」到语言空间，所有推理随后都在语言域里进行。
> 这条**自动翻译路径比人类提供的文本翻译更差**，这是合乎逻辑的 —— 正如我们的纯文本设定所示。
> 因此我们的工作展示了**翻译式方法的极限**。

（图 8/9/10 的逐模型数值只在图里，可引结论不可引数。）

### 1.3.2 成本：图比结构化文本**便宜**，这和直觉相反

| 口径 | 结构化文本 | 图像 | 出处 |
|---|---|---|---|
| 每次交互 | HTML / a11y 方案 **约 4,000 ~ 6,000 token** | 720p 图 **恒定 1,196 token** | Aguvis 2412.04454 §2.2、§4.4 |
| 端到端效果 | — | 对 GPT-4o 在 Mind2Web-Live 上**成本降 93%、每步输入 token 降 70%** | 同上 |
| Multimodal-Mind2Web 平均 | **HTML 91,163 ~ 128,827 token** | 视觉 **4,172 ~ 4,653 token** | SeeAct 2401.01614 表 1 |
| ServiceNow 页面 | 扁平 HTML **40K ~ 500K token**（已做基础清洗） | — | WorkArena 2403.07718 §3.2 |

**所以「视觉输入很贵」这个前提在 agent 场景是错的** ——
一张图比一棵完整的 a11y 树便宜一个数量级。
贵的是**全分辨率的长截图**（见 §3.2）和**多张图同时在上下文里**（见 §4.1.7）。

**对本项目的含义**：如果 scene graph 做得很啰嗦（把每个物体的全部属性都列出来），
它可能比截图还贵。**scene graph 必须是「摘要」而不是「转储」** ——
这与 §3.3 的敏感性分析一致（每步文本观察从 300 涨到 1,200 token，累计输入从 1.16M 涨到 1.87M）。

### 1.3.3 文本表征的格式工程，收益比加视觉模态大一个数量级

### 1.3.4 但是：结构化表示会在三个地方系统性失效

这是本节必须给的反面，否则会把 scene graph 用过头。

| 失效模式 | 证据 | 数字 |
|---|---|---|
| **闭集语义的结构图单独用会严重欠载** | GraphEQA（2412.14480 表 2）：3D 语义场景图 vs 视觉记忆 vs 两者 | **只给 3DSG 文本 13.6%** / **只给视觉记忆 45.7%** / **两者 63.5%**（成功率）。规划步数 8.8 / 1.0 / 5.1；轨迹长 33.0 / 3.9 / 12.6 米 |
| **图→表的转译会丢掉颜色等视觉属性** | DePlot 2212.10505 表 7，标题就是「DePlot+LLM 在与**视觉属性如颜色（在图转表时丢失）**相关的 query 上吃力」 | 同篇在 PlotQA 上 **66.6 对端到端 MatCha 的 91.5**，完全反转 |
| **a11y 树对视觉控件不完备** | WebVoyager 2401.13919 表 1，同 GPT-4V 栈，纯文本 vs 截图+SoM | Overall **40.1 → 59.1**；Booking **2.3 → 43.2**、Google Flights **7.1 → 59.5**、Coursera 23.8 → 73.8 |

**GraphEQA 那一行对本项目是个警告**，因为我们的方案很依赖 scene graph。
原文归因：

> GraphEQA-SG 成功率更低……因为它只把 3DSG 作为文本输入给 VLM planner，
> 这表明**用闭集语义构建、且没有任何任务相关语义增强的语义场景图，
> 会提供不完整、不充分的环境理解**。

**caveat**：GraphEQA-SG / Vis 不是纯粹的模态互换 —— Vis 版同时把探索策略换成了随机 frontier exploration。
但 13.6 对 45.7 对 63.5 的量级差距仍然说明：**闭集、无任务增强的结构图单独用会欠载。**

**这正好对上 04_verifier 自己的实测**（draft_verifier §29）：
「按 API 名字断言场景里有几个球几个圆柱只能到 14/29，因为它查的是实现路径而不是结果」。
→ **scene graph 的「闭集语义」问题我们已经踩到过了。** 对策也是同一条：
**结构化断言要查结果（几何、包围盒、颜色）而不是查 API 名，并且必须与视觉通道交叉核对。**

### 1.3.5 这一格的结论可以这样下

**精确结构化表示能否替代截图，取决于该表示对任务是否「信息完备」。**

| 任务 | 结构化通道是否完备 | 谁赢 |
|---|---|---|
| 点哪个按钮、填哪个表单 | DOM / a11y 树**完备** | **文本赢**（SeeAct 39.1 对 20.3；AgentOccam 43.1） |
| 日历组件怎么交互 | **不完备** | **图赢**（WebVoyager Booking 2.3 → 43.2） |
| 渲染出来好不好看、有没有视觉崩坏 | **不完备** | **图赢**（ArtifactsBench 79.06 → 90.95） |
| 图表里「红色那条线」是什么 | 转表后**颜色丢失** | **图赢**（DePlot 表 7） |
| 场景里有几个物体、相对位置、尺寸比例 | scene graph **完备**（如果查几何而非 API 名） | **文本赢**（SpatialEval 0.555 对 0.237） |

### 1.5.2 Plot2Code：唯一的生成侧纯文本臂

设定（§3.2）：**Direct** = 只给图；**Conditional** = 给图 + 文字指令，
**而指令是 GPT-4 从 ground-truth 代码里抽出来的**（平均 279 ± 115 token），**对纯 LLM 只给指令不给图**。

表 3（132 个 matplotlib 图，Pass / Text-Match / Rating）：

| 模型 | 模态 | Direct | **Conditional** |
|---|---|---|---|
| **GPT-4** | **纯文本（只给指令，无图）** | — | 80.3 / 68.0 / **7.36** |
| **GPT-4V** | 图 + 文 | 84.1 / 57.7 / 6.48 | 81.8 / 70.7 / **7.68** |
| GPT-4V (PS+) | 图 + 文 | 86.4 / 55.3 / 6.25 | 85.6 / 71.4 / **7.83** |
| ChatGPT | 纯文本 | — | 80.3 / 56.7 / 6.59 |
| Claude-3-Opus | 图 + 文 | 84.1 / 57.5 / 4.37 | 78.0 / 69.7 / 7.68 |

**三个读数**
1. **图的边际价值很小**：同基座 GPT-4 对 GPT-4V，Conditional 下 rating **7.36 → 7.68（+0.32）**，
   即**纯文本拿到了多模态的 95.8%**。
2. **「只有图」反而输给「只有精确文字描述」**：GPT-4V 只给图 rating **6.48 < GPT-4 纯文本 7.36**。
3. **最大的口径坑**：这份文字描述是**从 ground-truth 代码里抽的 oracle**，不是模型自己看图描述出来的。
   所以 7.36 是「截图 → 描述」管线的**上界**，不是它的实际水平。
   **真实的「自己描述」版本就是 ChartMimic 的 HintEnhanced：81.2 → 81.1，白做。**

→ **这两条合起来就是本节最重要的推论**：
**「把视觉信息精确地文本化」极其有价值（拿到 95.8%），但「让模型自己去文本化」毫无价值。**
差别在于前者是 oracle，后者要经过那条「翻译路径」（SpatialEval 指出的极限）。
**本项目的 scene graph 属于前者 —— 它是程序从运行时状态直接读出来的，不经过模型。这是它的全部价值来源。**

|---|---|---|---|---|
| DCGen（agent 管线） | 69.6 | 45.0 | 约 137 s | 约 7,600 |
| ScreenCoder（agent 管线） | 85.7 | 80.0 | 约 66 s | 约 4,600 |
| **UI2Code^N-RL（端到端 9B）** | **86.1** | **88.6** | **约 40 s** | **约 2,600** |

原文：「基于 agent 的系统更容易受**误差传播**影响」，端到端「token 少 2~3 倍」。

→ **对本项目的判断**：外挂工具路线的证据是混乱的（Claude 上负收益、GAIA 的增益混淆于搜索工具），
而端到端原生多模态在 image-to-code 上**同时更准、更快、更省 token**。
**这一条支持「选原生多模态底座」而不是「纯文本底座 + 外挂视觉」。**

## 1.7 本节对选型的结论

| 判断 | 结论 | 置信度 |
|---|---|---|
| **要不要原生视觉输入** | **要。** 本项目的核心任务（判断自己的渲染结果）落在 E 档，图是唯一信息源：ArtifactsBench 79.06 → 90.95、SWE-bench M「图必需」子集 17.6 → 8.8 | **高** |

# 2. 视觉编码器与分辨率

## 2.0 本节的核心判断

前端截图的分布特征是：**高分辨率、长条形（1:3 到 1:10）、文字密集**。把现有消融按「源图原生分辨率」分层后：

> **① 分辨率是第一旋钮，编码器规模不是。**
> **② 但饱和点由「源图原生分辨率」决定，不由模型决定** —— 所以前端长截图要按 **InfoVQA / DocVQA** 外推，
> 不能按 TextVQA / ChartQA / **OCRBench**（这三个的源图都太小，早早饱和）。
> **③ 长宽比的处理方式（原生 vs 切块）比分辨率数值更能区分模型** —— 这是本节最大的发现。
> **④ 不要把钱花在 OCR 能力上** —— 文字是最早饱和、最不可训、最不区分模型的那一维。

### 2.1.1 MM1 的原始排序

MM1（2403.09611 表 1，固定 2.9B LLM）的「Encoder Lesson」逐字：

> **图像分辨率影响最大，其次是模型规模与训练数据构成。**
> 224 → 336 所有指标提升**约 3%**；ViT-L → ViT-H（**参数翻倍**）通常提升**不到 1%**；
> 加 VeCap-300M 在 few-shot 上提升 1% 以上。

§1 的总排序：「重要性依次是**图像分辨率、视觉编码器的 loss 与容量、视觉编码器的预训练数据**。
但令人意外的是，我们**几乎没有找到证据表明「视觉数据如何喂进 LLM」这个架构选择有影响**。」

**饱和点**（§5.1 图 7b，扫 224 ~ 1792）：「相对 336 基线，支持 1344×1344 可获得 **15% 相对提升**；
**而最大的 1792×1792 平均性能略有下降**，可能因为很多评测图本身小于该分辨率，resize artifact 影响性能。」
→ 饱和点落在 **1344 ~ 1792** 之间。（逐点数值只在图里，未核实。）

还有一条与「解冻编码器」交互的发现（§C.4）：
**低分辨率下冻结编码器更好（+2.2）；1344 px（有子图分解）下解冻更好（+2.9）。**
归因是「预训练是在基础分辨率下做的，没有插值或图像再分割」。
Eagle（2408.15998 表 9）独立复现了这个方向性反转：336 冻结 → 336 解冻，**OCRBench 354 → 305、ChartQA 42.1 → 24.5**。

### 2.2.2 真正的分水岭：候选集型 / 约束型 / 无块型

比「切不切块」更根本的是**长宽比是怎么被处理的**。三种结构，决定了「候选集能表达的最大长宽比」：

| 类型 | 规则 | 代表 | **可表达的最大长宽比** |
|---|---|---|---|
| **候选集型** | 从离散集合里挑最近的那个网格 | LLaVA-NeXT（7 个候选）**1:4**；LLaVA-OneVision **1:6**；Idefics3 **1:5**；DeepSeek-VL2 mn≤9 ⇒ **1:9**（评 InfoVQA 时特批放宽到 **1:18**）；InternVL n_max=12 ⇒ **1:12**，n_max=24 ⇒ 1:24 | **被 n_max 卡死** |
| **约束型 / 自适应型** | 把长宽比当**约束**而不是待匹配项 | **IXC2-4KHD**：`p_w·p_h ≤ H` 且 `p_h = ⌈p_w·h/w⌉`，严格保原比例；**LLaVA-UHD**：各块尺寸可变，不 pad 不拉伸 | **无上限（保真）** |
| **无块型** | 根本不产生「块间碎片」 | Qwen2-VL / Qwen2.5-VL / Pixtral / MoonViT / Ovis2.5（2D-RoPE + packing）；CogAgent（cross-module，但**硬 resize 成正方，对长图不可用**） | 原生保真 |

**对本项目的直接后果**：
一个「支持 7,290 视觉 token」的候选集型模型（LLaVA-OneVision），在 1:4.7 的图上**只能给到 384 px 宽**；
而一个只用 3,035 token 的约束型模型（IXC2 HD-25）能给到 672 px。
**候选集的比例粒度比 token 上限更关键。**

**一个值得注意的声明**：GLM-4.1V / 4.5V / 4.6V（2507.01006 §2.1，用 AIMv2-Huge + 每层 2D-RoPE +
原绝对嵌入 bicubic 插值）在论文里**明确声称支持「超过 200:1 的极端长宽比」与「4K 以上」** ——
这是全部文献里最激进的声明。
**而 UI2Code^N 的基座正是 GLM-4.1V-9B-Base**（§5.1.1）。
⚠️ 但该论文**未公开 max_pixels**（只给 seq len 32,768 / 131,072），所以 §2.4 的面积封顶陷阱**无法排除**。
**这是选型前必须查的一个硬参数**（查 `zai-org/GLM-4.5V` 的 `preprocessor_config.json`）。

两条编码器自己的「插值不够用」表态，方向一致：
- **Kimi-VL / MoonViT**（2504.07491 §2）：插值原绝对嵌入「随分辨率升高**越来越不够用**」，所以要加 2D-RoPE。
- **Ovis2.5**（2508.11737 §2）：**P1 阶段关 RoPE、只用动态插值；P2 才打开 RoPE** —— 隐含结论是插值单独不够。
- **Pixtral**（2410.07073 §2.2）：明确说学习式绝对嵌入「插值往往要付性能代价」，
  所以用 RoPE-2D，并**在行间插 `[IMAGE BREAK]` 以区分同面积不同长宽比**。

### 2.2.3 一个直接针对长截图的实测：GPT-4V 在切块重叠区会重复计数

**LLaVA-UHD（2403.11703 §2）** 做了一组很漂亮的探针，结论对「送长截图」是直接的警告。

前提：GPT-4V 的 high 模式按 `⌈W/512⌉ × ⌈H/512⌉` 切 512² 的 slice，
**而当分辨率不能被 512 整除时，切块之间存在重叠**，且**重叠量在不同分辨率下不一致**。

实验：合成图里放 **4 个圆**（GT = 4），prompt 固定不变，**只改圆的位置**；
用 `{红, 绿, 白} × {圆, 三角, 方}` 共 9 组控鲁棒性；每个实例查 15 次。

回答分布：

| 回答 | 占比 | 相对 GT=4 |
|---|---|---|
| **4（正确）** | **66.1%** | ×1 |
| 5 | 16.6% | 接近 |
| 3 | 10.2% | 接近 |
| **8** | **5.2%** | **×2（两块重叠区被数了两次）** |
| **16** | **1.9%** | **×4（四块重叠区被数了四次）** |

热力图的 pattern **以 256×256 的方格为界被切开**（256 正是 512 步长的一半）：
**中央方格给出最高的回答数，四个角最接近 ground truth** —— 因为角上只属于一块。

扫分辨率还出现明显相变：Phase 1 多数正确（没有切块）；
**Phase 2 以「12」绝对主导**（每个 slice 里出现了不完整的圆）；Phase 3 是 9 / 12 / 16 混合。

**§2.3 的总结论最适合直接引用**：

> 无论是 GPT-4V 这样强大的闭源 LMM，还是开源的 LLaVA-1.5，
> **在其底层视觉编码策略上都存在系统性的正确性问题**。
> **padding、形变式 resize、以及重复切块等常见做法，会导致计算浪费、模型能力损失，甚至对对抗攻击的脆弱性。**

同篇还有一个 padding 对抗的探针：
合成图四周用**灰色**包围（正是 LLaVA-1.5 padding 所用的 RGB 值），问「最左/右/上/下区域是什么颜色」——
**LLaVA-1.5 忽略灰色输入区域（把它们当作 padding），忠实回答中央矩形的颜色**。
机制句：「padding 的另一个问题是，**模型本质上无法知道这些类 padding 的像素是来自图像预处理，
还是原始输入图像的真实组成部分**。」

→ **对本项目有两条可操作的含义**：
1. **我们的 verifier 里有「数物体个数」这类断言**（04_verifier 的场景图断言）。
   如果让 VLM 去数，**在切块重叠区会系统性多数** —— 这是 §1.3.4「程序化断言为主」的又一条独立理由。
2. **不要在渲染图周围加纯色留白**（三维场景的转台图很容易这样），模型可能把它当 padding 直接忽略。

作者自己留的余地：「除视觉编码策略外，模型行为也受累积的训练动态和 RLHF 影响，
**因此翻倍/翻四倍效应并不主导结果**」。Fig.3 左的具体攻击成功率只在图里（未核实）。

### 2.2.4 逐编码器横评：三条硬结论

#### 结论一：没有语言监督的编码器在文字上是瞎的，加分辨率也救不回来

Cambrian-1（2406.16860 表 14，1.2M adapter + 737K IT，**冻结** encoder）：

| 编码器 | 架构@分辨率 | **OCRBench** | **DocVQA** | ChartQA | Avg |
|---|---|---|---|---|---|
| **SigLIP** | ViT-SO400M/14@384 | **37.20** | **40.19** | 43.76 | **53.91** |
| **OpenCLIP** | ConvNeXt-XXL@1024 | 28.00 | **48.11** | **48.00** | 52.18 |
| **OpenCLIP** | ConvNeXt-L@**1024** | 25.50 | **44.13** | **46.08** | 51.00 |
| OpenCLIP | ConvNeXt-L@**512** | 28.00 | 28.41 | 34.40 | 49.16 |
| DFN-CLIP | ViT-H/14@378 | 30.60 | 31.69 | 41.08 | 51.17 |
| OpenAI CLIP | ViT-L/14@336 | 30.90 | 32.11 | 37.84 | 50.49 |
| **DINOv2** | ViT-L/14@336 | **3.30** | **11.79** | 16.44 | 41.85 |
| **SAM** | ViT-H/16@**1024** | **2.50** | **8.98** | 15.68 | 32.54 |

→ **高分辨率 + 无语言监督 = 对文字完全无用。** 这条排除了「拿 SAM / DINOv2 当高分辨率编码器」的想法。

原文归因（§3.4）：「我们推测这是因为 CLIP 的训练数据（如 LAION）**包含大量 OCR 和文字密集数据**，
而 SSL 和其他视觉模型主要在自然图上训练、文字内容少得多。」

**同一编码器家族只改分辨率**（ConvNeXt-L 512 → 1024）：**DocVQA +15.72、ChartQA +11.68、TextVQA +3.78**，
代价是 MMVP −0.66、MMBench 从 60.60 塌到 58.21。
**Finding 5**：「高分辨率编码器大幅提升 chart 与 vision-centric benchmark，
而**基于卷积的架构天生适合这类任务**。」

#### 结论二：专用编码器是「单维度冠军、通用能力废」

Eagle（2408.15998 表 10，**都给 1024 token / 1024² 输入**，这是本调研里最干净的编码器横评）：

| 类别 | 编码器 | 解冻 | **OCRBench** | **DocVQA** | **GQA** | **SEED** | Avg |
|---|---|---|---|---|---|---|---|
| **VL 对齐** | **ConvNeXt** | ✓ | **518** | **77.9** | 63.3 | 72.9 | **659.7** |
| **文字识别专用** | **Pix2Struct** | ✓ | **472** | **72.5** | **54.9** | **55.1** | 584.8 |
| 目标检测 | EVA-02 | ✓ | 358 | 57.1 | 64.3 | 72.7 | 614.4 |
| 自监督 | DINOv2 | ✓ | **45** | **20.4** | 64.2 | 71.8 | 518.0 |
| 分割 | SAM | ✓ | **35** | **21.2** | 60.2 | 65.9 | 494.7 |

**Pix2Struct（OCR 预训练）的 OCRBench 472 / DocVQA 72.5 很强，但 GQA 塌到 54.9、SEED 塌到 55.1。**
原文归因（§2.3）：「仅在视觉任务上预训练的编码器（检测、OCR、分割）
**相比视觉-语言对齐预训练的编码器竞争力更弱，这可能是因为与 LLM 整合时存在表征不一致**。」

→ **ConvNeXt@1024 是单编码器综合最优。** 而我们的场景既要读文字（前端）又要判几何（three.js），
**不能用单维度冠军。**

#### 结论三：堆编码器买不到 OCR

Eagle 表 12（逐个加编码器）：

| 编码器数 | 组合 | **OCRBench** | Avg |
|---|---|---|---|
| 2 | CLIP + ConvNeXt | **551** | 681.5 |
| 3 | + Pix2Struct | 550 | 685.1 |
| 4 | + EVA-02 | 540 | **694.6** |
| **5（Eagle-X5）** | + SAM | **529** | **697.1** |
| 6 | 全部 | 525 | 686.8 |

**Avg 从 681.5 单调涨到 697.1，而 OCRBench 从 551 单调掉到 529。**
→ 混编码器提升的是通用能力，**不是 OCR**。这修正了 §5.3.1 里「混多个编码器 > 放大单个编码器」的说法 ——
**那条对通用能力成立，对文字密集任务不成立。**

融合方式（表 11）：**Channel Concatenation 最优**（1024 token，OCRBench **551**）；
而「注入式」方法（LLaVA-HR 498、Mini-Gemini 478、Deformable Attn 463）
**在 OCRBench 上甚至不如单独用 ConvNeXt**（原文 §2.4 的表述）。

**机制（可引，不只是趋势）**：Eagle 选的 Channel Concat 在 OCRBench 上的峰值也只是 2 编码器时的 551，
而注入式融合连单独用 ConvNeXt 都不如。
→ **「混编码器」在文字密集上的上限就是「其中最强的那个高分辨率语言监督编码器」。
多出来的编码器是在买 vision-centric 与 general，不是买 OCR。**

#### 一条必须说出来的方法论警告：单编码器横评跨论文不可比

| 论文 | SigLIP 的 DocVQA | OpenAI CLIP 的 DocVQA | 方向 |
|---|---|---|---|
| Cambrian-1 表 14 | **40.19**（SO400M@384） | 32.11（L/14@336） | SigLIP 赢 |
| **AIMv2 表 7** | **16.9**（L/14，576 patch ⇒ 336px） | **25.6**（L/14@336） | **OpenAI CLIP 赢** |

→ **编码器横评只能在同一篇内部读。** 本节三条结论都是单篇内部对照。

Molmo（2409.17146 表 5a）的第三方印证：
**OpenAI CLIP 76.9 / MetaCLIP 77.2 / SigLIP-So400m 77.1（三者 ±0.3 等价）/ DINOv2 75.6**。
原文：「在有噪声的网络规模数据上训练的视觉编码器（CLIP、SigLIP、MetaCLIP）**表现大致相同**。」

#### 补一条反向的权重：语言骨干比视觉骨干更重要

Idefics2（2405.02246）**Finding 1** 逐字：

> **在参数量固定时，语言骨干的质量对最终 VLM 的影响大于视觉骨干的质量。**

支撑（表 1 vs 表 2）：换语言骨干（Llama-1-7B → Mistral-7B，MMLU 35.1 → 60.1）**Avg +5.1**；
而换视觉骨干（CLIP-ViT-H@224 → EVA-CLIP-**5B**@224 → SigLIP-SO400M@384）只 57.4 → 60.2 → **60.7**。
原文还点名：「尽管 EVA-CLIP-5B 的参数量是 SigLIP-SO400M 的**十倍**，我们得到**相近**的性能，
说明 EVA-CLIP-5B 可能**严重训练不足**；我们承认**开源 VLM 社区缺少一个大而训练充分的视觉编码器**。」
⚠️ 表 2 有分辨率混淆（224 vs 384），不能当纯编码器对照读。

→ **合起来**：视觉编码器选「语言监督 + 原生分辨率 + 0.4B 级」就够（§2.7 的 Eagle 26 倍 FLOPs 打平），
**省下的预算应该花在语言骨干和数据上。**

## 2.3 饱和位置由「源图原生分辨率」决定，不由模型决定

五条独立归因指向同一判据：

| 论文 | 原文归因 | 推出的判据 |
|---|---|---|
| **Monkey** 2311.06607 §4.4 | 「**TextVQA 的原始图像平均只有 950×811 像素**，进一步提高输入分辨率似乎没有必要」 | 原图长边约 950 ⇒ **896² 就是顶** |
| **IXC2-4KHD** 2404.06512 §4.1 | 统计指出 **InfoVQA 约 50% 的图长边超过 2000 px** ⇒ 所以它「到 4KHD 都没观察到饱和」 | 原图长边 > 2000 ⇒ **8,737 token 仍不够** |
| **MM1** 2403.09611 §5.1 | 1792² 下降的归因：「**很多评测图像本身小于该分辨率**，resize artifact 可能影响性能」 | 超过原生分辨率后是**纯负收益** |
| **Qwen2-VL** 2409.12191 §3.3.1 | min_pixels 过高导致 OCRBench 严重下降：「**OCRBench 含大量极小图**，过度放大使它们偏离训练分布，变成 OOD 样本」 | **放大小图也会掉分** ⇒ 不是「越大越好」，是「**对齐原生分辨率**」 |
| **PaliGemma 2** 2412.03555 §4.2 | 分辨率敏感组的归因：「这些 benchmark 里的图像**原生分辨率往往显著大于 224 px²**」 | 同一判据的正向表述 |

**合成成一句话**：
**分辨率的收益曲线 ≈ `min(模型有效分辨率, 源图原生分辨率)` 的函数。**
当模型有效分辨率追上源图原生分辨率后，继续加只剩插值伪影和 OOD 风险。

**推论到前端截图**：全页截图长边常 **3,000 ~ 10,000 px**，属于 **InfoVQA 那一侧**。

| 可外推的曲线 | 不可外推的曲线 |
|---|---|
| IXC2-4KHD HD9 → 4KHD（1,561 → 8,737 token）：**InfoVQA +18.8、DocVQA +9.6** | ChartQA：728² 后 +0.3；672 → 1008 只 +0.4 |
| NativeRes-LLaVA 378² → 1792²：**InfoVQA +31.0、DocVQA +32.0、OCRBench +97** | TextVQA：**896 后饱和**；728² 后 +1.3 |
| SigLIP2-So400m 224 → 384 px：**DocVQA +30.0**（SigLIP 非 2 版 +28.4） | **OCRBench：576 token 就见顶**（828 → 3136 时掉到 786） |
| PaliGemma2 3B 224² → 448²：**DocVQA +33.7** | MMMU / AI2D / MMBench / POPE / SEED：全程 ±1.7 |

**一个可操作的副产品**：
**OCRBench 不适合做本场景的选型指标**（图太小、576 token 饱和、放大还掉分）。
该用 **InfoVQA / DocVQA / OCRBench v2 的 Element Parsing / HR-Bench / RC-Bench**。

## 2.4 像素预算的陷阱：`max_pixels` 是按**面积**封顶的

**长宽比保真不等于可读。** 这是本节最容易在实现里踩到的一个坑，而且它**只对一部分权重成立** ——
下面把两类分清楚。

### 2.4.1 实测各家的出厂默认（HF 权重配置里的**实现事实**，不是论文声明）

| 模型 | 出厂默认上限（像素面积） | 等价 token 上限 |
|---|---|---|
| **Qwen2-VL / Qwen2.5-VL-7B-Instruct** | **12,845,056** | **16,384** |
| **GLM-4.5V / GLM-4.1V-9B-Thinking** | **9,633,792** | **12,288** |
| UI-TARS-7B-DPO | 2,116,800 | 约 2,700 |
| ShowUI-2B（**README 推荐值**） | 1,053,696 | **1,344** |
| OS-Atlas-Base-7B | 1,048,576 | 约 1,337 |
| Aguvis-7B-720P | 937,664 | **1,196** |

**换算口径**：`patch_size=14`、`merge_size=2` ⇒ 每个视觉 token 覆盖 28×28 = **784 像素**。
**验证锚点**：Aguvis 的 937,664 ÷ 784 = **1,196**，与论文原文「720p 恒定 1,196 tokens」**精确吻合** ——
这证明整套换算是对的。

**GLM 的配置实测**（本轮新抓到，`zai-org/GLM-4.5V` 与 `zai-org/GLM-4.1V-9B-Thinking`
的 `preprocessor_config.json` **三份内容完全一致**）：

```json
{"size": {"shortest_edge": 12544, "longest_edge": 9633792},
 "patch_size": 14, "merge_size": 2,
 "image_processor_type": "Glm4vImageProcessor"}
```

⚠️ **两条使用限定，必须一起引**：
1. **字段名有坑**：`Glm4vImageProcessor` 的 `size.shortest_edge / longest_edge`
   **不是边长，是面积**（起的是 Qwen 的 `min_pixels / max_pixels` 的作用，走同一套 `smart_resize`）。
   依据：12,544 = 16×28²、9,633,792 = 12,288×28²，整除得干干净净，面积解释是唯一自洽的。
   但**论文（2507.01006）一个字都没写**，所以这条的级别是「**配置实测 + 字段语义推断**」，不是论文声明。
2. **这是 HF 权重的出厂默认，不是论文声明**（与 UI-TARS 那格同性质）。
   论文只给了 seq len 32,768（4.6V 到 131,072）。

### 2.4.3 三条可直接用于选型的结论

**① 「保真 ≠ 可读」，而且这个陷阱只对 GUI 专用权重成立。**
Qwen / Aguvis / OS-Atlas / ShowUI 都严格保长宽比，但 `max_pixels` 按**面积**封顶 ⇒
长条形把预算摊到两个方向，**宽度被牺牲**。
**但 GLM / Qwen 的出厂默认（9.6M / 12.8M 像素）已经够把 1280×6000 按原生宽度喂进去**，
而**所有 GUI agent 专用权重（ShowUI-README / UI-TARS / OS-Atlas / Aguvis）的默认值是按 720p ~ 1080p 单屏调的，
差了 4 ~ 10 倍**，直接套用会把宽度压到 448 ~ 672 px。
→ **这正好印证 2507.01006 §2.1 那句「支持超过 200:1 的长宽比与 4K 以上」不是宣传话术 —— 声明与配置一致。**

**② 「候选集的比例粒度 > n_max」。**
InternVL 从 n_max=12 跳到 18~24 是**质变**（448 → 896 px），
但**再升到 36 / 40 完全没有改善** —— 因为下一个更近的候选 3×14=42 块被 n_max 卡掉。
**瓶颈不是 n_max，是候选集的比例粒度。**

**③ 保住宽度只有两条路**：
(a) **把像素预算调到 ≳ 8M**（GLM / Qwen 默认已在此量级）；
(b) **纵向切块滚动**（UGround §G.2 是唯一写清楚的工程协议，块内 896 px、首块命中约 80%），
代价是**丢全局布局** —— 而这恰恰是 screenshot → code 的核心（§2.5.1 的缩略图消融已证明）。

### 2.5.1 缩略图（全局视图）保的是布局，不是 OCR —— 所以不能省

| 来源 | 配置 | 变化 |
|---|---|---|
| **IXC2-4KHD**（2404.06512 表 7） | HD9，有 → 无 global view | **MMBench 79.5 → 75.1（−4.4）**、**MME 2201 → 2019（−182）**；而 DocVQA 79.4 → 78.1、**ChartQA 78.2 → 77.9（只 −0.3）** |
| **Monkey**（2311.06607 附录 G） | 896，有 → 无 global | **TextVQA +7.5、DocVQA +6.2** |
| **UReader**（2310.05126 表 2） | 20 crops，加 global | **VisualMRC +11.0 CIDEr**、DocVQA +1.3、WTQ +1.8；而 **ChartQA −1.4** |
| **UGround**（2410.05243 §2.3） | > 1000 px 场景，**去掉**低分辨率全局图 | 原文：「图像大于 1,000 px 时它直观上提供不了有信息量的上下文，而且我们**实测发现它轻微损害性能**」 |

**读法**：IXC2 那一行最关键 —— 去掉缩略图后 **MMBench 掉 4.4、MME 掉 182，而 ChartQA 只掉 0.3**。
**缩略图护的是「布局 / 通用感知」那条通道，不是 OCR。**
而 image-to-code 的第一步就是整体布局 ⇒ **不能省**。
但**分辨率一上千就要换做法**：要么像 UGround 那样去掉，要么像 DocOwl2 那样
**把缩略图升级成压缩器的 query**（同 token 预算下 DocVQA +7.1）。

### 2.5.2 块数涨上去会先打掉「通用感知」

| 来源 | 对比 | 下降项 |
|---|---|---|
| **SPHINX**（表 3） | 2×2（4 块）→ 3×3（9 块） | **VSR 65.4 → 57.1（−8.3）**、IconVQA −2.2、OCR-VQA −2.2、VizWiz −1.9；只有 TextVQA +2.4 涨。第三方复核：TFLOPs **39.7 → 69.4** |
| **IXC2-4KHD**（表 6 对角线） | HD9 → HD16 → HD25 | **SEED\* 单调 76.6 → 75.7 → 74.9**；MMBench 79.5 → 80.2 → **78.5** |
| **Molmo**（表 12） | train 12 crop / test 36 crop（**不匹配**） | **PixMo-Count 85.2 → 73.9（−11.3）**、11-avg 76.9 → 75.8 |
| **IXC2-4KHD** §4.2 | 推理分辨率 > 训练分辨率 | **ChartQA 三次全掉**（78.2 → 75.8；80.1 → 79.1；80.3 → 79.4），归因「分辨率改变后模型对 chart 结构感到困惑」 |
| **Idefics2**（表 9，**同一份权重**） | 64 → 320 token | TextVQA **+2.6**、DocVQA +6.7；而 **MMMU −0.5、MathVista −0.2、MMBench −0.1** |
| **UReader**（表 2） | 9 crops → 20 crops（都不加 global） | DocVQA +6.1、WTQ +2.9；但 **VisualMRC −4.6 CIDEr —— 唯一的网页截图任务反向** |

**三条规律**
1. **块数涨，「通用感知 / 空间推理」先掉**（SEED、MMBench、VSR、MMMU、HallusionBench），OCR 后涨 ——
   **这是明确的 trade-off，不是帕累托改进。**
2. **块数涨而不同步压 token，会把 OCR 也打掉**（TextMonkey −9.2 DocVQA，见 2.7）。
3. **训练分辨率分布 ≠ 推理分辨率时，结构化图表会退化** ⇒ **推理时别随便把 max tiles 往上调。**

**最极端的一条**（Monkey 2311.06607 表 5，同为 896²，只换「怎么把高分辨率喂进去」）：

| 方式 | TextVQA | DocVQA | DeepForm |
|---|---|---|---|
| **位置编码插值** | 44.7 | 53.9 | 11.4 |
| **滑窗切块** | **67.6** | **66.5** | **40.6** |

**同样的分辨率，换一种喂法差 23 分。** 这条印证了 MM1 的「架构选择不重要」是**只在同一类喂法内**成立的。

## 2.6 projector 里别用可学习 query，合并方向要跟文字排布一致

三篇独立同向（把保留 2D 的压缩换成可学习 query 后）：

| 工作 | 退化 |
|---|---|
| DocOwl1.5 | 文本**定位** **−10.6** |
| DocOwl2 | DocVQA **−7.1** |
| IXC2 | DocVQA **−2.8** |

**合并形状的消融**（DocOwl1.5 2403.12895 表 4，DocVQA）：
**1×4（横向）72.8** > 2×2 **71.8** > 2×4 71.4 > 1×8 69.9 > 2×8 **69.2**。

→ **前端截图的文字是横排的，所以横向合并优于方形合并。** 这是实现里很容易做错的一个点。

同篇还有一条：**H-Reducer 用 9 个 crop 就打赢 Abstractor 用 20 个 crop（72.8 对 71.4）** ——
**换压缩方式比加切块数划算。**

**但有一条反向约束**（Idefics3 2408.12637 §2.2.2，它明确推翻了 Idefics2 自己的结论）：

> 在 Idefics2 里作者发现预训练时 128 token 代替 64 token 没有明显改善。这对大多数任务成立，
> **但在用 image-splitting 策略微调之后，每图用更多视觉 token 的好处在 OCR 任务上显现出来了。**

换 perceiver(64) → pixel-shuffle(169) 后 **DocVQA +13.7**。
→ **压缩不能把 2D 结构压掉**，否则 OCR 任务上的 token 收益就看不见了。

## 2.7 预算要花在「更高分辨率 + 更强压缩」

| 证据 | 数字 |
|---|---|
| **Molmo** 的切块数 | 单 crop 62.8 → 多 crop 重叠 **76.9（+14.1）**；而 **12 → 36 crop 只 +0.3** |
| **DocOwl2** | **324 token 拿到 DocVQA 80.7**，是 DocOwl1.5（**1,806 token**，82.2）的 **98% 性能、18% token**；首 token 延迟 **0.58 s → 0.26 s** |
| **TextMonkey** | 896 → 1344，**不压 token 反而 DocVQA 64.1 → 54.9（−9.2）**。冗余 token 占比（cos-sim > 0.8）：448 档 **26.6%** → 896 档 **55.8%** → 1344 档 **59.5%** |
| 同上（压缩反而更好） | 896 / r=512 的 DocVQA **64.3 > 896 / 全量 64.1**；1344 / r=1024 的 **64.5 ≫ 1344 / 全量 54.9** |
| **LLaVA-UHD** | 672×1008（LLaVA-1.5 的 **6 倍像素**）只用 **94% 算力**，TextVQA **+6.4**。换成不压缩的 MLP 要 **113.65 TFLOPs**（对 14.63），TextVQA 反而 **66.9 < 67.7** |
| **Eagle**（最刺眼的一条） | CLIP **0.3B** 插值到 448 ⇒ 1024 token、**214 G FLOPs**；InternViT-**6B**@448 ⇒ 1024 token、**5,669 G FLOPs**。**Avg 670.5 对 671.5 —— 打平，FLOPs 差 26 倍** |
| **IXC2.5 对 InternVL2** | IXC2.5-7B 用约 **7,395** token 得 DocVQA **90.9**；InternVL2-8B 用约 **3,198** token 得 **91.6**。**多花 2.3 倍 token，分数反而低 0.7** |
| **LLaVA-OneVision §3.2 的原则** | 原文：「**分辨率的 scaling 比 token 数的 scaling 更有效**」 |

**Eagle 那一行应该直接写进选型结论**：
**把 ViT 从 0.3B 换成 6B，在同样的 token 预算下是打平的，而算力差 26 倍。**
这是 §5.3「视觉编码器规模不是旋钮」最硬的单点证据。

**ShowUI 的 token selection 还给了一条实现细节**（2411.17465 图 9）：
按 UI 连通图剪 token，**ratio 0.5 时 ScreenSpot 70.8 → 70.4（−0.4）且训练加速 1.5×**，
但**推理期也开则 −5.9**；同压缩率下 token **merge** 只有 42.3（位置关系被毁）、随机选 65.3。
插入层位置：**隔层插入（cross-layer）70.5 最好**，全 28 层 65.7 最差。
→ **只在训练期剪，推理期给全量；而且要选不毁位置关系的剪法。**

## 2.8 文字密集截图的 OCR 能力：不是瓶颈

### 2.8.1 按度量口径分层（同一个模型能差 5 倍）

同一个 DeepSeek-VL-7B：**Design2Code Text 77.0，ChartMimic Text 15.3。**

| 口径 | 代表指标 | 前沿模型表现 | 是否瓶颈 |
|---|---|---|---|
| **条件型字符 Dice**（只在已匹配的块上算，门限 0.5） | Design2Code Text | GPT-4o **98.6**，全模型极差约 4 个点 | **否，结构性饱和** |
| 同上（难集） | Design2Code-HARD Text | GPT-4o 89.8（而 **Block 只 56.6**） | 否，退化幅度是 Block 的 1/4 |
| 同上（第三方复测） | UI2Code^N 表 2；ScreenCoder 表 1/2 | Text 全模型极差 **2.7 个点**；SFT+RL 增益只 **+0.013 ~ +0.017** | **否，训不动也不用训** |
| **真 · 文字 P/R/F1**（无门限，执行失败记 0） | ChartMimic Text | GPT-4o **81.5**，DeepSeek-VL-7B **15.3** | **是（图表场景）** |
| 文字精确率（PaddleOCR 抽取） | Plot2Code Text-Match | GPT-4V 直接看图 **57.7** | **是（图表场景）** |
| 文字块 IoU（布局层） | Sketch2Code Text IoU | Claude-3.5-Sonnet **22.51** | 布局问题，不是 OCR |
| **结构化输出**（最接近 image-to-code） | OCRBench v2 Element Parsing | InternVL2-8B **27.3**，且**随分辨率单调降到 24.8** | **是，而且方向反了** |

**两条必须一起看**
1. **Design2Code 的 Text 98.6 是个假象**：它是**条件型**指标 —— 只在「已经匹配上的块」里算字符 Dice，
   **漏掉的块根本不进分母**。它衡量的是「认出来的字准不准」，不是「有没有都认出来」。
2. **OCRBench v2 的 Element Parsing 随分辨率下降（27.3 → 26.2 → 24.8）**，方向与 2.1 相反。
   只有 3 个点，样本太少，但方向值得记：**结构化输出任务的瓶颈不在看清，在组织。**
   同表的对照：Average 只 +0.2、Extraction 66.2 → **65.2** 也在掉。

### 2.8.2 真正的瓶颈是元素召回与布局

| 维度 | 表现 |
|---|---|
| **Text** | Design2Code 极差 2.7 个点，SFT+RL 只涨 **0.013** |
| **Position** | SFT+RL 涨 **0.129**（约 10 倍于 Text） |
| **Block（元素召回）** | Design2Code-HARD GPT-4o 只 **56.6**，**漏 30 ~ 40% 的 block** |
| 错误类型 | DCGen 的 **85.34% 错误是 omission（漏元素）** |

→ **「文字不可读」是错的方向。** 模型不是读不清字，是**在大图上漏元素、把层级搞错**。
这两样的杠杆恰恰是：**有效宽度（2.4）、块间结构信号（2.5）、不丢 2D 的压缩（2.6、2.7）。**

### 2.8.3 「先 OCR 再写码」的流水线不值得做

| 方案 | DINO / VLM-Judge | 耗时 | token |
|---|---|---|---|
| DCGen（agent 管线） | 69.6 / 45.0 | 约 137 s | 约 7,600 |
| ScreenCoder（agent 管线） | 85.7 / 80.0 | 约 66 s | 约 4,600 |
| **UI2Code^N-RL（端到端 9B）** | **86.1 / 88.6** | **约 40 s** | **约 2,600** |

（2511.08195 表 15，Design2Code-HARD）
LayoutCoder §6.4 另有实测：DCGen 在**高长宽比**数据上失败率与成本都显著上升 —— **正好是本场景。**

**两个「用额外视觉线索替代分辨率」的尝试都是负收益**：
- **ChartMimic 的 Scaffold Prompting**（在图上叠带坐标标签的点阵，表 5）：
  GPT-4o 81.2 → **79.0**；InternVL2-76B 58.5 → **56.7**；InternVL2-8B 36.6 → **29.9**；InternVL2-2B 23.5 → **11.5**。
  原文：「额外的点阵会**干扰高信息密度图表中已有的坐标轴信息**」。
- **Plot2Code 的 OCR token 前置**（§4.3）：效果「与高分辨率设置所取得的提升相当」——
  即只是替代，不是叠加。（数值只在图 5，未核实。）

**真要绕开读字，正确做法是换输入而不是加前置 OCR**：
- **PSD2Code（2511.04012 表 4/表 7）**：直接吃设计文件的结构元数据，SSIM **0.623 → 0.878**；
  **去掉 PSD 解析只给截图，SSIM 塌到 0.423**。
  ⚠️ **数据质量告诫**：只有约 100 例、15 例测试集；表 4 里 CodeFun 的 CodeBLEU = CodeBERT = SSIM = 0.691
  三个数完全相同（可疑）；§5.3 的组件贡献占比三项相加超过 100%。**方向可引，绝对值不可引。**
- **UI2Code^N 的局部 DOM grounding 目标**（给 DOM 节点 bbox，预测对应代码片段，2511.08195 式 12）。

→ **这两条对本项目特别契合**：我们是**自己写的代码自己渲染**，
所以 DOM / scene graph **本来就在手上，不需要从图里反推**。
这正是 §1.5.2 那条推论的工程落点：
**「把视觉信息精确地文本化」极其有价值，而我们有特权通道能做到。**

## 2.9 一个值得做的零成本实验：OCR 分数与 image-to-code 分数的相关性

**截至 2026-10，没有任何公开工作报告过「模型的 OCR / DocVQA / TextVQA 分数」与
「其 image-to-code 分数」的相关系数。**

最接近的：

| 工作 | 做了什么 | 数值 |
|---|---|---|
| **ChartMimic 附录 H** | 唯一真做了「感知基准 ↔ image-to-code」相关性：ChartQA 代表图表理解、HumanEval 代表代码能力 | **r_chart = 0.6877**；**r_code = 0.8714** |
| 同上 表 6 | 自家指标 ↔ 人类评价 | High-Level r = 0.7041；Low-Level r = 0.7681 |
| ArtifactsBench | 报了 vision 分 ↔ code 分相关性 | 「强正相关，说明能力提升是 **holistic 而非孤立的**」（只有定性） |

**ChartMimic 那组是本节最该引的数字**：**r(感知) = 0.69 < r(代码) = 0.87** ——
**代码能力的解释力比感知能力更强。** 原文结论：「两者都影响表现，**代码生成能力的影响更显著**……
未来模型开发应**聚焦基础代码生成能力**」。

**两条旁证**
- **GLM-4.1V / 4.5V 的跨域 RL 泛化矩阵**（2507.01006 图 6）：
  「在 **OCR & Chart** 数据上训练会在 STEM、GUI-agent 和通用 VQA 上带来增益……
  OCR & Chart 与 GUI-agent 任务互相促进，反映了它们对准确文字识别的共同需求。」
  ⚠️ **五个域里没有 coding**，所以回答不了 OCR ↔ code。
  作者在 §7 Limitations 里把这件事列为未来方向：
  「理解视觉推理任务（如**解读图像中的代码**）能否提升**纯文本 coding 任务**的表现，是一个有前景的研究方向」。
- **OCRBench v2（2501.00321）**：全文确认**没有任何前端 image-to-code 任务**。
  最接近的是 Parsing Type（把图像转成 HTML / Markdown / JSON，用 TEDS 评），
  但那是表格 / 文档结构解析。**OCRBench v2 与 image-to-code 之间没有桥接。**

**→ 零成本、可立刻做**：前沿模型卡（Qwen3-VL 2511.21631、GLM-4.5V 2507.01006）在**同一篇**里
同时报 OCRBench / OCRBench v2 / DocVQA / CC-OCR / OmniDocBench **和**前端代码基准，
**但从不把二者放一起做相关性**。把已发表的数字抓出来回归一次，不需要任何 GPU。

## 2.10 文字这条线真正要担心的三件事（不是分辨率）

| 风险 | 证据 |
|---|---|
| **多语种** | Design2Code §4.5：「非英文网页通常更难生成」，HARD 集 **19% 非英文**；WebMMU：「multilingual generalization 仍弱」，Fuyu-8B 英文低至 **2%** |
| **长上下文下的文字复读崩溃** | Sketch2Code：给 InternVL2-8b 全部文字后 **HTML 合法率 98.0% → 39.2%**、Layout **−6.07**；Design2Code：Idefics2-8B Text **80.3 → 55.6 → 22.6**（Direct → Text-Aug → Self-Revision） |
| **评测口径** | 同一个 DeepSeek-VL-7B：Design2Code Text **77.0** 对 ChartMimic Text **15.3**。看到「Text 98%」必须回查：① 有没有 0.5 匹配门限；② 执行失败记不记 0 |

**第二条对本项目是硬约束**：**对开源小模型，把文字塞进 prompt 是净负收益。**
这与 §1.3.2「图比完整 a11y 树便宜」不矛盾 —— 便宜不等于有用。
**我们的 scene graph 必须是摘要，而且要先在目标底座上验证「塞进去会不会让它崩」。**

## 2.11 3D 渲染图这一侧：不会和前端抢分辨率预算

**检索未发现任何针对「3D render → code」的视觉编码器分辨率消融。**
现有 CAD / render-to-code 工作一致用**低分辨率 + 多视角**：

| 工作 | 输入规格 | 核实状态 |
|---|---|---|
| cadrille（2505.22914） | 4 个固定视角拼成 2×2 网格，**268×268**，**400 个视觉 token** | 未核实全文 |
| Zero-to-CAD（2604.24479） | 每个形状 **8 张 256×256** render，Qwen3-VL-2B | 未核实全文 |
| CAD-Coder | CLIP ViT-L **@336 px**，LLaVA-1.5 架构，第一阶段冻结 encoder | 未核实 |
| GACO-CAD（2510.17157） | 消融的是几何先验图（depth / normal）的编码与融合方式，**不是分辨率消融**；且每个替代方案都更差 | 未核实全文 |
| CADBench（2605.10873） | 单视角 / 照片级 / 多视角 × 11 个 VLM；报告「重建质量随几何复杂度上升而下降」，**未隔离 render 分辨率** | 未核实 |

→ **推断（无直接消融支撑）**：3D 渲染这一侧是常规 1:1 比例、不触发长宽比失配、256 ~ 336 px 就够，
所以**底座的分辨率策略应完全按前端长截图来定，3D 侧搭便车。**
这与 §3.4 的配置一致：three.js 的 8 视角拼成 2048×1024（每格 512×512），
比 cadrille 的 268×268 / 400 token 还宽裕。

## 2.12 现有 image-to-code benchmark 的分辨率规格：「没有消融」本身就是结论

> **Design2Code、UI2Code^N、ChartMimic、Plot2Code、Web2Code 五个 image-to-code benchmark，
> 没有任何一个做过输入分辨率消融。**

| Benchmark | 截图怎么来 | 实际分辨率 | 长页面是否截断 | 有分辨率消融？ |
|---|---|---|---|---|
| **Design2Code** | Playwright Chromium `page.screenshot(full_page=True)` | 宽 = Chromium **默认视口 1280 px**；随后把**短边缩到 768 px** | **不截断，但超长页面整例丢弃**：`rescale_image()` 规定「缩放后长边 > 2000 px → return False」⇒ **测试集每张 ≤ 768×2000，长宽比上限约 1:2.6** | **无**。全文 "resolution" 只出现 2 次，均与模型无关 |
| 同上（**评测侧**） | `visual_score.py` 在算 CLIP 相似度前**把截图 resize 成正方形** | — | — | — |
| **Web2Code** | Selenium Chrome `--window-size=1920,1080`，先 `PAGE_DOWN` 再 `get_screenshot_as_png()` | **1920×1080 固定** | **截断**。该 API 只抓视口；而且截图前先按了一次 PAGE_DOWN ⇒ **抓到的是第二屏而非首屏**（源码注释写「Scroll to capture the entire page」，但该 API 做不到） | **无**。baseline 用 **CLIP ViT-L/14 @ 336×336** 去看 1920 px 的网页截图 |
| **UI2Code^N** | 全文无 viewport / 分辨率 / 截图尺寸任何说明 | **未披露** | 未披露 | **无**。它的替代方案是**局部 DOM grounding** |
| **ChartMimic** | matplotlib 渲出的 PNG | **未披露**，全文无任何图像尺寸统计 | 不涉及 | **无**。harness 里写死 `max_num=6` + `use_thumbnail=True`（448²×6 ≈ 1,792 token） |
| **Plot2Code** | 132 张 matplotlib gallery 图 | **未披露** | 不涉及 | **半个，且与自己的表不一致**：正文说「更高分辨率的 MLLM 持续提升性能」，但表 3 里同模型 LR→HD 的 **Pass Rate 是 8x7B −2.3、34B −11.6** |

**→ 两条结论**
1. **「长页面 / 高长宽比」这个前端截图最核心的难点，在现有 image-to-code benchmark 上基本没被测到。**
   Design2Code 的长宽比上限 1:2.6（而且评测时把图 resize 成正方形），真实长页面是 1:3 ~ 1:10。
   **拿 Design2Code 的分数当选型依据，测不出 §2.4 的那个陷阱。**
2. **自建评测必须包含 1:5 以上的长截图，并且单独拆一个可渲染率指标。**
   Plot2Code 的 Pass Rate 从 LR 到 HD 掉 11.6；OCRBench v2 Element Parsing 随分辨率 27.3 → 24.8。
   两条都弱，但方向一致：**只看视觉相似度会漏掉「分辨率提上去但代码跑不起来」。**

**对照：非 image-to-code 的 UI 数据集反而有分辨率统计**

| 论文 | 实际屏幕分辨率 | 最极端长宽比 |
|---|---|---|
| Ferret-UI | Android 2560×1440；iPhone 1792×828 / 2436×1125 | 约 **2.16:1** |
| Ferret-UI 2 | WebUI 1280×720 ~ 2048×2732；iPad 2224×1668 | 约 **2.46:1** |
| UGround | 773K Common Crawl 网页截图，Playwright 渲染，**随机抽图像尺寸以覆盖多种分辨率与长宽比**；「**对每个长网页，随机采样最多三个视口大小的 block**」 | 上限 1344×1344（横）/ **896×2016（竖）** |

**UGround 的做法值得直接抄**：**对长网页随机采样最多三个视口大小的 block** ——
这正好是 §3.2 建议的「纵向切片」的数据侧对应物，而且它的切片数（3）与 §3.4 的滑窗数一致。

**另一条相关的长度退化证据**（WebCode2M 2404.06369 表 3，按代码长度分 Short/Mid/Long）：
WebCoder-1.3B 的 **TreeBLEU .35 → .22 → .15（腰斩）**、Visual .78 → .69 → .65；
而 **GPT-4o 的 Visual Score 0.85 → 0.81 → 0.82（几乎不退化）**。
→ **长度退化主要打击专用小模型。** 这对「选 9B 还是更大」是一条反向压力（见 §6.3）。

WebCode2M §5.1 还给了它选 Pix2Struct-1.3B 做基座的理由，**对本场景直接有用**：
> **对极端长宽比鲁棒、能动态适应序列长度和分辨率的变化。**

# 3. 图像 token 预算

## 3.0 先纠正三处口径

本节的三个数字在成稿里出现过，这次回到官方文档和自己的算式重核，**三处都要改**。

| 成稿里的说法 | 核实结果 | 改成 |
|---|---|---|
| 「超限的 tool_result 图片直接报错，不会自动缩放」（06_harness §2.2） | **只对 computer use / browser use 这两套工具的 tool_result 成立**。其他超限图像是**自动下采样**的，除非显式给 image block 设 `transformations` 要求报错 | 见 3.1，区分两种路径 |
| 「多视角拼成一张 contact sheet，token 是逐张发送的 1/8 左右」（06_harness §2.2）、「703 对 8288」 | **不是同口径**。703 是 1024×512 的拼图（总像素 524,288），8,288 是 8 张 1024×768（总像素 6,291,456）。像素比本身就是 12.0×，token 比 11.8× —— **省的几乎全是降分辨率，不是拼图** | 同像素下，拼图相对 8 张独立小图只省 **12.1%**（800→703）；每格 512 时只省 **5.2%**（2,888→2,738） |
| 「图像在累计输入里占 8%，文本历史才是大头」（draft_training §6） | **只在最便宜的那一档成立**。8% 对应「滑窗 3 张 1024×512 拼图」。换成能看清文字的配置，图像占比升到 16%~36% | 见 3.3 的分档表 |

**第二条的意义**：拼图的价值不在省 token，在**省「图像数量」这个独立配额**（3.1 的 20 张门槛、Gemini 的 3,600 张上限），
以及少付每张图的固定开销。**想省 token 只有一条路：降分辨率。而降分辨率会直接伤 OCR。**

---

## 3.1 一张 1440 宽的截图，各家编码成多少 token

三家的规则都**不是一个纯公式**，而是「公式 + 像素上限 + token 上限」三段。先给规则（均来自官方文档，2026-10-15 实查）：

| 厂商 | 公式 | 上限 | 出处 |
|---|---|---|---|
| **Claude** | `⌈w/28⌉ × ⌈h/28⌉` | **两档**：标准档（4.7 之前的模型）长边 **1568 px**、视觉 token **1568**；高清档（4.7 及之后）长边 **2576 px**、视觉 token **4784**。超限按长宽比缩到刚好塞进上限 | platform.claude.com/docs/en/build-with-claude/vision |
| **OpenAI** | patch 计法：`⌈w/32⌉ × ⌈h/32⌉`，再乘模型系数（gpt-6-astra / 5.6 / 5.5 / 5.4 / 5.2 都是 **1.2**；gpt-5-nano 1.5、gpt-4.1-mini 1.62、gpt-4.1-nano 2.46） | 按 `detail` 分档。gpt-6-astra：`low` 塞进 512×512；`high` **2,500 patch** 预算 + 65,535 px 最大边；`original` 保留原尺寸，**超过 30,000 patch 直接拒绝、不缩** | developers.openai.com/api/docs/guides/images-vision |
| **Gemini** | 两边都 ≤384 px → **258 token**。否则：`crop unit = floor(min(w,h)/1.5)`，`tiles = ⌈w/cu⌉ × ⌈h/cu⌉`，每块 **258** | Gemini 3 用 `media_resolution` 档位设每图 token 上限；每请求最多 **3,600** 张图 | ai.google.dev/gemini-api/docs/image-understanding |

**Gemini 的切块规则要特别注意**：06_harness 记的是「按 768 切块」。
768 是 tile 的像素尺寸，但**块数是由 `min(w,h)/1.5` 这个 crop unit 决定的**，不是除 768。
官方自己的例子：960×540 → crop unit = floor(540/1.5) = 360 → 960/360 与 540/360 → **3 × 2 = 6 块 = 1,548 token**。
按 768 算会得到 2×1=2 块，**差 3 倍**。已用官方例子校验，我的实现复现出 6 块。

### 实算结果（括号里是「实际进模型的像素尺寸」）

| 输入 | Claude 标准档 | Claude 高清档（4.7+） | astra `high` | astra `original` | Gemini |
|---|---|---|---|---|---|
| 1440×900（桌面首屏） | 1,550（1382×864） | 1,716（1440×900） | 1,566（1440×900） | 1,566（1440×900） | 1,548（6 块） |
| 1440×1800（两屏） | 1,540（964×1205） | 3,380（1440×1800） | 2,904（1408×1760） | 3,078（1440×1800） | 1,032（4 块） |
| 1440×3000（整页长图） | 1,512（**752**×1567） | 4,140（1236×2576） | 2,897（1088×2266） | **5,076（1440×3000）** | 2,064（8 块） |
| 1440×8000（超长页） | **616（282×1568）** | 1,564（463×2576） | 2,949（671×3733） | **13,500（1440×8000）** | 4,644（18 块） |
| 768×1024（移动端） | 1,036（768×1024） | 1,036 | 922 | 922 | 1,032（4 块） |
| 512×384（缩略） | 266 | 266 | 231 | 231 | 1,032（4 块） |

**算式已用官方表校验**：Claude 文档给了 5 组（1000×1000、1092×1092、1920×1080、2000×1500、3840×2160 的两档 token 数），
我的实现 **10 格里 9 格完全一致**，只有 2000×1500 标准档差 34（我的迭代缩放步长粗，不影响结论）。
Gemini 的 960×540 = 6 块也复现一致。

## 3.2 本节最重要的发现：token 上限不是成本问题，是**可读性问题**

看上表最后两行。**1440×8000 的整页长图在 Claude 标准档只要 616 token —— 比 1440×900 的 1,550 还便宜。**
原因是它被缩成了 **282 px 宽**。

| 1440×8000 的三种送法 | token | 实际进模型 | 宽度保真 |
|---|---|---|---|
| ① 一张整页长图 | **616** | 282×1568 | **20%** |
| ② 纵向切 9 片 1440×900 | **13,950** | 每片 1383×864 | **96%** |
| ③ 切 9 片再降到 720 宽 | 7,722 | 每片 720×900 | 50% |

**①→② 贵 22.6 倍，但宽度保真从 20% 提到 96%。**

这是一个**反直觉的陷阱**：
「给模型一张整页截图」这种最自然的做法，**既最便宜又几乎什么都看不清**，
而且账单上看不出任何异常 —— 你只会看到模型一直读错文字、写错布局，却找不到原因。

**三条工程结论（推断，但算式确定）**

1. **永远不要送整页长图。** 纵向切成视口大小的片，分别作为独立图像送。
2. **切片数量受另一个配额约束**：Claude 文档明确写，单请求超过 **20 张**图像（含历史轮次重发的、含 `tool_result` 里嵌的）
   就会对**该请求里的每一张**施加更严的尺寸限制 —— 要么把每张图缩到任一边不超过 **2000 px**，要么把请求控制在 20 张以内。
   9 片 × 滑窗 3 步 = 27 张，**已经越线**。所以滑窗步数和切片数要联合定（见 3.4）。
3. **OpenAI 侧要显式用 `detail: "original"`。** 官方文档原话：
   「对需要精细视觉细节或精确坐标的任务，例如光学字符识别（OCR）、小目标检测、computer use，
   在支持时使用 `detail: "original"`」。
   默认的 `high` 在 1440×3000 上会把图缩到 1088 宽（2,897 token），`original` 保 1440 宽（5,076 token）——
   **多付 75% 换回 32% 的宽度**。

## 3.3 一条 visual coding 轨迹的 token 构成

假设（与 08_rl_recipe §2.4.1 同一套，便于对账）：40 步，系统加任务 3,000，每步输出 800，每步文本观察 300。

| 图像配置 | 常驻图像 token | 终局上下文 | 累计输入 | **图像占比** |
|---|---|---|---|---|
| 不给图（只给 scene graph / DOM 摘要） | 0 | 47,000 | 0.98 M | **0%** |
| 滑窗 3 张 1024×512 拼图（成稿口径） | 2,109 | 49,109 | 1.06 M | **7.9%** |
| 滑窗 3 张 1440×900 整页截图 | 4,650 | 51,650 | 1.16 M | **16.0%** |
| 滑窗 3 步 × 每步纵向切 3 片 | 13,950 | 60,950 | 1.54 M | **36.3%** |
| 每步截图全留（12 次自检，1440×900） | 18,600 | 65,600 | 1.72 M | **43.2%** |

**所以成稿的「图像只占 8%」要加限定**：它对应的是**最便宜、也最看不清文字**的那一档。
**一旦为了读清文字而提分辨率或切片，图像就占到三分之一以上** —— 这时它确实是上下文的主要矛盾。

另一个方向的敏感性：把每步的结构化观察做长（scene graph 更详细）会**稀释**图像占比，但推高总量：

| 每步文本观察 | 累计输入 | 图像占比（滑窗 3 张 1440×900） |
|---|---|---|
| 300 token | 1.16 M | 16.0% |
| 600 token | 1.40 M | 13.3% |
| 1,200 token | 1.87 M | 10.0% |

**读法**：图像占比低不等于图像便宜，可能只是文本更贵。
要控总量，**两边都得管**；而 40 步轨迹的累计输入里，`i×(输出+观察)` 这一项是随步数**平方**增长的，
所以**减步数永远比减单步长度划算**（这与 08_rl_recipe §4.1.3 的 LSP 结论同向：降 20% 轮数约等于降 36% 输入 token）。

## 3.4 本项目的图像预算配置（推断）

| 用途 | 配置 | token/步 | 依据 |
|---|---|---|---|
| **policy 的每步自检（前端）** | 当前视口 1440×900 **一张**，不切片、不整页 | 约 1,550 | 3.2：整页长图不可读；切片会撞 20 张配额 |
| **policy 的历史** | 滑窗 **3 张**，历史位降到 720×450 | 约 2×400 | OpenCUA 的 3 张实测（见 1.x）；降分辨率只伤历史位，不伤当前位 |
| **policy 的每步自检（three.js / Blender）** | 8 视角拼成 **2048×1024**（每格 512×512） | 2,738 | 每格 512 才够看清部件；拼图在这一档只省 5.2%，但省的是图像**张数**配额 |
| **需要读文字时** | 对文字区域**裁剪放大**后单独送一张，不提整页分辨率 | 约 500 | 整页提分辨率是平方级成本，裁剪是常数级 |
| **judge** | contact sheet + 关键源码片段，可以比 policy 多看 2 张 | — | UI-TARS-2 的 ORM 看最后 5 张；policy 看 3 张 |
| **硬预算** | 每条轨迹视觉 token 上限写进环境，超了强制降分辨率 | — | 06_harness §2.2 已定；本节给出它该设多少：**按上表 40 步约 8 万视觉 token，设 10 万** |

**不确定度**：上表的「720×450 的历史位够不够」没有实测。
可做的最小实验：取 20 个前端自检 case，分别用 1440×900 / 1024×640 / 720×450 的历史位，
看模型能否正确回答「上一步改了什么」。这是 1 小时的实验，能把这一行从推断变成实测。

SWE-Gym（2412.21139 表 8，Qwen2.5-Coder-7B tokenizer）：

### 4.1.5 一个必须说出来的落差：模型根本没在复刻那份 HTML

UI2Code^N（2511.08195 表 15）在 Design2Code-HARD 上端到端只输出约 **2,600 token**
（agent 流水线 DCGen 约 7,600、ScreenCoder 约 4,600），SFT max seq len 32,768。
而 Design2Code-HARD 的参考 HTML 平均 **251 个标签**，全集平均 **31,216 token**。

→ **模型吐的 2.6K token 不是在复刻那份真实 HTML，而是生成一个视觉近似的短版本。**
引用 visual coding 的「token 成本」时必须区分**参考答案多长**和**模型实际吐多长**，
否则会按 31K 去配上下文预算，而真实需求只有 2.6K 输出 + 几千 token 的截图。

**对本项目的直接含义**：「复刻真实网页」这个目标在当前底座上**不是上下文问题，是能力问题**。
如果任务定义成「输出与参考 HTML 结构等价的代码」，31K 输出就是硬需求；
如果定义成「输出视觉等价的代码」（现有所有工作的实际做法），2.6K 就够。
**任务定义决定上下文需求，差一个数量级。这应该写进任务构造那一章。**

## 4.2 上下文编辑 / 摘要 / 滑窗：四组受控对照

### 4.2.1 最直接的一组：滑窗打平甚至打赢摘要

**The Complexity Trap（2508.21433）**，标题就是答案：
*Simple Observation Masking Is as Efficient as LLM Summarization for Agent Context Management*。
全部 SWE-agent + SWE-bench Verified，带 95% bootstrap 置信区间。

| 模型 | 策略 | Solve Rate (%) | 每实例成本（美元） |
|---|---|---|---|
| **Qwen3-Coder 480B** | Raw Agent（append-only） | 53.4 ± 4.3 | 1.29 ± 0.26 |
| | **Observation Masking** | **54.8 ± 4.4** | **0.61（−52.7%）** |
| | LLM-Summary | 53.8 ± 4.2 | 0.64（−50.4%） |
| Gemini 2.5 Flash | Raw Agent | 32.8 ± 4.1 | 0.41 |
| | Observation Masking | 35.6 ± 4.2 | **0.18（−56.1%）** |
| | LLM-Summary | **36.0 ± 4.1** | 0.24（−41.5%） |
| Gemini 2.5 Flash (thinking) | Raw Agent | **40.4 ± 4.3** | 0.56 |
| | Observation Masking | 36.4（−9.9%） | **0.24（−57.1%）** |
| | LLM-Summary | **31.4（−22.3%）** | 0.25 |

**五条结论**
1. 两种策略都把成本砍掉 **> 50%** —— 上下文管理「不只是优化，而是经济上的必需」。
2. **5 组里 4 组 observation masking 成本最低**；摘要**无法一致或显著地**优于它。
3. 机制一：**轨迹变长**（trajectory elongation）—— 摘要让轨迹更长，抵消了压缩收益。
4. 机制二：**摘要调用自己要钱**，占总成本最高 **7.2%**。
5. 为什么 masking 这么强：**环境 observation 占一个 turn 全部 token 的约 84%**。打这一块 ROI 最高。

**两条跨场景搬运的警告**
- masking 的窗口 M 是 **scaffold 相关超参**。SWE-agent 的最优 M=10 搬到 OpenHands
  「性能**急剧退化**」，要调到 **M=58** 才复现。原因是 SWE-agent 会把语法错误重试从历史里剔掉。
- 作者自己的 limitation：SWE 领域「工具输出特别啰嗦，这个条件天然偏向 masking」，别外推到交互简短的领域。

### 4.2.2 SWE-agent 的原始消融：滑窗不只省钱，直接提分

2405.15793 表 3（SWE-bench Lite + GPT-4）：

| 类别 | 设置 | % Resolved |
|---|---|---|
| Context | **Last 5 Obs.（默认）** | **18.0** |
| Context | Full history | **15.0（−3.0）** |
| File Viewer | 30 行 | 14.3（−3.7） |
| File Viewer | **100 行（默认）** | **18.0** |
| File Viewer | **整个文件** | **12.7（−5.3）** |

**两条**
1. **「只留最近 5 条 observation」比完整历史高 3.0 个百分点** —— 不是为了省钱，是直接提分。
   原文机制：倒数第 5 条之前的 observation 各压成一行占位符，
   「在减少不必要上下文的同时保留关于计划与动作历史的关键信息，这允许更多交互轮次，
   并**避免展示过时的文件信息**」。
2. **整个文件比给 100 行低 5.3 个百分点，比给 30 行还低** —— **上下文过多和过少都掉分，中间有最优值。**

超参 sweep（表 5，37 实例 × 5 samples）：Last-5 在 8 个配置组合里**有 7 个不低于 Full**。

### 4.2.3 把上下文管理训进模型才真正翻盘

| **CaT（把上下文管理做成可调用的 tool 并训进模型）** | **57.6** |

按最大步数分档（表 3，信息量比上表更大）：

平均上下文稳定在约 **35K token**，100 轮后仍有 **> 40%** 轨迹存活。

**CompactionRL（2607.05378 表 4）—— 把「要不要更长的窗口」直接做成对照**
GLM-4.5-Air（106B-A12B）。`Comp.(×4)` = 80K 峰值 + 最多 3 次压缩；`Long` = **真给 160K 非压缩窗口**：

| | 训练预算 | SWE-bench V. Comp.(×4) | SWE-bench V. **Long(160K)** |
|---|---|---|---|
| GLM-4.5-Air（基座） | – | 59.8 ± 1.9 | **59.5 ± 1.6** |

**三条读法，每条都能单独当一个论点**
1. 基座层面，**给 160K 真窗口（59.5）和给 80K 加压缩（59.8）完全打平** —— 纯加窗口零收益。
2. 训练预算翻倍到 160K 只拿到 64.0；**学会压缩（80K×4）拿到 66.4**，只花一半的峰值上下文。
3. 最反直觉：**CompactionRL 的 ckpt 在 160K 非压缩窗口下只有 61.8，比它自己用压缩的 66.4 低 4.6 分。**
   即模型学到的不是「处理长上下文」，而是「结构化地丢掉上下文」——
   **这两件事不等价，而且后者更有用。**

还有一个重要的负面结果（表 2）：在不带压缩的条件下做完 RL，再**在推理期打开压缩**，
分数从 52.5 **掉到 48.2**。**训练与推理的上下文管理口径不一致，净亏 4.3 分。**

### 4.2.4 通用压缩方法基本都不如不压缩

**SWE-Pruner（2601.16746 表 3）**，SWE-bench Verified **随机 50 条子集**，Mini SWE Agent：

| 策略 | Success (%) | Tokens (M) |
|---|---|---|
| Full Context | **62.0** | 0.972 |
| + LLMLingua2（token 级压缩） | **54.0** | 0.856 |
| + RAG（粗粒度检索） | **50.0** | 0.771 |
| + LLM Summarize | **56.0** | 0.794 |
| + LongCodeZip | 54.0 | 0.889 |
| + **SWE-Pruner**（行级、query-aware 剪枝） | **64.0** | **0.670** |

**除 SWE-Pruner 外，所有通用压缩方法都比不压缩差 6~12 个百分点。**
语法保全率（表 8）：LLMLingua2 的 AST 正确率只有 **0.29%**，SWE-Pruner **87.3%**。

**口径警告：n=50，±7 个百分点量级的噪声。**

全量 500 题（表 1）：Claude Sonnet 4.5 下 70.6 → **72.0（+1.4）**、token **−23.1%**。

### 4.2.5 摘要会丢什么：四组量化

| 证据 | 数字 |
|---|---|
| **只换摘要器，差 6.5 分**（2607.05378 表 1） | 执行 agent 固定为 GLM-4.7-Flash，只换 summary agent：Qwen3.5-27B **55.5** / 自己 50.5 / Qwen3-30B-A3B **49.0**。**平均每条轨迹只触发约 1 次摘要，就造成 6.5 个百分点的差距** |
| 丢的是哪两项（同上 表 9，0~5 分） | 即便是专门训过的 CompactionRL：Requirement Fidelity 4.00、Current-State 3.53、**Failure-History 3.48**、**Next-Step Validity 3.43**、**Continuation Usefulness 3.05**。**丢得最狠的恰好是 agent 最需要的「失败史」和「下一步」** |
| **摘要的压缩率是失控的**（2605.23296 表 1） | 同一个摘要 prompt，输入从 2,048 涨到 98,304（**48 倍**），平均输出只从 981 涨到 3,015（**约 3 倍**），实际压缩率从 **47.9% 变成 3.1%**。原文：「模型**自我限定了输出长度**，无论收到多少上下文」 |
| **更聪明的摘要反而更糟**（2508.21433 §D.3） | 给摘要 prompt 加 critic 与反思：solve rate **无提升**，而**轨迹变得更长**。原文：「critic 的反思自然地**鼓励 agent 去探索替代方案**……**提供了更多可追逐的方向，进一步延迟终止**」。结论句：「简单地给摘要加更复杂的反馈，可能会**加剧而非解决**效率问题」 |

**第三条是最根本的结构性结论**：
**你无法通过提高触发阈值来减少信息损失，因为阈值越高，实际压缩率越激进。**
摘要的「丢多少」不是你能调的参数，是模型自己定的。

**LLM 放大 4.25 倍，OCR 与图表维度的收益是 0.6 分。**

### 5.2.2 但有一个必须加的反驳：一部分「推理更吃规模」是 benchmark 污染

Cambrian-1 §3.1 原文：

> SQA-I、**MMMU、MathVista、AI2D 在开启与关闭视觉输入之间的差距不到 5%**，
> 说明这些 benchmark 可能并不显著依赖视觉输入，而是**严重依赖底座 LLM**。
> ……而 MMVP 与 MME Perception 在关闭视觉后的表现明显差于随机猜测，说明强视觉接地在那里确实关键。

**也就是说：5.2.1 里「推理类 +11.8」有相当一部分其实是在量 LLM 本身，不是在量多模态能力。**
这条 caveat 必须和 delta 表一起引，否则会得出「买更大 LLM 就能提升 visual coding」的错误结论。

### 5.2.3 VL-RewardBench 看起来方向相反，实际是「位置依赖」

VL-RewardBench（2411.17451 §4.1）原文：

> 最显著的改善发生在基础感知任务上，例如 Qwen2-VL 从 7B 放大到 72B
> **把计数错误率降低了 18.2 个百分点（74.1% → 55.9%）**。
> 而推理任务的收益要温和得多，**放大带来的平均错误率下降只有 6.0%**。

同节还有：GPT-4o-mini 的 Existence 错误率 **67.9%**、Qwen2-VL-7B 的 Recognition 错误率 **80.9%**，
而 Reasoning 平均错误率只有 **41.8%** —— 「感知是瓶颈，不是推理」。

**怎么调和**：这篇量的是「作为 judge 的错误率」，起点极低（计数错 74%），
所以放大带来的绝对下降很大；而 5.2.1 的 OCR/doc benchmark **已经贴着天花板**（DocVQA 93→95）。
**结论是位置依赖的，不是能力类型依赖的**：

| 任务离天花板的位置 | 规模的边际收益 |
|---|---|
| 远离天花板的感知任务（计数、细粒度存在性判断、渲染图差异检测） | **大**（计数 −18.2pp） |
| 已接近饱和的 OCR / doc benchmark | **接近 0**（Cambrian-1 +0.6） |
| 推理 / 知识 benchmark | 大，但其中一部分是在量 LLM 而非多模态（5.2.2） |

**对本项目的直接含义**：我们的任务（判断渲染图与参考图的差异、读清截图里的文字、
判断场景里有几个物体）**恰好落在第一行** —— 远离天花板的细粒度感知。
04_verifier 已给了同向证据：渲染图差异检测上 GPT-4o 的 F1_hard 只有 25.0。
**所以在本项目上，规模可能比通用 OCR benchmark 显示的更有用。这是选型里最大的不确定项。**

### 5.2.4 GUI 定位上的饱和与分辨率

UI-TARS（2501.12326 §5.3）原文结论（表格数字在 HTML 里被剥空，**只引结论**）：

> 从 UI-TARS-2B 放大到 7B，三个 grounding 数据集上都有显著提升。
> 对比 7B 与 72B，**ScreenSpot v1 与 v2 没有显著变化，而 ScreenSpot Pro 有明显提升**。
> 这说明 ScreenSpot v1/v2 可能不足以刻画更高规模下的定位能力。

同节另一句：**「提高 ScreenSpot Pro 的输入图像分辨率带来了显著的性能提升」。**

**读法**：7B→72B 在简单 benchmark 上完全饱和，只有高分辨率的 ScreenSpot-Pro 还在吃规模；
而同一个 benchmark 上提分辨率也显著有效。**难点是分辨率，规模只是在代偿分辨率不足。**
这与 5.3 的 MM1 结论完全一致。

## 5.3 视觉编码器的规模 vs 分辨率：MM1 的排序

MM1（2403.09611 表 1、§3.1）固定 2.9B LLM（原文说明：故意不用 1.2B，
「以确保有足够容量去利用更大的图像编码器」），扫编码器与分辨率：

| 配置 | 0-shot | 4-shot | 8-shot |
|---|---|---|---|
| CLIP_DFN+VeCap **ViT-L @224** | 36.9 | 58.7 | 62.2 |
| CLIP_DFN+VeCap **ViT-H @224** | 37.5 | 60.0 | 63.6 |
| CLIP_DFN+VeCap **ViT-L @336** | **39.9** | 62.4 | 66.0 |
| CLIP_DFN+VeCap **ViT-H @336** | 40.5 | 62.6 | 66.3 |
| CLIP_DFN ViT-H @378 | 40.9 | 62.5 | 66.4 |

原文「Encoder Lesson」逐字：

> **图像分辨率影响最大，其次是模型规模与训练数据构成。**
> 把分辨率从 224 提到 336，所有架构上的所有指标都有**约 3% 的提升**。
> 把模型规模从 ViT-L 提到 ViT-H，**参数翻倍，性能提升通常不到 1%**。

以及 §1 的总排序：

> 重要性依次是：**图像分辨率、视觉编码器的 loss 与容量、视觉编码器的预训练数据**。
> 但令人意外的是，我们**几乎没有找到证据表明「视觉数据如何喂进 LLM」这个架构选择有影响**。

验算：ViT-L@224 → ViT-H@224 是 **+0.6**；ViT-L@224 → ViT-L@336 是 **+3.0**。原文结论与表格一致。

### 5.3.1 两条比「放大 ViT」便宜得多的杠杆

| 杠杆 | 数字 | 出处 |
|---|---|---|
| **换更好的同尺寸 ViT**（不是放大） | 固定 1.7B LLM、1.5T token，SigLIP-2 → Qwen3-ViT：OCRBench 77.2→**78.7**、AI2D 74.1→**76.2**、RealWorldQA 58.7→**66.1（+7.4）**、InfoVQA 65.3→**67.0** | Qwen3-VL 2511.21631 §5.12.1 表 8 |

**编码器专长分工的证据**（对本项目有用）：
Eagle §2.3 表 10 —— **Pix2Struct 在文字识别上最强但在物体识别与通用 VQA 上很弱**；
DINOv2 与 SAM 在文字识别上很差；EVA-02 在 POPE/GQA 最强。
Cambrian-1 附录表 22 佐证：在 DocVQA 这类文字密集高分辨率图上，**ConvNeXt 的注意力权重大幅上升**。
→ 前端截图（文字密集）与 three.js 渲染图（几何为主）**对编码器的要求不同**，这是混编码器的一个具体理由。

### 5.3.2 InternViT-300M → 6B 值多少分：**没有干净对照**

- InternVL 系的 ViT 换代（300M→6B）**始终与 LLM 规模同时变**（≤14B 用 300M，≥38B 用 6B），无法解耦。
- InternVL2.5 §1 只有一句跨族比较（不是消融）：「相比配 600M 视觉编码器的 Qwen2-VL-72B，
  我们配 6B 视觉编码器的 InternVL2.5-78B 只用 **1/10 的训练 token** 就能取得更好性能」。
- 勉强可比的一对（InternVL3.5）：30B-A3B（300M ViT）vs 38B（6B ViT）——
  OCR Overall 83.9 vs 84.6，Reasoning Overall 59.0 vs 66.0。**差异主要在推理侧**，不支持「大 ViT 大幅提感知」。
- **结论：公开论文里没有「同 LLM 下 ViT 300M vs 6B」的干净对照。** 本项目不要按这条做决策。

## 5.4 MoE：视觉 token 会不会走不同的专家

**答案取决于初始化方式，两篇给出干净的对照。**

| 工作 | 初始化 | 路由现象 |
|---|---|---|
| **MoE-LLaVA**（2401.15947 §4.4） | FFN **复制**初始化 + soft router | 「**文本与图像的路由分布高度相似**……MoE-LLaVA 的每个专家都能同时处理文本 token 与图像 token，这表明 **MoE-LLaVA 对任何模态都没有明显偏好**」。层级分工明显（17-27 层几乎被 expert 3 独占），但**模态分工没有** |
| **Uni-MoE**（2405.11273 §V） | **模态专属**预训练专家（Expert 1 = 原 MLP、Expert 2 = 图文训、Expert 3 = 图音训、Expert 4 = 音频） | 输入 audio-text 时 expert 2 与 4 **几乎独占**全部 token，expert 1/3 几乎无负载；image-text 也类似。图 5 标题：「**训练模态专属专家有助于专家分配的学习，促进专家特化**」 |

→ **同质初始化 ⇒ 视觉与文本 token 不分流；模态专属初始化 ⇒ 强分流。**
Kimi-VL（2504.07491）与 DeepSeek-VL2（2412.10302）**都没有做路由分析**，只有架构配置
（DeepSeek-VL2：routed experts 64/64/72、shared 2、Top-K=6、VL2 加 expert correction bias 做负载均衡）。

### 5.4.1 一个 MoE 的反例：总参数不等价于稠密参数

从 InternVL3.5 表 3/4 自算：

| 模型 | OCR Overall | Reasoning Overall |
|---|---|---|
| InternVL3.5-8B（稠密） | 81.2 | 60.3 |
| InternVL3.5-14B（稠密） | 82.0 | **62.0** |
| InternVL3.5-20B-A4B（MoE，GPT-OSS-20B 底座） | 81.7 | **56.0** |
| InternVL3.5-30B-A3B（MoE） | 83.9 | 59.0 |

**20B-A4B 的推理分（56.0）低于 14B 稠密（62.0），甚至低于 8B 稠密（60.3）。**
30B-A3B 的 59.0 同样不如 14B 稠密。
→ **在多模态推理上，激活参数量比总参数量更主导。** 选 MoE 时要按激活量对标稠密模型，不要按总参数。

## 5.5 固定算力下「更大的底座」vs「更好的数据和 verifier」

### 5.5.1 先说结论：**没有公开的直接对照实验**

没有任何一篇论文做了「固定总算力，一路加大底座 vs 一路投到数据与 verifier」的对照。
下面全是**单边证据**，每条都标明它到底对照了什么。

### 5.5.2 最接近的量化横向：ScaleRL

ScaleRL（2510.13786 附录 A.13 表 1；A = 渐近 pass rate，B = 算力效率指数，C_mid = 达到一半增益的算力点；
**A 的经验误差 ±0.02**，三次独立 run）：

| 实验 | C_mid | B | **A** |
|---|---|---|---|
| ScaleRL（8B 稠密，默认配方） | 2,542 | 1.92 | **0.610** |
| ScaleRL-32k（8B，生成长度 32k） | 11,272 | 1.89 | 0.645 |
| ScaleRL-bs2048（8B，大 batch） | 10,909 | 1.70 | 0.645 |
| **ScaleRL-Scout（Llama-4 17B×16 MoE）** | 4,242 | **1.65** | **0.710** |

原文（§5）：

> 用 ScaleRL 训练 17B×16 的 Llama-4 Scout MoE 展现出**与 8B 模型相同的可预测扩展行为**……
> 这些扩展点与拟合曲线一致，支持我们配方的**模型规模不变性**。
> 而且，**更大的 17B×16 MoE 的渐近 RL 性能远高于 8B 稠密模型，只用后者 1/6 的 RL 训练算力就超过了它。**

**我做的横向（非原文）**：
- 在 8B 上把 RL 超参轴拉到最优：A 从 0.610 → **0.645**，即 +0.035（误差 ±0.02，勉强显著）。
- 换成 17B×16 MoE：A 从 0.610 → **0.710**，即 **+0.100**。
- **换规模的收益约为换超参的 3 倍。**
- 但代价是：Scout 的 **B 更低（1.65 vs 1.92）、C_mid 更高（4,242 vs 2,542）** ——
  **大模型起步更慢、在低算力区间更差，但天花板高很多。**
  这与 §A.12 的 batch 观察同形：「小 batch 在低算力预算下更好，大 batch 达到更高的渐近值」。
- **关键限定：ScaleRL 全程用同一批可验证的 math/code 数据和同一个规则 verifier，没有做数据或 verifier 的消融。**
  所以它对照的是「RL 超参轴 vs 模型规模」，**不是**「数据/verifier vs 模型规模」。

另一条让人警惕的数字（§3.2）：单项消融里，**把 LM head 改成 FP32 把 A 从 0.52 推到 0.61（+0.09）**，
和换规模同量级；但 §4 的 leave-one-out 里这一项影响很小。
→ **「方法」的收益高度依赖基线有多烂。** 在一个已经调好的基线上，方法轴的空间远小于规模轴。

### 5.5.3 但在视觉编码这个具体任务上，数据管线的单边收益远大于规模

| 对照 | 数字 | 出处 |
|---|---|---|
| **固定 9B 基座，只加数据与训练阶段** | Design2Code：GLM-4.1V-9B-Base **9.0** → +持续预训练（约 10M 图-码对）**53.3** → +SFT **79.3** → +RL（RVPO）**88.6**，合计 **+79.6** | 2511.08195 表 11 |
| 同族放大 10 倍（同一张表上的对照） | Design2Code：InternVL3-9B 15.3 → 78B **30.0**（×8.7 参数，+14.7）；Qwen2.5-VL-7B 29.1 → 72B **41.9**（×10，+12.8） | 2511.08195 表 1，**自算 delta** |
| **规模完全不变，只换数据与配方** | ScreenSpot-Pro：**Qwen2-VL-72B 1.6 → Qwen2.5-VL-72B 43.6**。原文：「远超其基座 Qwen2-VL-72B 的 1.6%」 | 2502.13923 §3.3.6 表 9 |
| 9B 打过闭源前沿 | UI2Code^N-9B-RL 在 6 个 benchmark 里 3 个胜出：Flame **95.0**（GPT-5 91.3）、UI2Code-Real **76.5**（GPT-5 67.8）、UIPolish-Syn **94.0**（GPT-5 68.0） | 2511.08195 表 1 |

**在 Design2Code 这一个指标上把两边摆在一起**：
固定 9B 基座的数据管线值 **+79.6 分**，而同族放大 10 倍值 **+12.8 ~ +14.7 分**。
**这是本项目范围内「数据 vs 规模」最硬的一组数字**，差 5~6 倍。
但必须声明三点限定：
1. 这**不是固定算力的对照** —— UI2Code^N 的 10M 图-码对持续预训练本身很贵（约 20M 图-码样本）。
2. 基座起点是 9.0 分，**离天花板极远**；在已经 80 分的位置上，同样的数据管线不会再有 +79.6。
3. 两条曲线最终会合并：UI2Code^N 的路线也可以在 32B 上跑，没人做过这个实验。

### 5.5.4 蒸馏与 RL：两条路都依赖「存在一个更强的教师」

| 对照 | 数字 | 出处 |
|---|---|---|
| **同一个 8B ckpt，换后训练方法** | +RL：**17,920 GPU 小时** → AIME'24 **67.6**（pass@64 **90.0**）；+on-policy 蒸馏：**1,800 GPU 小时** → **74.4**（pass@64 **93.3**） | Qwen3 2505.09388 表 21 |
| **同规模，蒸馏 vs 大规模 RL** | Qwen2.5-32B-Base 上跑 >10K 步 math+code+STEM RL（Qwen2.5-32B-Zero）AIME'24 **47.0**；R1-Distill-Qwen-32B **72.6** | DeepSeek-R1 2501.12948 表 16 |
| 蒸馏的规模饱和（自算） | R1-Distill-Qwen AIME'24 pass@1：1.5B→7B **+26.6**、7B→14B **+14.2**、**14B→32B +2.9**；32B 72.6 vs Llama-70B 70.0 | 2501.12948 表 15 |

**两条必须一起读的原文**：

- Qwen3 §6.3：**「RL 不提升 pass@64」**（90.0→90.0、83.3→83.3），而蒸馏提升（→93.3、→86.7）；
  原因是「从教师 logits 蒸馏让学生模型能扩展其探索空间」。
- DeepSeek-R1 附录 F.1：「首先，把更强的模型蒸馏进小模型效果极好，
  而**小模型依赖本文所述的大规模 RL 需要巨大算力，甚至可能达不到蒸馏的效果**。
  其次，蒸馏策略既经济又有效，但**要突破人类智能的边界，仍可能需要更强的基座模型与更大规模的强化学习**。」

→ **这不是「数据打败规模」，而是「规模的成本可以被搬到一次性的教师训练上」。**
而且 **RL 只收紧已有分布，蒸馏才搬进新能力** —— 这条在选底座时比任何 benchmark 分数都重要：
如果底座的 pass@k 里根本没有正确答案，RL 救不回来。

### 5.5.5 「verifier 质量相当于把模型放大多少倍」：没有换算

没有任何公开工作给出这种换算。最接近的三条：

| 来源 | 内容 | 差什么 |
|---|---|---|
| Web-Shepherd 2505.15277 | 3B PRM vs GPT-4o-mini 当 verifier：+10.9 分、成本低 10 倍 | policy 规模固定，无「等价放大多少倍」 |
| Let's Verify Step by Step 2305.20050 | 过程监督在**所有数据收集规模下**都胜过两种结果监督；过程监督模型解出 MATH 代表性子集的 **78%** | 大小两个 scale 的 generator 不同，原文明确说「因此这些模型不适合做 apples-to-apples 比较」 |
| Skywork-VL Reward 2505.07263 | 7B 专训 RM 73.1 > 78B 通用 63.3 | 量的是 judge 自身规模，不是省下多少 policy 规模 |

**所以这一问的诚实答案是：这条链上只有「专训小 verifier 打过通用大模型当 verifier」的单边证据，
没有任何工作给出 verifier 质量与模型规模的等价换算。**

| **分辨率 / 像素预算** | **按 InfoVQA 曲线外推，不按 TextVQA / ChartQA** | DocVQA / InfoVQA 吃满分辨率（+9.6 ~ +33.7），而 ChartQA 728² 后只 +0.3、TextVQA 896 后饱和（§2.1、§2.1.1）。GUI 社区默认的约 1M 像素，在 1280×6000 上只剩 **448~672 px 宽**（§2.2） | **低**（曲线侧）/ **中**（外推到长截图侧） |
| **单图视觉 token 预算** | 当前视口 **约 1,550**（1440×900）；三维场景 contact sheet **约 2,738**（2048×1024）；要原生 1280 宽的长图需 **约 9,800** | §3.1 实算（已用官方表校验 10 格中 9 格一致）；§2.2 按 Qwen2.5-VL 公式 | **低**（算式确定） |
| **每条轨迹视觉 token 上限** | **10 万**（40 步约 8 万的 1.25 倍余量） | §3.3 分档表 | 中（步数假设） |
| **同时在上下文里的图像张数** | **≤ 3 张（policy）/ ≤ 5 张（judge）**，硬上限 **16 张** | OpenCUA 实测 3→5 只有边际收益、多约 3K token（§1.1.1）；**开源 8B 级 VLM 在 20~50 张崩到随机**（Visual Haystacks，§4.1.7）；开源 LMM 超 16 帧不再提升（LongVideoBench） | **中高**。但**全部来自自然图 benchmark，没有一条在渲染图上测过** |
| **文本上下文窗口** | **32K 下限、64K 够用、128K 是余量**；**不要为 256K 付溢价** | 成功轨迹 95 分位 **39.5K**（SWE-Gym 表 8）、单轮峰值 30~65K（§4.1.1-2）；真 160K 窗口对 80K+压缩是 **59.5 对 59.8，打平**（CompactionRL，§4.2.3） | **低** |
| **上下文管理** | **observation masking（只留最近 N 个工具结果），N 从 5 起调**；先不做 LLM 摘要 | SWE-agent：Last-5 比完整历史 **+3.0 分**（§4.2.2）；Complexity Trap：5 组里 4 组 masking 最省且不输摘要（§4.2.1）。**N 不可跨 scaffold 搬**（SWE-agent 10 → OpenHands 58） | **低** |
| **渲染结果怎么进上下文** | **程序化断言为主、图为辅，两路交叉核对** | 图针 **22.4** 对文针 **88.4**（MM-NIAH，§4.1.7）；但闭集结构图单独用会欠载（GraphEQA **13.6 / 45.7 / 63.5**，§1.3.4） | 中（GraphEQA 有混淆） |
| **要不要先上 RL** | **先问有没有更强的教师。** 前端优先蒸馏；three.js 复刻类 RL 信号最干净 | Qwen3 表 21：RL **17,920 GPU 小时 → 67.6**，on-policy 蒸馏 **1,800 → 74.4**（§5.5.4）。且 **RL 不提升 pass@64**，蒸馏提升 | **低**（但限定在同规模换方法） |

## 6.2 一句话配置

> **9B 级原生分辨率多模态稠密底座（GLM-4.1V/4.6V-9B 或同级），
> 64K 文本上下文，当前视口一张 1440×900（约 1,550 token）、历史滑窗 3 张低分辨率，
> 单条轨迹视觉 token 上限 10 万，observation masking N=5，
> scene graph 走摘要而非转储、与视觉通道交叉核对。**

## 6.4 选型之前必须做的三个实验

这三个实验都是半天到一天的量级，能把上表里标「中」的几行变成实测。

| # | 实验 | 要回答什么 | 为什么现在没有答案 |
|---|---|---|---|
| 1 | **渲染图的多图崩溃点**：取一个 three.js 场景，生成 N = 1/3/8/16/32 张多视角图，问「哪一张里缺了鼻子」 | 6.1 的「同时 ≤ 3 张、硬上限 16 张」到底对不对 | **所有多图数字都来自自然图 benchmark，没有一条在渲染图上测过**。渲染图纯色背景多、结构重复，崩溃点可能更早也可能更晚 |
| 2 | **长截图的有效宽度**：对同一个页面，分别送整页长图 / 纵向切片 / 不同 `max_pixels`，看模型能否正确读出小字号文案 | §3.2 的「整页长图只有 20% 宽度保真」在目标底座上的实际后果 | §3.2 是按官方算式推的，**没有在具体底座上验证过模型到底读不读得出来** |

## 交付后的更正（2026-10-15）

上游调研 agent 在本文定稿之后补抓到了 GLM 系的像素面积上限，所以下面两处「未公开 / 未核实」的说法要撤回：

  §5 里「优势有多少来自分辨率策略无法分离」这一句的前提也随之消失。

一处限定要保留：该实现里的 `shortest_edge / longest_edge` 字段**语义是面积不是边长**，
这一点来自读实现代码的推断，官方文档没有写明。引用时要带上这个限定。
