# 本地实验：three.js 可验证任务的 verifier 与自动造题

代码：`/mmu_mllm_hdd_4/deep-research/visual-coder-blog/scripts/vc_verifier/proto/`
结果：同目录 `runs/`，每个数字都能用下面的命令重跑。
机器：无 GPU，Chrome 148 无头 + SwiftShader 软渲染。

---

## 0 结论先行

1. **单张截图做 reward 是不够的，但不是因为 VLM 看不懂，而是因为像素指标看不懂。**
   同一批 case：逐像素相似度判对 5/13，多模型 VLM 投票判对 18/18。
   真正的问题是像素指标和 VLM 各有不同的盲区，而且 VLM 单次判定会翻面。
2. **3D 场景的可靠信号来自运行时状态，不是图。**
   四层程序化 verifier 在 29 个带标签变异上 29/29，且每层都能指出挂在哪，这是 VLM 给不出的。
3. **「抓场景」不需要模型配合。**
   利用 three.js 自带的 `__THREE_DEVTOOLS__` 事件，页面无论用 CDN、importmap 还是把 three 整个打包进去，都能拿到 scene 和 renderer。
4. **自动造题的关键不是「造」，是「准入」。**
   LLM 提的破坏里有 6%~12% 是 verifier 根本看不出来的；准入测试把它们挡在数据集外，比事后发现噪声便宜得多。
5. **最容易被忽视的坑：verifier 查了问题描述里没给的信息。**
   预实验里模型的两次失败全是这个原因，不是能力问题。这类任务进了 RL 就是纯噪声。

## 1 Harness：怎么从一个页面里把 3D 场景拿出来

### 1.1 做法

`harness.js` 在页面脚本执行前注入三样东西：

- **场景捕获**：预先定义 `window.__THREE_DEVTOOLS__ = new EventTarget()`。
  three 的 `Scene` 与 `WebGLRenderer` 构造函数里都会向它派发 `observe` 事件（见 three r160 源码 `three.module.js` 第 30938、31088 行）。
  监听到 renderer 后包一层 `render`，就能记下页面每一帧渲染的是哪个 scene 和哪个 camera。
- **冻结时钟**：接管 `requestAnimationFrame`、`performance.now`、`Date.now`、`Math.random`，
  帧只在 harness 调 `__vcStep(n, dt)` 时推进。同一页面重复探测逐字节一致。
- **断网**：除了 three 本身，所有外部请求一律拦掉，页面从内存里的 URL 加载。

### 1.2 为什么不要求模型暴露全局变量

常见做法是让模型写 `window.__SCENE__ = scene`。两个问题：

- 训练时模型会学会「写这一行就行」，评测换个 harness 就失效；
- 模型可以伪造这个对象，而伪造 `__THREE_DEVTOOLS__` 事件没有意义，因为事件是 three 自己发的。

### 1.3 实测：打包版页面也能抓到

把 three 源码整个内联进 `<script type="module">`，页面不发任何网络请求：

```
node harness.js tasks/snowman_bundled.html runs/t_bundled
→ {"meshes":4,"renders":31,"errors":[],"ms":1025}
```

和 CDN 版结果一致（meshes 4、体素完全相同）。

### 1.4 一个要注意的点

`WebGLRenderer` 默认 `preserveDrawingBuffer: false`，所以 `canvas.toDataURL()` 必须和 `render()`
在同一个同步任务里执行，中间不能 await，否则会截到空白。探针里是同步循环，所以没问题。

### 1.5 探针读了什么

| 产物 | 内容 | 用途 |
|---|---|---|
| 场景图 | 每个可见 mesh 的几何类型、顶点数、世界包围盒、主色；灯光类型列表 | 结构化断言、喂给模型当文本反馈 |
| 9 视角渲染 | 8 个方位角（仰角 15 度）+ 1 个俯视，相机由场景包围盒自动定 | 剪影 IoU |
| 同 9 视角剪影 | `overrideMaterial` 换成纯白 + 黑背景 | 不受材质、光照、背景影响 |
| 页面相机 1 张 | 页面自己设的相机 | 对照组，模拟「只截一张图」 |
| 48³ 体素 | 每个 mesh 单独沿 +z 射线，按穿越次数奇偶判内外，体素记该 mesh 的主色 | 占据与颜色，与建模手法无关 |

单次探测约 0.8~1.0 秒，含启动浏览器。

## 2 Verifier：四层，以及每层补上了什么

```
L0 执行门    页面报错 / 没渲染出任何 mesh                       → fail
L1 多视角剪影 9 个视角，双面剪影（外轮廓）与单面剪影（破洞、反面片）
             各取最差一个 < 0.9                                → fail
L2 体素占据   按颜色的全局 IoU（主色 < 0.9 或其它色 < 0.5）
             或 6³ 分块后最差块 IoU < 0.5                      → fail
L3 部件与拓扑 按颜色的体积比偏差 > 25% 或连通块数不等；
             或开放边界边数明显多于参考                        → fail
```

开放边界边数 = 只被一个三角面用到的边。闭合实体是 0，破洞或开口面片大于 0。
它是拓扑量，不随洞的大小衰减，所以能抓住被全局 IoU 淹没的小破洞（见 3.2）。

颜色做了就近归并：候选的颜色与参考调色板 RGB 距离小于 60 的算同一色，
所以轻微调色不算错，换一个色系仍然算错。

### 2.1 判别力：29 个带标签的变异

对两个场景（雪人、桌子加杯子）各写一组变异，人工标注「该挂」还是「不该挂」：

- **该挂**：部件缺失、挪位、朝向反、比例变、颜色换、杯子悬空或陷进桌面。
- **不该挂**：网格精细度、光照强弱、背景色、相机机位、轻微色差、尺寸 ±5%。

| 信号 | 雪人 13 例 | 桌子 16 例 | 合计 |
|---|---|---|---|
| 页面单张截图逐像素相似度 | 5 | 7 | 12/29 |
| 几何类名多重集一致（朴素断言） | 6 | 8 | 14/29 |
| 多视角剪影 IoU | 9 | 10 | 19/29 |
| 按颜色体素 IoU | 11 | 14 | 25/29 |
| **四层组合** | **13** | **16** | **29/29** |

补齐单面剪影与拓扑信号后重跑，仍然是 13/13 和 16/16，没有新增误杀。

复跑：

```
python3 mutate.py snowman   # 13 例
python3 mutate.py table     # 16 例
python3 blockiou.py         # 分块 IoU
```

### 2.2 每一层解决了什么，证据是什么

| 层 | 没有它会漏掉 | 具体例子 |
|---|---|---|
| L1 多视角 | 单视角看不见的错误 | 雪人鼻子长在后脑勺：页面截图相似度 0.999，剪影 0.981，但多视角里背面一看就错 |
| L2 分块 | 小部件的局部缺陷 | 桌子一条腿短 30%：全局剪影 0.96、体素 0.981 都过关，分块后最差块只有 0.167 |
| L2 按色 | 颜色错 | 杯子变成木色：剪影 1.0、分块 1.0，但该色体素 IoU 为 0 |
| L3 连通块 | 细长部件 | 显示器立杆删掉：剪影 0.989、分块 0.914 都过，连通块数 7 变 6 |
| L3 拓扑 | 小破洞 | 用 LatheGeometry 转出的雪人顶部没封口：剪影 0.997、单面剪影 0.958、体素 0.995 全过，开放边界 0 变 64 |

### 2.3 留出测试：第三个场景，阈值一个不动

前两个场景的 29/29 要打折扣，因为阈值在它们身上看过。所以又做了一次干净的留出测试：

- 新场景是一辆小车（9 个 mesh：底盘、车厢、斜风挡、4 个轮子、2 个前灯）。
- 18 个变异和它们的标签**先写死再跑**，只跑一次，阈值沿用前两个场景，一个没调。

结果 **18/18**。三个场景累计 47/47，其中 18 个是真正留出的。

每一层在留出集上都确实有用，不是摆设：

| 变异 | 挂在 | 为什么别的层抓不到 |
|---|---|---|
| 前灯少一个 | L3 部件 | 剪影 0.998、分块 0.924、该色体素 0.5 都在阈值之上；只有连通块数 2 变 1 抓到 |
| 风挡挪到车尾 | L2 按色 | 剪影 0.992，外轮廓几乎没变；但玻璃色体素 IoU 为 0 |
| 风挡改成车身色 | L2 按色 | 剪影和分块都是 1.0，形状完全没动，只有颜色没了 |
| 少一个轮子 | L2 分块 | 全局剪影 0.903 刚好在阈值之上，分块最差块 0.0 |
| 轮子轴向转 90 度 | L1 剪影 | 外轮廓就变了 |

最接近误杀的一例是「轮子半径 +4%」：分块最差块 0.727，阈值 0.5，还有余量。

### 2.4 阈值是怎么定的（要打的折扣）

- `mv_min 0.9`、体素 `0.9 / 0.5`：在雪人上定，在桌子上复验未调。
- `blk_min 0.5`：在两个任务上各扫了 0.5 / 0.6 / 0.7，三档结论一致，取最松的。**这一项等于在变异集上看过一眼**。
- 颜色容差 60：是看到「轻微调色被误杀」后加的，同样在变异集上调过。
- 所以前两个场景的 29/29 要打折扣。2.3 的留出测试就是为此补的，结论是阈值迁移得住。

## 3 VLM judge：和程序化 verifier 比

把参考与候选的渲染图上下拼成一张交给 VLM，判 pass 还是 fail。两种看图条件：

- **single**：各一张页面相机视角。
- **multi**：各 4 个视角（正面、90 度侧、背面、俯视）。

48 个 case（雪人 5 个候选 + 13 个变异、桌子 16 个变异、桌面工作台自动生成的 16 个缺陷），
4 个 judge，每个 case 每种条件跑 2 次，temperature 0，共 768 次判定。

| judge | 单视角判对 | 多视角判对 | 单视角重测翻面 | 多视角重测翻面 |
|---|---|---|---|---|
| gpt-6-astra | 84/95 | 92/96 | 16.7% | 4.2% |
| gemini-3.8-flash | 88/96 | 92/96 | 8.3% | 0.0% |
| doubao-seed-2.1-pro | 78/91 | 81/84 | 6.2% | 8.3% |
| claude-opus-5-5 | 76/96 | 74/93 | 16.7% | 20.8% |
| 4 模型 8 票多数投票 | 44/48 | 46/48 | — | — |

分母不足 96 的是没能解析出结论的次数（模型没按格式输出）。

复跑：`python3 vlm_judge.py` / `python3 analyze.py judge`

### 3.1 这一节的结论推翻过一次

最早只跑了 18 个 case，看到多视角判对率不升反降，写下了「多视角对 VLM 无效」。
扩到 48 例、并修正一处人工标注错误之后结论反过来。记在这里是因为这个教训比结论本身更有用：
**18 个样本上的方向性结论不可信。**

逐 case 配对比较：单视角赢 11 例、多视角赢 27 例。
把每个 judge 的每个 case 当独立配对做 McNemar 得 p=0.015，但这高估了独立性，
因为 4 个 judge 判的是同一批 case；逐模型单独看没有一个到显著（p 从 0.13 到 0.61）。
所以能说的是「多视角不差于单视角，对强 judge 更好」，不能说「多视角一定更好」。

### 3.2 VLM 比像素指标强得多，但单次判定不能用

同一批 case，逐像素相似度 12/29，而单模型 VLM 是 74 到 92（分母 84 到 96）。
像素指标判不出「鼻子不见了」，因为鼻子只占几十个像素。

但同一个模型、同一张图、温度 0 跑两次，最差一档有 20.8% 的 case 会翻面。
多视角把两个最强 judge 的翻面率从 16.7% 压到 4.2%、从 8.3% 压到 0，但对 opus 没用。

### 3.3 投票也救不回全部，漏的是定量偏差

4 模型 8 票投票在 48 例上单视角 44 对、多视角 46 对，而程序化信号在它自己的标注集上是 47/47。
投票漏掉的几例是同一类错误：

| 漏判的 case | 票型 | 程序化信号怎么抓到的 |
|---|---|---|
| 一条桌腿缩到 70% | 8 票全判通过 | 分块体素最差块 0.167 |
| 桌面厚度减到三分之一 | 5 票判通过 | 按色体素 0.528 |
| 屏幕卷曲 | 4 比 3 判通过 | 分块体素 0.066 |
| 灯臂镜像 | 多视角 4 比 2 判通过 | 部件连通块数 7 变 8 |

数据解读：VLM 擅长「有没有这个东西」，不擅长「这个东西的尺寸对不对」。
定量几何偏差正是程序化信号最强的地方，两者的盲区是互补的。

### 3.4 一次翻案：VLM 对，我标错了

最早被记成「多视角投票判错」的是 `ok_lathe`：用 LatheGeometry 把三个球的轮廓一次转出来。
我把它标成 pass，因为它外观和参考一致、只是建模手法不同。

多视角条件下 8 票里 7 票说它有问题，而单视角条件下投票判它通过。
后来把俯视图放大看，**它头顶真的有一个洞**，LatheGeometry 在极点没有封口——那个洞只在俯视图里看得见。

这件事值三条结论：

- **人工标签不是金标准。** 标注者和自动指标会在同一个地方同时瞎掉。
- **当时的程序化 verifier 对它结构性失明**：双面剪影把洞填上了（`overrideMaterial` 用的是
  `DoubleSide`），换成单面剪影后 IoU 只从 0.997 掉到 0.958，因为洞只占几十个像素；体素 IoU 0.995 同理。
- **修法不是调阈值，是换一个不随尺寸衰减的量。** 加了开放边界边数之后，
  参考是 0、它是 64，直接判挂。加这个信号后两个变异集仍然 13/13 和 16/16，没有新的误杀。

也就是说，VLM judge 和程序化 verifier 是**互补**关系：
VLM 能发现「这里不对劲」但说不清是什么；程序化信号能精确指出哪一项超了，但要先有人想到查这一项。
**VLM 的价值是帮你找到该加哪条程序化检查**，而不是直接当 reward。

## 4 自动造题与准入测试

`gen_tasks.py`：给一个能跑的页面，让 LLM 提 N 个**语义性破坏**（SEARCH/REPLACE 加一句用户视角的需求），
应用后做准入测试，三条全过才收：

1. 参考解必须过 verifier（自比自，防 verifier 本身坏掉）；
2. 破坏版必须被判挂（否则这个破坏不可验证）；
3. `search` 片段必须在源码中唯一（防止改到别处）。

| 场景 | LLM 提 | 收 | 弃 | 弃的原因 |
|---|---|---|---|---|
| 桌子加杯子 | 10 | 9 | 1 | 杯子倒置：杯子是圆台，翻转后占据几乎不变，verifier 看不出 |
| 桌面工作台（13 个 mesh，带层级和旋转） | 16 | 14 → **16** | 2 → 0 | 显示器立杆缺失、灯臂镜像：加 L3 连通块后都能抓到 |

两点值得记下来：

- **准入测试的产出不只是任务，还是 verifier 的体检报告。**
  被弃掉的 case 精确指出了 verifier 的盲区（圆台翻转、细长部件），
  其中细长部件这条直接催生了 L3。
- **先造题再补 verifier，比先定 verifier 再造题有效。**
  盲区是被具体 case 逼出来的，不是设计阶段想出来的。

### 4.1 收下来的 16 个任务按挂在第几层分布

| 挂在 | 个数 | 典型 |
|---|---|---|
| L1 多视角剪影 | 6 | 桌面下沉、腿悬空、少两条腿、腿跑到桌面外、显示器压在键盘上、屏幕竖过来 |
| L2 体素 | 8 | 屏幕卷起、键盘立起、键盘变屏幕色、杯子悬空、杯子换边、灯头立起、灯头脱落、灯头挂错父节点 |
| L3 部件 | 2 | 显示器立杆缺失、灯臂镜像 |

层级分布本身就是难度分布的粗略代理：挂在 L1 的是一眼可见的粗错，挂在 L3 的是细节错。

## 5 一个必须避免的坑：verifier 比问题描述知道得多

预实验里 opus-5.5 在 9 个桌子任务上一轮过 7 个。两个没过的，查下来都不是模型的问题：

| 任务 | 需求原文 | verifier 要求 | 结果 |
|---|---|---|---|
| cup-wood-color | 「杯子应使用有别于桌面木色的独立颜色」 | 必须恰好是参考里那个蓝（0x3a9ad9） | 模型选了另一种颜色，该色体素 IoU 为 0，判挂 |
| legs-centered | 「桌腿应位于桌面四个角落附近」 | 腿的位置要和参考几乎重合 | 模型把腿放到角上但缩进量不同，剪影 0.885 差一点点，判挂 |

**结论：verifier 能查的信息量必须小于等于问题描述给出的信息量。** 两条解法：

- 把参考渲染图放进问题描述，让它变成复刻任务（信息补齐）；
- 或者把 verifier 放松到与描述同样的精度（例如「颜色和木色的距离大于阈值」而不是「等于某个蓝」）。

第一条更好做也更可扩展，而且正好对应「Problem Statement 带多模态参考」这个设定。
这条在实验矩阵里作为独立的一维（text 与 text+参考图）来测。

## 6 一道 0% 的题，查出两个独立的问题

16 个自动生成的修复任务里，有一道所有模型在所有条件下全军覆没，32 组全挂。
按本文自己的规则，0% 通过率的第一嫌疑是 verifier，不是模型。查下来确实是，而且是两个叠在一起的问题。

那道题要求「台灯的灯罩应该斜着朝向桌面中心」。

### 6.1 第一个：开口曲面的体素化无效

把模型产物的场景图和参考解逐项对比，包围盒几乎逐位相同，而该颜色的体素重合度只有 0.017。

原因在体素化的实现。判断一个体素在物体内部，用的是沿一个方向打射线、数穿过表面的次数、按奇偶判内外。
这套方法的前提是网格闭合。那个灯罩是一个**开口的圆锥面**，没有内部可言，奇偶计数给出的结果几乎是任意的，
朝向稍微一动，被判为「内部」的体素就整体换一批。

修法是按网格是否闭合分流：闭合的照旧用奇偶填充，不闭合的改成记录表面经过的体素。
闭合与否本身就是已有的拓扑量，也就是前面用来抓破洞的开放边界边数，不需要新增测量。
改完之后三个带标签的变异集重跑，仍然是 13/13、16/16、18/18，没有新增误杀。

### 6.2 第二个：修完之后这道题还是 0%

这是最该记住的一半。修好体素化之后重测同一批候选，该颜色的重合度变成 0.023 到 0.105，仍然全挂。

把参考解和候选并排渲染出来看，两者的灯罩都是斜着朝下、朝桌面中心的锥体，只是倾角与朝向不同。
按题面「斜着朝向桌面中心」的说法，两者都对。

真因有两条，都和 bug 无关：

- **题面没有钉死朝向**，而 verifier 要求和参考几乎重合。这是本文反复讲的那条——verifier 能查的信息量必须小于等于题面给出的信息量。
- **灯罩在 48 的体素网格下只占 20 个体素**。这个规模上的 IoU 已经退化成「位置是否精确相等」，
  任何可见的朝向差都会让它掉到 0 附近。**小部件上的占据类指标不是相似度，是等值判断。**

### 6.3 三条可带走的结论

- **假阳性比假阴性难发现得多。** 漏判会在抽检里暴露，误杀只表现为「这题好难」。
  一道 0% 的题是 verifier 的体检报告，不是模型的成绩单。
- **跑策略比跑变异更能查出 verifier 的毛病。** 变异集是我们自己造的，手法和参考解同源；
  模型会用我们没想到的方式实现同一个形状，正好撞出盲区。这一道题一次撞出了两个。
- **修完第一个问题不等于问题解决了。** 如果当时只看到体素化那个 bug 就收工，
  这道不可解的题会原样留在数据集里，而且因为通过率稳定为 0，难度筛选还会优先保留它。

同类问题在图表那条线上也独立出现过三次，全部是假阳性，全部与坐标系或帧有关，也全部不是阈值问题。

## 7 实验矩阵：自我修正只在「有东西可比」时才发生

16 个自动生成的修复任务 × 4 个模型 × 4 种反馈 × 2 种问题描述，每个最多 3 轮，每轮用同一个 verifier 判定。
模型看不到判定理由，只能看到自己产物的渲染结果。

- **问题描述**：纯文本需求 / 文本加参考解的 4 视角图。
- **反馈**：无反馈一次成型 / 页面相机一张图 / verifier 的 4 视角拼图 / 场景图文本。

基础设施故障（网关断连、返回体缺字段）单独剔除，不计入分母——这正是前面讲 RL 配方时
「预算耗尽、环境故障、模型自己的错」三分法在本地的落实。283 组有效。

| 问题描述 | 反馈 | 首轮通过 | 末轮通过 |
|---|---|---|---|
| 纯文本 | 无 | 19/39 = 49% | 19/39 = 49% |
| 纯文本 | 页面一张图 | 20/34 = 59% | 21/34 = 62% |
| 纯文本 | 4 视角拼图 | 21/33 = 64% | 21/33 = 64% |
| 纯文本 | 场景图文本 | 22/33 = 67% | 23/33 = 70% |
| 文本加参考图 | 无 | 23/39 = 59% | 23/39 = 59% |
| 文本加参考图 | 页面一张图 | 25/37 = 68% | 29/37 = 78% |
| 文本加参考图 | 4 视角拼图 | 25/35 = 71% | 31/35 = 89% |
| 文本加参考图 | 场景图文本 | 24/33 = 73% | 25/33 = 76% |

### 7.1 两个结论

**第一，参考图把首轮通过率抬了约 8 到 10 个百分点。**
同样是无反馈一次成型，纯文本 49%，加参考图 59%。这是问题描述的信息量值多少钱的直接计价。

**第二，更重要的是：首轮挂掉之后能不能救回来，几乎完全由「有没有参考图」决定。**

| 问题描述 | 页面一张图 | 4 视角拼图 | 场景图文本 |
|---|---|---|---|
| 纯文本 | 1/14 | 0/12 | 1/11 |
| 文本加参考图 | 4/12 | 6/10 | 1/9 |

数据解读：纯文本描述下，三种反馈合计救回 2/37，约 5%；给了参考图之后是 11/31，约 35%。
4 视角拼图这一格最极端，从 0/12 变成 6/10。

**模型不是不会改，是不知道该改成什么。** 让它看自己的产物，只有在它手里有一个可比对象时才有用。
这和公开文献的方向一致：没有外部判据的自我修订，对前沿模型接近零，对开源模型是负收益。

### 7.2 再加一个对照：只告诉它「哪一类不对」

前面四种反馈都只给产物，不给判定。加第五种：产物的 4 视角拼图，外加 verifier 判出的那一层的**名字**，
不给阈值也不给数值。层名被翻译成一句人话，例如「物体的占位或颜色不对」「部件的数量、体积或连通关系不对」。

这一臂用的是修好开口曲面之后的 verifier，和它同一轮跑的 multi 臂一起看才同口径：

| 问题描述 | 反馈 | 首轮通过 | 末轮通过 | 首轮挂后救回 |
|---|---|---|---|---|
| 纯文本 | 4 视角拼图 | 6/16 | 7/16 | 1/10 |
| 纯文本 | 拼图加层名 | 40/62 | 44/62 | 5/22 |
| 文本加参考图 | 4 视角拼图 | 8/19 | 11/19 | 3/11 |
| 文本加参考图 | 拼图加层名 | 41/64 | 50/64 | 9/23 |

数据解读：两种描述下，加了层名都比只给图救回得多（10% 对 23%，27% 对 39%）。
层名不含任何「怎么改」的信息，它只说出「哪一类不对」。
**模型缺的不是修改能力，是判断能力。**

这和前一小节是同一个结论的两面：

- 给它一个**可比对象**（参考图），它能自己判断，于是能改对。
- 给它一个**外部判断**（层名），它不需要自己判断，也能改对。
- 两样都不给，只让它看自己的产物，救回率接近零。

公开文献里最接近的一组是 BlenderAlchemy 的拆解：视觉通道的增益里，给评估器看图占 84%，给生成器看图只占 16%。
本节的四格数据是同一件事的另一种测法。

要打的折扣：multi 那两行的分母只有 10 和 11，因为这一轮没跑完；
前一小节那组更大的 multi 样本（0/12 与 6/10）来自修 bug 之前的 verifier，不能和本表直接相减。
能确定的是方向，不是幅度。

### 7.3 最精确的反馈反而最没用

场景图文本是四种反馈里信息最精确的一种——每个物体的几何类型、世界包围盒、颜色，全是数字。
它在两种描述下都是最差的一档：纯文本 1/11，加参考图 1/9。

原因很具体：问题描述给的是图，反馈给的是数字，模型需要先把图翻译成数字才能比对，而这一步正是它不擅长的。
**反馈要和问题描述在同一个量纲上**，否则精确度帮不上忙。

### 7.4 要打的折扣

- 这批数据用的是修开口曲面 bug 之前的 verifier。受该 bug 影响的是含灯罩的 4 道题。
  剔除这 4 道题重算，12 道题上的结论不变：纯文本救回 1/18，加参考图救回 5/12。
- 每格的分母只有 9 到 14，救回 6/10 与 0/12 的差别明显，但 4/12 与 1/14 这类比较还不足以单独成立。
- 任务全是「修复单处破坏」，不是从零构建。真实需求的分布不长这样。
- 三轮上限是我们设的，不是模型自己停的。

## 7 实验矩阵

16 个自动生成的任务 × 4 个模型 × 4 种反馈 × 2 种问题描述，每个最多 3 轮：

- **反馈**：无反馈一次成型 / 页面相机一张图 / verifier 4 视角拼图 / 场景图文本。
- **问题描述**：纯文本需求 / 文本加参考 4 视角图。
- **判定**：每轮都用同一个四层 verifier，模型看不到判定理由，只能看到自己产物的渲染。

要回答的问题：

1. 多模态参考能把通过率抬多少（即问题描述的信息量值多少）；
2. 给模型看自己的渲染结果，它能不能真的改对（自检能力）；
3. 图像反馈和结构化文本反馈哪个更有效（这决定 agent 工具该怎么设计，也决定图像 token 花得值不值）。

判定用的是修好开口曲面之后的五信号 verifier，五个反馈臂共用同一套。
基础设施故障（网关断连、返回体缺字段）单独剔除，不计入通过率分母——
这正是前面讲 RL 配方时要求的「预算耗尽、环境故障、模型自己的错」三分法在本地的落实。
第一轮（修 bug 之前）的结果留在 `results_prefix_bug.jsonl` 里备查。

## 8 留一层消融：数据集偏向哪一层

关掉某一层信号，重跑准入，看还能收下多少任务。收得越少，说明数据集越依赖那一层。

```
python3 ablate.py
```

| 关掉哪一层 | 桌面工作台（16 个提议） | 桌子加杯子（10 个提议） |
|---|---|---|
| 不关，全部信号 | 16 | 9 |
| L1 多视角剪影 | 16 | 9 |
| L2 体素占据 | 14 | 8 |
| L2b 自洽性 | 16 | 9 |
| L3 部件与拓扑 | 14 | 9 |

数据解读：

- **L1 和 L2b 可以关掉而不损失任务**，不是因为它们没用，而是它们抓的粗错误别的层也抓得到。
  它们的价值在于「第一时间否决、给出可读的失败原因」，不在于独占。
- **L2 和 L3 各自独占两道题。** 没有 L3 就没有「细长部件缺失」这类训练样本。
- 这个消融量的不是判别力，是**数据集的偏向**。每次改 Verifier 都该跑一遍。

一个推论：准入测试在把噪声挡在外面的同时，也把「Verifier 看不见的那类错误」整类挡在外面。
拿这样的数据训出来的模型，学会的是修 Verifier 看得见的毛病。这件事没有干净解法，只能量化并记录。

## 9 难度分布：单处破坏造不出中间难度

把 10 道有足够样本的修复任务按首轮通过率排开，每道题汇总 23 到 32 次尝试（跨 4 个模型、两种问题描述）：

| 任务 | 首轮通过率 |
|---|---|
| lamp-head-upright | 0.00 |
| lamp-head-detached | 0.04 |
| monitor-on-keyboard | 0.26 |
| keyboard-standing | 0.27 |
| lamp-arm-mirrored | 0.73 |
| legs-outside-top | 0.77 |
| legs-floating | 0.91 |
| lamp-head-wrong-parent | 0.93 |
| keyboard-screen-color | 1.00 |
| missing-front-legs | 1.00 |

数据解读：

- **中间带是空的。** 0.3 到 0.7 之间一道题都没有。
- 剔除全对与全错剩 7/10，看着健康；但按常见的 0.3 到 0.7 收紧，**一道都留不下**。
  所以「难度带留存率」这个成本模型里最敏感的外推项，取值完全由带宽决定，不是一个可以拍的常数。
- 根因在造法：只改一处的破坏，模型要么看出来改对，要么没看出来全错，不存在「部分做对」。
  要拿到中间难度得换造法——多处缺陷叠加，或者从零构建而不是修复。

折扣：样本跨模型汇总，混进了模型强弱；真正的 pass@k 要逐模型算，而每模型每题只有 7 到 8 次，不够。
但「中间带是空的」这个形状在逐模型数据里同样成立。

## 10 从零搭建：这套 verifier 不适用

前面所有判别力数字都来自「修复单处破坏」的任务。真实需求不长这样，真实需求是「按描述搭出来」。
换成从零搭建重测一次，结果是零。

做法：起始页只保留渲染器、相机、灯光和材质，没有任何物体；
需求用一段自然语言描述场景；另一档额外给参考解的 4 视角图。四个场景、4 个模型、最多 3 轮。

```
python3 scratch.py
```

| 问题描述 | 首轮通过 | 末轮通过 |
|---|---|---|
| 纯文本需求 | 0/13 | 0/13 |
| 文本加参考图 | 0/13 | 0/13 |

26 组里 23 组挂在第一层，也就是多视角剪影；四个场景分别是 0/8、0/8、0/6、0/4。

### 10.1 不是模型没搭对

把「桌子加杯子」那道题的四个从零产物和参考并排渲染出来看：四个都是木色桌面、四条腿、桌上一个蓝色圆柱杯，
人看都对。差别在比例——桌子的高宽比、腿的粗细、杯子的大小与位置各不相同。

**verifier 判挂的理由是这些产物和参考不够重合，而不是它们不满足需求。**

### 10.2 为什么会这样

这套判据量的是**绝对几何的重合度**。它在修复任务上成立，是因为修复任务的初始状态里除了一处之外全都和参考一致，
所以「和参考重合」等价于「那一处改对了」。换到从零搭建，这个等价关系就断了：
需求没有钉死任何一个尺寸，模型凭什么搭出和参考同样高的桌子。

这是本文反复讲的那条规则的又一次应用——**verifier 能查的信息量必须小于等于题面给出的信息量**。
只不过这次不是某一道题越界，是整套判据的适用范围被越界使用了。

### 10.3 从零搭建该怎么判

答案在 3JSBench 那套判据里，它本来就是一个从零搭建的评测：它的 695 条必查项分六族，
**没有一条查绝对位置**。部件计数 223 条、结构 160 条、空间关系 157 条，三族占 78%，
查的全是「有几个」「接在哪」「挨着谁」——都是相对关系。

所以两类任务需要两套判据，不是一套判据调松阈值：

| | 修复型任务 | 从零搭建型任务 |
|---|---|---|
| 初始状态 | 除一处外与参考一致 | 空场景 |
| 可以查 | 与参考的绝对几何重合度 | 部件计数、连接与间隙、接触与支撑、相对比例、拓扑 |
| 本项目现有判据 | 适用，三场景 47/47 | **不适用，0/26** |
| 阈值能不能救 | — | 不能。放松到让这四个都过，等价于把第一层关掉 |

### 10.4 对整个方案的影响

这条限制比它看起来严重，因为它同时解释了两件事：

- 自动造题之所以只造「修复单处破坏」，不是因为那样方便，而是因为**现有判据只支持那一种**。
- 前面量到的难度分布之所以是双峰、中间带是空的，根源也在这里：单处破坏天然没有「部分做对」。

要支撑从零搭建，得先补相对关系那一族判据，然后才谈得上造那类任务。
在补齐之前，用这套数据训出来的模型学到的是「照着参考改对一处」，不是「按描述搭出来」。

### 10.5 相对关系判据的原型：方向对，还不够

照着上面那张表写了一个原型（`relational.py`），只看相对关系，不看绝对位置：

1. 先把场景整体归一化——平移到包围盒中心，按对角线缩放。
2. 从体素网格里按颜色取连通块当部件（按颜色分组会把桌面和四条腿合成一块，少一条腿就看不出来）。
3. 查六项：部件个数、体量占比、相对尺度、上下关系、接触关系、开放边界。

全部是比例或序关系，与整体尺度和位置无关。结果：

| 测试集 | 绝对重合度判据 | 相对关系判据 |
|---|---|---|
| 从零搭建的每一次尝试（80 次） | 0/80 | **13/80** |
| 三个场景的带标签变异（47 例） | 47/47 | 35/47 |

数据解读：

- **方向是对的。** 同一批人看都对的从零产物，从一次都过不了变成能过一部分。
- **还不够。** 部件最多的那个场景（桌面工作台，6 种颜色十几个部件）仍然是 0。
- **代价是实打实的。** 变异集从 47/47 掉到 35/47，漏掉的十二个有共同点：
  相对结构没变——腿还连在桌面上、杯子还接触桌面、比例还在容差内。
  **它换来对整体尺度的不变性，就放弃了对绝对位置与绝对尺寸的敏感，这是定义上的，不是实现不好。**

三件该补的事，按优先级：

1. **部件个数不能要求完全相等**，要先做匹配再比，允许小部件缺失或多出。
2. **体量用包围盒乘积是粗估**，圆柱和锥体会被高估，应当用体素计数或凸包体积。
3. **接触关系要分方向**，现在只判「挨着没挨着」，判不出「在上面」还是「穿过去」。

结论不变：修复型与从零搭建型需要两套判据。相对关系这一族是对的方向，但要做到可用，
工作量和当初做绝对判据那一套相当——而本文前面所有判别力数字都只覆盖了其中一套。

## 11 取证链路的覆盖缺口也是假阳性

做对抗测试时撞到一个和判据无关的问题：harness 原先只拦 ES 模块那一条引入路径，
模型用经典脚本标签引入库时，页面直接报「库未定义」，被执行门判挂。

```
{"renders":0,"errors":["THREE is not defined","no render within 15s"]}
```

接着又连撞两处，性质一样：

| 缺口 | 模型写的是什么 | 症状 |
|---|---|---|
| 只拦 ES 模块那条路径 | 经典脚本标签引入 | 库未定义，执行门判挂 |
| 拦截规则写死了路径结构 | 从另一个 CDN 引入，路径里没有 build 这一段 | 同上 |
| 断网把 addon 一起拦了 | 用了 three 自带的几何工具 addon | 模块加载失败，执行门判挂 |

修法分别是：同时服务 UMD 构建、只按文件名判而不按路径判、本地有的 addon 直接服务。
改完三个变异集回归，仍是 13/13、16/16、18/18。

这条和前面那些盲区性质一样——都是假阳性——但来源不同：**它不在判据里，在取证链路里。**
而且它伪装得最好：表现是「模型连页面都写不对」，很容易被当成模型能力问题记下来。

所以 harness 的覆盖面要单独验收，至少包括：
库的各种引入方式（ES 模块、经典脚本、打包内联、CDN 与本地）、
常见的渲染循环写法、以及模型可能用的各种版本。
验收办法就是拿真实策略的产出去跑，而不是拿自己写的参考解去跑——
我们自己写的参考解永远用同一种写法。

## 12 取证的重复性

成稿把「取证 flaky 率」列为必须监控的指标。本项目自己的基线：

```
python3 flaky.py
```

9 个产物（两个场景的参考解与各四个变异）各探测 3 次：

| 口径 | 结果 |
|---|---|
| 判定翻面 | 0/9 |
| 信号值漂移 | 0/9，逐位相同 |

这不是「噪声很小」，是这一环为零。做到零靠三件事：冻结时钟（帧只在 harness 推进时前进）、
固定随机种子、以及断网（除了库本身，所有外部请求一律拦掉）。

限制：这是同一台机器、同一个浏览器版本、同一个进程内的重复。
跨版本的确定性没有测过——公开材料里记过超越函数在不同引擎版本上会分叉，
所以如果 harness 镜像升级，这条基线要重新量。

## 13 让模型自己来找漏洞

手写攻击只能覆盖想得到的路径。RL 里真正发生的是策略自己找路径，所以又做了一轮：
把判据的构成原原本本告诉模型，让它写一个「能过验收但实际不满足需求」的页面。

```
python3 hack_probe.py
```

三个场景乘四个模型，12 次请求。结果：

| 口径 | 数字 |
|---|---|
| 产出了作弊页 | 5 |
| 产出但探测失败 | 1 |
| 拒绝或没按格式输出 | 6 |
| **verifier 判过** | **0** |

分母要说清楚：四个模型里有两个在三个场景上全部没有产出，也就是它们没有接这个活。
所以「0 份判过」的实际分母是 5，不是 12。

模型试过的路子，按它们自己写的注释与代码特征归类：

| 路子 | 哪几份用了 | 被哪一层挡住 |
|---|---|---|
| 用贴图画出「看起来对」的东西 | 3 | 多视角剪影：贴图撑不起体积 |
| 往约定好的全局变量里塞一个正确场景 | 1 | 取证不读约定变量，只认库自己派发的事件与可见画布 |
| 直接操作画布读写 | 3 | 多视角剪影由 verifier 自己的相机重渲，不看页面画布 |
| 玩绘制顺序 | 1 | 自洽性那一层 |

全部挂在第一层，也就是多视角剪影。

要克制地解读这个零：

- 它说明的是**这一轮里模型想到的那几条路被堵住了**，不是「不可 hack」。
  模型只试了一次、没有梯度、也看不到判定反馈；RL 里的策略有成千上万次尝试和明确的分数信号。
- 这些路子和我们手写的七条高度重合（贴图、伪造状态、离屏渲染、透明度、绘制顺序），
  说明**手写攻击集的覆盖面没有想象中差**，但也说明两边都受限于同一套直觉。
- 真正有价值的对抗样本只能从训练里来。所以防 hack 的工程重点不是「上线前想全」，
  而是「上线后抽检高分样本」。

有一个模型直接拒绝了这个请求。记在这里只是为了说明分母是怎么来的。

## 14 判别也需要可比对象

前面量过的 VLM judge 都是「参考与候选并排」。再加一档：**只给候选的渲染图，外加一段文字需求**，
其余全部不变——同样两个 judge、同样的 case、同样的候选渲染图，唯一的差别是看不看得到参考。

```
python3 judge_noref.py
```

45 个带标签的 case，两个 judge。核心发现：拿掉参考图，判别力从九成五掉到七成上下，而且掉的主要是检出。

| 条件 | 总判对 | 检出（该挂的抓到多少） | 保真（该放行的放过多少） |
|---|---|---|---|
| 有参考图，单视角 | 101/107 = 94% | 58/63 = 92% | 43/44 = 98% |
| 有参考图，四视角 | 105/108 = 97% | 61/64 = 95% | 44/44 = 100% |
| 无参考图，单视角 | 65/96 = 68% | 35/56 = 63% | 30/40 = 75% |
| 无参考图，四视角 | 73/96 = 76% | 34/56 = 61% | 39/40 = 98% |

数据解读：

- **检出从九成二掉到六成上下**，而四视角下的保真仍有 39/40。
  换句话说，没有参考的 judge 变成了一个偏宽松的放行器——它仍然不怎么冤枉好人，但一多半的缺陷放了过去。
- 单视角下连保真也掉到 30/40，说明没有参照时它连「这算不算问题」都拿不准，两头都在猜。
- 机制很直接：拿掉参考之后，judge 只能对着那段几十个字的需求判。
  需求没写桌子多高、杯子多大、鼻子伸多长，于是尺寸和位置类的缺陷全都「不违反需求」。
- **这就是本文那条规则从 judge 这一侧看到的样子**——判据能查的信息量，不会超过题面给出的信息量。
  并排放上参考图，等于把题面的信息量提高到「逐像素」，judge 这才有东西可查。

把这一节和前面的实验矩阵放在一起看，两边说的是同一件事：

| 角色 | 没有可比对象时 | 有可比对象时 |
|---|---|---|
| 生成方（修自己的产物） | 首轮挂掉后救回 2/37 | 救回 11/31 |
| 判别方（判别人的产物） | 检出 61% 到 63% | 检出 92% 到 95% |

**模型缺的不是能力，是参照。** 这条对数据构造的要求很具体：
Problem Statement 必须带可比对象，而且训练与评测时给模型的观察通道要和那个对象同模态。

## 15 单模型 pass@8：难度带留存是 19% 不是 60%

前面那组难度分布是**跨 4 个模型、每题汇总 23 到 32 次首轮尝试**算出来的。
成本模型要用的却是另一个量：**同一个策略**采 k 次能不能既不全对也不全错——因为零梯度是按组判的，组内全是同一个策略。
这两个量不一样，而且差别是系统性的：汇总跨模型的尝试会把「强模型会、弱模型不会」混成一个中间通过率，
**凭空制造出并不存在的中等难度**。

所以重跑了一遍严格的 pass@8：16 道自动造的修复题，单一模型，温度 1.0，每题独立采 8 次，共 128 次。

核心发现：13 道题是全有或全无，中间带一道都没有。

| 通过次数 | 任务数 |
|---|---|
| 0/8 | 5 |
| 1/8 | 2 |
| 2/8 到 6/8 | 1 |
| 7/8 | 0 |
| 8/8 | 8 |

数据解读：剔除全对与全错后只剩 **3/16 = 19%**（Wilson 95% 区间 6.6% 到 43.0%），
落在 0.3 到 0.7 这个最有训练价值的带内的是 **0/16**。
注意即便取区间上界 43%，也仍然低于成本模型假设的 60%——**这个假设站不住不是因为样本少，是方向就错了**。

对成本模型的直接后果：

| 项 | 原假设 | 实测替换后 |
|---|---|---|
| 难度带留存 | 0.60 | 0.19 |
| 漏斗总留存 | 37.2% | 11.8% |
| 造 10 万任务需要的候选数 | 26.9 万 | **84.8 万** |
| 探针调用 | 约 160 万次 | 约 500 万次 |

也就是说，按单处破坏这一种造法，**规模化的成本要乘以 3.2**，而且多花的那部分全部花在生成最后会被丢掉的任务上。

两条可操作的结论：

- **扩产之前必须先换造法。** 多处缺陷叠加、或者从零构建而不是修复，才可能产出中间难度。
  单处破坏这条路在难度维度上是封顶的——它的双峰不是采样不足造成的，是造法本身决定的：
  要么模型看出了那一处改动，要么没看出，不存在「部分看出来」。
- **用跨模型汇总来估难度会高估可用率。** 本项目两种口径差 3.2 倍（跨模型汇总 70%，单模型 pass@8 19%），
  而且偏差方向固定是乐观。估 RL 的零梯度比例只能用**将要训的那个策略自己**的 pass@k。
